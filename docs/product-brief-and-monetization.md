# そらばん：やりたいことのまとめと、外に売れる形（別の開発に持ち出す用）

作成日：2026-10-30 ／ 作成：Claude（のりさんの依頼）
元にした文書：`docs/00_NORTH_STAR.md`（§0.1.9〜§0.1.11、§8）、`docs/north-star-revision-proposal.md`、`docs/design/design-system.md`
注意：売り方（§6）は**案**です。北極星は「課金プランの検討は年度末の見直しまで行わない」と決めています（§0.1.11）。ここでは、別の開発に反映するための仮説として書きます。法律の判断は専門家の確認が必要です（§8）。

---

## 1. 一言で

> 飛ばす前から飛んだ後までの手続き（計画 → 点検 → 日誌）を、迷わず漏れなくこなせるようにする運航管理アプリ。どの画面でも「なぜその結論か」を、法令・条例・判例（参考）の出典つきでたどれる。

- 最初の利用者は自社（フューチャーテック）。次に山陰の事業者、その後に全国。
- 申請・通報は、DIPS 2.0 などの公式の手続きで、**利用者本人が本人名義で**行う。そらばんは「準備と記録と根拠」を担当し、代わりに出さない。

## 2. 解く課題

| 課題 | そらばんの答え |
|---|---|
| 飛ばしてよいか、法令・条例が多層で分からない | 多層判定。分からないときは厳しい側に倒す（見落としゼロ） |
| 計画・点検・日誌がバラバラで漏れる | 一つの「飛行」でつなぎ、「次にやること」を出す |
| 後から「なぜ飛ばせたのか」を説明できない | 判定をそのときの版で保存（不変のスナップショット）。根拠を台帳でたどれる |
| 機体・操縦者の許可や期限の管理 | 一覧と期限の札。期限が近い・切れたを見逃さない |
| 現場（屋外・手袋・日差し）で使いにくい | 現場モード（大きいボタン、高コントラスト、動きなし） |

## 3. できること（現在地：2026-10-30）

**できている（社内で使える段階の手前）**
- 判定（トップ画面）：地図、規制レイヤー、結論と根拠、小型無人機等飛行禁止法の区域表示
- 運航管理：ホーム／計画／点検／日誌／登録、現場モード、通報の準備と記録、事故・ヒヤリハット、判定の履歴
- 登録：機体、操縦者、許可・承認（期限の札）、地点、利用者（役割と認可）
- 品質：自動テスト多数、アクセシビリティ検査、デザイン基準（v2）

**予定**
- DIPS 2.0 連携（機体・操縦者の読み取り。航空局の回答待ち。それまでは手入力）
- 根拠の台帳の整備（確認の状態：確認済み／要確認／未確認）
- 条例の収録地域の拡大（収録なしは「収録なし」と示す）
- 判例は「参考として示す」だけ（結論には使わない）

## 4. 別の開発に持ち出せる設計の考え方

他の領域（建設・消防・点検業務・許認可が絡む業務など）にも使えるものです。

1. **背骨は業務の流れ、判定は根拠つきの部品。** 判定を看板にせず、毎日使う流れに載せる。
2. **根拠の台帳。** 根拠ごとに、種類・名称・条項・URL・版・取得日・確認日・確認者・確認の状態を持つ。
3. **確認の3段階。** 確認済み／要確認／未確認。一次情報で確認できないことは断定しない。要確認・未確認は安全側に倒す。
4. **「見つからなかった」と「存在しない」を区別。** 確認の日付と範囲を書く。
5. **スナップショット。** 判定や計画はそのときの版で不変に保存し、後から辿れる。
6. **外部への送信は抽象の裏に置く。** 手動・模擬・API の3つを差し替えられる形（通報ゲートウェイ）。API が使えなくても製品が成立する。
7. **分からないときは「要」。** 「不要」「問題なし」と出さない。
8. **画面の掟。** 結論を入力の直下に。色は意味ごとに分ける（操作の橙と、判定の色は別）。現場モードは別の基準（7:1、56〜64px、影なし、動きなし）。
9. **開発の進め方。** 契約（完了条件）→実装→見た目→独立評価。手元で全テスト（DB含む）を通してから push。

## 5. 外に売るときの「商品」は何か

**売るもの（安全な側）**
- 記録・管理・期限の通知（点検、日誌、台帳）
- 法令・条例・判例（参考）の**調べ物の整理と出典の提示**
- 申請・通報の**準備**：利用者が入力した内容を、公式の入力順に整えて見せる、コピーできる
- 利用者本人が行った結果の**記録**

**売らないもの（避ける側）**
- 利用者の代わりに申請書を作って出すこと、「代行」「代理」「自動申請」
- 個別の事案について「適法です」と法的な結論を保証すること
- 判例に基づく自動の結論

## 6. 売り方の案：買い切りかサブスクか

| 観点 | サブスク（月額・年額） | 買い切り |
|---|---|---|
| 法令・条例は改正される | 更新が価値そのもの。売り方と合う | 更新が止まると古い判定が残る。誤判定のリスクと責任が重い |
| 収益 | 安定。保守の費用を賄える | 一度きり。保守は持ち出し |
| 利用者の受け止め | 「更新と根拠が付く」が分かりやすい | 安心感はあるが、更新が別料金になりやすい |
| 責任 | 常に最新版を提供する義務は規約で整理できる | 版の保証が難しい |

**推奨：サブスク（年払い割引つき）。** 理由は、価値の中心が「最新の根拠」だからです。買い切りを選ぶ場合も、「ソフト本体は買い切り、法令・条例の更新は年額」という分け方にします（更新なしで売ると、古い判定を売ることになります）。

**プランの案**（既存の §8.1 を、方針に合わせて直したもの）

| プラン | 対象 | 中身 |
|---|---|---|
| お試し | 個人 | 月の判定件数に上限、記録は少数 |
| 事業者 | 個人事業主・小規模 | 判定、計画・点検・日誌、期限管理、PDF 出力 |
| チーム | 中小事業者 | 複数利用者と役割、監査用の履歴、API |
| 組織向け | 大手・自治体 | SSO、収録地域の追加、個別の取り決め |

- 旧案の「申請補助」は、**「申請の準備（入力の整理）」**に言い換える（行政書士法に触れる読みを避けるため）。
- 価格は未検証。まず自社と山陰の数社で「いくらなら続けるか」を聞いてから決める。
- 観光庁・自治体向けは、月額ではなく、調査・導入支援・ライセンスの形が現実的（仮説。需要の確認が先）。

## 7. 法的な線引き（表現と設計のルール）

### 行政書士法（官公署に出す書類の作成）
考え方：報酬を得て、他人の依頼に応じて官公署に提出する書類を作る行為が問題になり得る。そらばんは「利用者本人が入力し、本人名義で出す」道具に徹する。

| 避ける表現・設計 | 使う表現・設計 |
|---|---|
| 申請を代行／代理申請／自動申請 | 申請の準備を支援／入力の整理／コピーして DIPS に入力 |
| 申請書を作成します | 入力内容を公式の項目順に表示します |
| そらばんが通報しました | 通報は DIPS で行ってください。結果の記録をそらばんに残せます |
| 事務所側が内容を決めて入力 | 利用者が内容を入力・確認する（確認画面を必ず挟む） |

### 弁護士法（法律事務の取扱い）
- 判例や条文から、個別の事案の法的結論を有料で出すと、法律事務に近づく可能性がある。
- 判例は「参考」にとどめ、結論に使わない。画面に「判断の責任は利用者にあります」を明記する。

### その他
- 官公庁・自治体サイトの利用条件（robots.txt、利用規約）の確認、著作権法 32 条の範囲での引用。
- 個人情報（操縦者の氏名・資格）の取り扱いと、利用規約・免責の整備。
- DIPS の API を使うときは、DIPS 側の利用規約に従う。

## 8. 専門家に確認すること（外に売る前）

1. **行政書士または弁護士：** 画面・料金表・営業文書の表現が、行政書士法と弁護士法に触れないか（1回）。
2. **グレーゾーン解消制度（経済産業省）：** 「申請の準備を支援するソフトの提供」が適法か、事業者として照会できる。確実にしたいときの手段。
3. **利用規約・免責：** 判定の誤りに対する責任の範囲。
4. **航空局：** DIPS 連携の可否と利用条件（問い合わせ中）。
5. **セキュリティ診断：** 山陰への展開前に1回（北極星の決定 7）。

## 9. 次の一歩（案）

1. 自社の点検業務で段階 0 を始める（手入力運用）。
2. 山陰の2〜3社に見せて、「何に払うか」を聞く（判定／日誌／期限管理のどれか）。
3. 専門家の確認（§8-1）を先に済ませ、売る言葉を固める。
4. 価格は、その聞き取りの後に決める。
