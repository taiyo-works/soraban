## 0.1 2026年10月の方針（§3.2・§6・§8.2・§9・§10 より優先する）

そらばんは、判定エンジンと運航管理を一つの道具として、フューチャーテック株式会社の事業として進める。本節は 2026-10-18 に定めた方針であり、§3.2 の機能マップ、§8.2 の事業ロードマップ、§9 のリスク、§10 のチェックリストと食い違う場合は本節を優先する。詳細と図は「そらばん 方針と運航管理」（https://claude.ai/code/artifact/a154207b-9400-4897-a74d-4eeaf8f49486 ）にある。

### 0.1.1 判定と運航管理を一つにする理由

判定が飛行ごとの義務を決め、運航管理がその義務を果たす。特定飛行では、事前の飛行計画の通報と、飛行日誌（飛行記録、日常点検記録、点検整備記録）の記載が義務となる。どの飛行が特定飛行に当たり、どの条例上の手続きが要るかを決めるのが、そらばんの判定である。

判定だけの道具は計画のときにしか開かれず、対価を得にくい。飛行日誌の道具は飛ぶたびに開かれるが、飛行日誌アプリ（ドローンノートなど）が法人向けポータルと DIPS 2.0 連携まで備えており、単独では差がつかない。価値の芯は、判定の結果が通報と日誌に流れ込み、飛行ごとに判断の根拠（どの法令と条例を、どの版と確認日で判定したか）が記録に残ることに置く。

### 0.1.1a 目標

最終的な目標は、全国での提供と、安定した稼働である。山陰（鳥取県・島根県）での自社運用は、そこへ向かう最初の段階と位置付ける。当面の範囲を山陰に絞るのは、網羅より正確さを優先し、運用の実績を積むためであり、目標そのものを山陰に限るものではない。このため、データの収集と更新、判定エンジン、運用の仕組みは、対象地域を広げても作り直さずに済む形で作る。

### 0.1.2 当面の範囲

山陰で自社の点検が実際に飛ぶ場所に絞り、網羅より正確さを優先する。

| 区分 | 内容 |
|---|---|
| 地域 | 米子、境港、出雲を起点に、鳥取県と島根県 |
| 判定の層 | 航空法（人口集中地区から工業専用地域を除いた区域、空港等周辺、150m 以上、緊急用務空域）、小型無人機等飛行禁止法（対象施設とその周囲おおむね 1,000m）、条例と施設管理者の定め（都市公園、指定史跡、港湾など） |
| 運航管理 | 飛行計画、判定スナップショット、日常点検、飛行記録、点検整備、証跡の出力 |
| 条例データ | 各件に出典（条例名、条番号、URL）、確認日、確認者を持たせる |
| 当面やらない | 全国の自治体の網羅（最終目標だが、当面の段階では行わない）、趣味の利用者向けの一般公開、判定結果を保証として示すこと |

2026-07-01 から人口集中地区の規制は工業専用地域を除く形に変わり、2026-07-14 から小型無人機等飛行禁止法の周辺地域はおおむね 1,000m になった。判定の層はこの二つを反映した状態を目標とする。2026-10-18 時点の判定エンジンはどちらも未反映であり（美保基地周辺は 300m のまま、人口集中地区から工業専用地域を差し引いていない）、第 1 段階の最初に改める。改めるまでは、該当する判定を過小（飛行禁止法）または過大（人口集中地区）に出しうる。

### 0.1.3 進め方

最初の利用者は、三社協業で行っている自社のドローン点検業務とする。自社で使い続けられる形になってから、協業先、試用先、社外の点検事業者の順に広げる。

| Phase | 期間（案） | 内容 |
|---|---|---|
| 1 | 2026-11 〜 2027-03 | 自社の点検で運用。判定と飛行計画、日常点検と飛行記録、点検整備と証跡の出力。DIPS 2.0 API の利用申請 |
| 見直し | 2027-03 末 | §0.1.4 の三点で続け方を決める |
| 2 | 2027-04 〜 2027-09 | 協業先と試用先へ。DIPS 2.0 との連携、協業先との記録の共有、点検報告書の出力 |
| 3 | 2027-10 〜 | 社外の点検事業者への提供、対象を中国地方へ拡大、自治体側の受付支援を検討 |

### 0.1.4 年度末の見直しで測ること（案）

| 観点 | 基準（案） |
|---|---|
| 自社での定着 | 2027-01 以降の自社の飛行記録を、すべて運航管理で作成している |
| 社外の対価 | 有償、または有償を前提とした試用に合意した運用者が 1 社以上ある |
| 条例データの鮮度 | 対象範囲の条例データの確認日が、すべて 90 日以内 |

三点を満たせば Phase 2 へ進む。社外の対価だけが満たせない場合は、社内の道具として維持し、範囲は広げない。自社で定着しない場合は、使われなかった理由を現場で聞き取り、形を見直す。

### 0.1.5 想定するリスクと備え

| リスク | 備え |
|---|---|
| 条例情報の無償公開 | オーストラリア政府は 2024-02 に地域ルールの地図を無料 API で公開した。国内でも DIPS 2.0 の飛行禁止エリア情報 API に「条例等で定めるエリア」という種別がある。山陰での収録状況を API の利用開始後すぐに確かめる。価値は判定から記録までの流れに置き、公的データが出れば取り込めるよう、データの取得口を差し替えられる作りにする |
| 判定の誤り | 判定は判断の支援として示し、各結果に出典と確認日を表示する。飛行前の手順に運航管理者の確認を入れる |
| 担当者への依存 | 条例データの更新手順書と管理画面を用意し、担当者が替わっても更新が続く形にする |
| 制度改正 | 国土交通省、警察庁、対象自治体の例規の更新を月 1 回確認する |
| 飛行日誌アプリとの競合 | 飛行日誌の単体機能では競わず、判定との接続を前面に出す |

### 0.1.6 技術上の決定

- データベースは Neon（PostgreSQL + PostGIS）とする。
- DIPS 2.0 API は接続元 IP アドレスの登録が必要なため、DIPS 宛ての通信だけを固定 IP の中継（検証環境は本社回線、本番は国内 VPS を想定）経由にする。アプリ本体は Vercel のまま動かす。
- Vercel の関数リージョンは、Neon（シンガポール）に近い sin1 とする（2026-10-18 設定済み）。

### 0.1.7 機能を足す前の確認項目（§10 に先立って問う）

1. 判定から通報、点検、記録までの手間か誤りを減らすか？
2. 山陰で自社の点検が飛ぶ場所で使うか？
3. 示す判定や記録に、出典と確認日を持たせられるか？
4. 担当者が替わっても、手順書と管理画面で維持できるか？

一つでも満たさない機能は、年度末の見直しまで保留する。

### 0.1.8 特許と知的財産（§6 より優先する）

- 2026-10-19 時点で、特許の出願も弁理士への相談も行っていない。当面は出願しない見込みである。§6 の特許戦略と、§5・§9・§10 の特許を前提とした記述は、この方針のもとでは適用しない。`docs/patent-claim-draft.md` は検討の記録として残し、保留とする。
- 特許に頼らない強みは、判定の出典と確認日を持つデータの質、判定と運航管理（通報・点検・記録）の接続、山陰での自社運用の実績とする。
- 出願するかどうかの最終判断は、社外に広げる前（2027-03 末の見直し）に行う。社外へのデモや公開の後では、原則として特許を取れなくなるためである。判断までは、社外への説明は秘密保持の取り決めのもとで行う。

## 1. プロダクトビジョン

### 1.1 顧客像（Primary Persona）

- **山陰地方の中小ドローン事業者**：従業員数 1〜20 名、年商 数千万〜数億、太陽光点検／インフラ点検／害獣駆除／測量を生業とする
- **意思決定者は社長または運航管理者**：現場経験者で、デジタルツール導入のリテラシーは中程度。Excel と DIPS は使えるが、複数 SaaS の連携運用は重荷
- **痛点は「条例の把握コスト」と「事故時の説明責任」**：自治体ごとに条例が違い、最新版を追いきれない。万一の事故時に「適切な事前確認をした」と証明できる仕組みが弱い

### 1.2 原体験（Why this, why now）

- 開発者本人が商用ドローン点検（太陽光・害獣・狭所）の現場経験を持ち、**条例調査と申請書作成に年間数十時間を消費**してきた
- 国交省は 2026 年度以降の **UAV Traffic Management（UTM）** 整備を進めているが、これは「空域管制側」の仕組み。**運航事業者側の事前判断 UX** は依然として空白
- 自治体条例は **公開されているが構造化されていない**。LLM の進化により、初めて低コストで構造化収集が可能になった

### 1.3 「7〜8 割が感動する」の操作的定義

「感動」を曖昧にしない。以下の **5 指標** すべてを満たすときに到達したと判定する：

1. **初回タップから 10 秒以内に「飛行可否」が信号機色で出る**
2. **判定根拠が 3 タップ以内で全レイヤー分閲覧できる**
3. **同業他社プロダクト（Aloft, DJI FlySafe）に戻ろうと思わない**ほどの情報密度差を体感する
4. **国交省・自治体・保険会社・依頼主のいずれに見せても恥ずかしくない**書面が自動出力される
5. **デザインが「業務ツール」ではなく「日用品の家電」のように感じられる**（後述：iOS 設定アプリ品質を基準）

## 3. プロダクト設計

### 3.1 コアエクスペリエンス（North Star UX）

ユーザーが地図上に飛行予定地を 1 タップ → 高度・時間・機体重量を入力 → **即座に信号機色で可否表示** → 各レイヤー（航空法・条例・電波法 等）の判定理由が縦に展開可能。これがプロダクトの背骨。

```
[地図タップ] → [飛行パラメータ入力] → [信号機判定] → [レイヤー別根拠] → [申請書類生成 or 飛行ログ記録]
```

### 3.2 機能マップ（v1.0 → v2.0 → v3.0）

| 階層 | v1.0（α、〜2026/05） | v2.0（β、〜2026/10） | v3.0（GA、〜2027/03） |
|---|---|---|---|
| 判定エンジン | 山陰主要 5 自治体の条例構造化、5 法令統合判定 | 中国地方全自治体、緊急空域 API 連携 | 全国対応、UTM 連携 |
| 申請ワークフロー | DIPS 入力支援（コピペ補助） | DIPS API 連携（実装可能性に応じ） | 完全自動申請 |
| 証跡 | PDF 出力、改ざん検知ハッシュ | タイムスタンプ局連携 | ブロックチェーン記録（オプション） |
| 多言語 | 日本語のみ | 英語追加 | 中国語・韓国語追加 |
| プラットフォーム | Web（PWA） | iOS / Android アプリ | API / Webhook 提供 |

### 3.3 拡張機能アイデア（北極星に沿う範囲で）

採用判断の基準：「3.1 のコア体験を強化するか、それとも逸脱させるか」。逸脱するものは Phase 4 以降に積む。

- **保険連携自動見積**：判定済飛行プランから損保各社（東京海上日動「DJI 保険」、三井住友「ドローン保険」等）の API/フォームへ流し込み、リスク係数別の保険料を即時提示
- **AI リスクスコア**：人口密集度・気象・機体特性・パイロット経験を重み付け、0〜100 で表示。事故統計を学習源に
- **地権者推定**：地番から登記情報・公図を引き、推定地権者と通知書テンプレートを提示（実装は登記情報サービスとの連携要）
- **クライアント向けレポート**：飛行前計画・飛行ログ・コンプライアンス証跡を 1 PDF に。**依頼主の稟議資料としてそのまま使える品質**を目指す
- **オフラインモード**：山間部・地下・離島での圏外運用に備え、判定結果を事前ダウンロード可能に
- **CO₂ 算出**：機体・飛行時間から推定排出量を算出、ESG 報告対応
- **A/B ルート比較**：同一案件で 2 案を並列判定、信号機の差で最適案を即決
- **チームコラボ**：複数パイロットの飛行スケジュール衝突検知、機体貸出管理
- **監査モード**：国交省・保険会社の立入検査対応のため、改ざん検知付きの全履歴エクスポート
- **コンプライアンス・スタンプ**：撮影写真・動画のメタデータに飛行許可番号を埋め込み、納品時の証跡とする

> **棄却済アイデア**：機体販売、保険販売、操縦講習。これらは「コンプライアンス基盤」というポジショニングを希釈するため、当面実施しない。

## 4. UI・デザイン哲学

### 4.1 コア原則（4 つの掟）

1. **モノクロ＋単一アクセント**：色は判定情報のためにある。装飾色を持たない。アクセントは藍（#1B3B6F）または墨（#1C1C1E）で固定
2. **タイポグラフィ・ファースト**：アイコンよりも文字で語る。和文 Inter Display + 游ゴシック、欧文 Inter
3. **余白は機能**：情報密度を上げない。1 画面 1 主題。Apple 設定アプリの行間を基準
4. **動きは最小限**：マイクロインタラクションは判定変化時のみ。信号機の点灯遷移には 240ms の ease-out

### 4.2 配色仕様

| 用途 | ライト | ダーク | 備考 |
|---|---|---|---|
| 背景 | `#FAFAF9` | `#0A0A0A` | 純白・純黒は避ける |
| 主要文字 | `#0A0A0A` | `#FAFAF9` | 14:1 以上のコントラスト |
| 補助文字 | `#52525B` | `#A1A1AA` | |
| アクセント（藍） | `#1B3B6F` | `#3D6FB8` | リンク・主要 CTA |
| 信号・青（OK） | `#16A34A` | `#22C55E` | 飛行可 |
| 信号・黄（注意） | `#CA8A04` | `#EAB308` | 条件付可・要申請 |
| 信号・赤（不可） | `#DC2626` | `#EF4444` | 飛行不可 |
| 罫線 | `#E5E5E4` | `#27272A` | |

色覚多様性対応：信号機 3 色は色だけに依存せず、**色＋アイコン＋テキストラベル**の三重符号化で表現する。

### 4.3 タイポグラフィ階層

| 役割 | フォント | サイズ | 行間 |
|---|---|---|---|
| Display（信号機テキスト） | Inter Display 600 | 48px | 1.1 |
| H1 | Inter / 游ゴシック 700 | 32px | 1.2 |
| H2 | 600 | 24px | 1.3 |
| Body | 400 | 16px | 1.6 |
| Caption | 400 | 13px | 1.5 |
| Mono（座標・許可番号） | JetBrains Mono | 14px | 1.5 |

### 4.4 国際性とローカリティの両立

- **日本人の安心感**：書体に游ゴシック系の柔らかさを採用、行政書類で見慣れた縦余白を確保
- **海外ユーザーへの訴求**：英語版で和語感を排除、`Soraban`（ローマ字）でブランディング、Apple/Linear 系の現代 SaaS テンプレートに沿う
- **共通の高級感**：余白・タイポグラフィ・モノクロ＋単一アクセントは万国共通の「上質」記号

### 4.5 アクセシビリティ要件（妥協しない）

- WCAG 2.2 AA 準拠
- VoiceOver / TalkBack でのフル操作
- フォーカスリングは藍色 2px、絶対に消さない
- キーボードのみで全機能到達可能
- 動的拡大（200%）でレイアウト崩壊しない
- アニメーションは `prefers-reduced-motion` に従う

## 5. 技術アーキテクチャ（特許性と直結する部分）

### 5.1 自治体条例構造化パイプライン（特許コア）

```
[自治体公式サイト/例規集] 
    ↓ 自動巡回（Playwright + 差分検知）
[原文 HTML/PDF]
    ↓ 構造抽出（Gemini Flash-Lite + プロンプト連鎖）
[構造化中間表現（JSON）]
    │ ├ 規制対象行為（離発着/飛行/撮影）
    │ ├ 適用区域（公園/河川/学校/特定地番）
    │ ├ 期間条件（時間帯/季節/イベント時）
    │ ├ 許可要件（届出/許可/同意/事前協議）
    │ └ 出典（条文番号・施行日・改正日）
    ↓ 地理空間紐付け（PostGIS）
[Soraban 内部条例 DB]
    ↓ 版管理・人手レビュー
[本番判定エンジンに供給]
```

**技術的な肝**：
- LLM の出力を **検証スキーマ（Zod / JSON Schema）で強制構造化**
- 区域指定が「地名」のみの条例も多いため、**地名→ポリゴン変換**にジオコーディング + 国土地理院数値地図を組み合わせる
- 改正検知は条文ハッシュ差分で判定し、人手レビューに回す（自動更新は誤判定の致命傷）

### 5.2 多層法令判定エンジン

入力：飛行地点（緯度経度／ポリゴン）、高度、開始終了時刻、機体重量、機体登録番号、パイロット資格

判定パイプライン：
1. **航空法レイヤー**：DID 判定、空港等周辺、150m 超、人口集中地区、夜間・目視外・人物等 30m 接近・催事上空・危険物輸送・物件投下
2. **小型無人機等飛行禁止法レイヤー**：重要施設＋ 300m バッファ
3. **電波法レイヤー**：使用周波数の免許要否（業務用 5GHz 帯等）
4. **道路交通法レイヤー**：道路上空からの離発着・物件投下
5. **民法・所有権レイヤー**：地権者同意の要否
6. **条例レイヤー**：自治体条例 DB との照合
7. **緊急用務空域レイヤー**：国交省 NOTAM API（提供範囲内）
8. **統合判定**：レイヤー横断で AND/OR 演算、最も厳しいものを採用、信号機色を決定

各レイヤーは独立に拡張可能なプラグインとして実装。

### 5.3 データモデル要点

```sql
-- 概念図（実際のスキーマは実装時に正規化）
ordinances
  id, municipality_code, title, source_url, version, effective_date
ordinance_clauses
  id, ordinance_id, clause_no, action_type, area_geom (PostGIS), 
  time_constraint, permission_type, raw_text, confidence_score
flight_plans
  id, user_id, geom, altitude_m, start_at, end_at, drone_id
judgments
  id, flight_plan_id, layer, verdict (green/yellow/red), 
  reasoning_jsonb, evidence_refs, computed_at
```

### 6.2 第 1 出願：請求項ドラフト（草案・代理人レビュー前）

**請求項 1（独立項）**：
> 自治体が公開する例規集データから無人航空機の飛行に関する規制条文を抽出し、当該条文を構造化データに変換するシステムであって、
> （a）公開された例規集データを巡回取得する取得手段と、
> （b）取得した条文に対し、規制対象となる行為種別、適用区域、期間条件、許可要件を所定のスキーマに従って抽出する大規模言語モデルを用いた抽出手段と、
> （c）抽出された適用区域について、地名・住所・地番から地理座標および地理空間ポリゴンへ変換する地理空間化手段と、
> （d）構造化データを版管理付きで保持する記憶手段と、
> （e）構造化データの矛盾を検出し人手レビューに回付する検証手段と、
> を備えるシステム。

**請求項 2〜10（従属項案）**：
- スキーマに「適用機体重量範囲」を含めるもの
- 改正検知を条文ハッシュ差分で行うもの
- 地名のみの記述に対しジオコーディング＋国土地理院数値地図を併用するもの
- 抽出時に LLM 出力を JSON Schema で強制し、不適合時に再生成プロンプトを連鎖させるもの
- 構造化データに信頼度スコアを付与し、所定閾値未満を人手レビューに回すもの
- 出典（条文番号・施行日）をメタデータとして保持し、判定根拠の表示に用いるもの
- 区域ポリゴンを PostGIS 形式で保持し、空間インデックスで近傍検索するもの
- 複数の自治体例規を統合データベースとして提供するもの
- ユーザーの飛行計画と空間照合し、適用される条文を返すもの
- 上記方法をコンピュータに実行させるためのプログラム

### 6.3 第 2 出願：請求項ドラフト（多層判定エンジン）

**請求項 1（独立項）**：
> 無人航空機の飛行可否を判定するシステムであって、
> （a）飛行計画（地理座標、高度、時間帯、機体属性、操縦者資格）を入力する入力手段と、
> （b）航空法、小型無人機等飛行禁止法、電波法、道路交通法、民法所有権、自治体条例、緊急用務空域指示、の各法令層について、独立した判定モジュールを保持し、それぞれが個別に飛行計画と照合して可・条件付可・不可のいずれかを返す多層判定手段と、
> （c）各層の判定結果を統合し、最も厳しい結果を採用しつつ、各層の判定理由を保持する統合判定手段と、
> （d）統合結果を 3 段階の視覚指標（緑・黄・赤）として出力するとともに、層別の判定理由をユーザー操作に応じて展開可能に提示する提示手段と、
> を備えるシステム。

### 7.1 国内競合・類似サービス

| 名称 | 提供主体 | 特徴 | そらばんとの差分 |
|---|---|---|---|
| DIPS 2.0 | 国土交通省 | 公式の許可申請ポータル | 申請ツールであり、事前判定 UX なし。条例層なし |

### 7.2 海外競合

| 名称 | 拠点 | 特徴 | そらばんとの差分 |
|---|---|---|---|
| Aloft (旧 Kittyhawk) | 米 | エンタープライズ向け。LAANC・フリート管理 | 米国向け、日本法令非対応 |
| AirMap | 米 | LAANC・空域 API。**2023/06 にアプリ・LAANC 終了** | 撤退済 |
| DJI FlySafe / GEO Zone | 中／米 | DJI 機体の Geofence 解除 | 機体メーカー Geofence のみ。法令判定なし |
| Skyward (Verizon) | 米 | エンタープライズ運航管理 | 米国中心 |
| Airspace Link | 米 | UTM・自治体連携 | 米地方自治体向け、条例構造化は限定的 |
| DroneDeploy | 米 | 撮影マッピング SaaS | コンプライアンスは限定的 |

### 7.3 隣接技術領域

- **法令文書 LLM 構造化**：海外で先行研究多数（米 Casetext, Harvey 等）。ただし「ドローン × 自治体条例 × 地理空間紐付け」という組合せは未確認
- **GIS × 規制レイヤー**：欧 U-space、米 LAANC は国レベル運用。自治体条例まで構造化する試みは確認できず
- **行政文書スクレイピング**：自治体の例規集は公開済だが API 提供は限定的。自動収集の正当性は利用規約と著作権法上の問題を整理済（後述リスク章）

### 7.4 差分マトリクスの結論

そらばんの**核心的新規性**は以下の 3 点の組み合わせ：

1. **日本の自治体条例を構造化対象にする**こと（地理的・言語的参入障壁により海外勢が来ない）
2. **多層法令を同時判定**する（既存サービスは単一または二層のみ）
3. **構造化からエンドユーザー UI までを一気通貫**で設計する

単独機能の新規性は限定的だが、**この三点の統合システムは出願に値する**。
