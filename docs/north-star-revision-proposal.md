## 0. 1 行で言えば

> **そらばんは、社内の運航管理アプリ（計画 → 点検 → 日誌）を、DIPS 2.0 と連携して機体・操縦者の情報を取り込むことで滑らかにし、その上に、法令・条例・判例を根拠として示す判定を載せて、全国へ展開するものである。**

今の 1 行（§0：「飛ばしてよいかを信号機一つで答えるコンプライアンス基盤」）との違いは三つある。

1. **主語が「判定」から「運用の流れ」に移る。** 毎日開かれるのは判定画面ではなく、計画・点検・日誌の画面だから。
2. **「根拠」が前に出る。** 「信号機で答える」のではなく、「何の法令・条例・判例に基づいて、その結論になったか」を示すことが、他との違いになる。
3. **順番が決まる。** 社内 → 山陰 → 全国。DIPS 連携は「社内で使い込むための手段」であり、目的ではない。

### 背骨をどうするか（比較と推奨）

「背骨」とは、迷ったときに戻る、製品の中心の流れのこと。3 つの考え方がある。

| 案 | 内容 | 良い点 | 弱い点 |
|---|---|---|---|
| A. 判定が背骨のまま（今の §3.1） | 地図タップ → 判定 → その先に書類・日誌 | 他にない部分（条例・根拠）が中心に据わる | 毎日は開かれない。社内の定着が測りにくい。のりさんの新しい指示（計画・点検・日誌がスムーズ）と中心がずれる |
| B. 運用の流れが背骨。判定は根拠つきの部品（**推奨**） | 計画 → 確認 → 通報の準備 → 点検 → 飛行 → 日誌、という「飛行」の一生が背骨。判定は、計画の入口、確認、通報の要否、日誌の根拠のそれぞれで呼ばれる部品 | 毎日開かれる側が中心になり、定着を測れる。判定の根拠が「記録に残る」という強みが、そのまま差別化になる | 「判定が他にない」ことが見えにくくなる恐れ。見せ方で補う（下） |
| C. 二本柱で並べる | 判定と運航管理を同格に置く | 方針の転換が小さい | 迷ったときの拠り所が二つになり、優先順位がつけにくい。実際、現行の北極星でも「判定が背骨」と「一つの道具」が並存して食い違いが出ている |

**推奨は B。** 理由は三つ。

1. 現行の北極星の §0.1.1（判定と運航管理を一つにする）と §0.1.10（統合した運航管理）は、すでに実質 B の考え方で、§3.1 だけが古い。B にすると、文書の中の食い違いが解消する。
2. 社内で使い続けられるかが最初の関門（§0.1.4）で、毎日開かれる流れを中心に据えるほうが、それを測りやすい。
3. B でも判定は軽くならない。**「どの画面でも、結論の根拠（法令・条例・判例、版、確認日）がたどれる」ことを、製品の約束にする。** それが、よそにないものになる。

B で補う点：「判定が他にない」ことは、画面の見せ方で示す。たとえば、計画の入口で根拠つきの結論を出す、日誌に当時の根拠が残る、など。

## 3. 「根拠」の設計

目的：画面に出す結論のすべてに、「どの法令・条例・判例に基づくか」を、**たどれる形で**示す。さらに、記録（計画・日誌）に、そのときの根拠を**そのまま残す**。

### 3.1 根拠の 3 種類と、扱いの違い

| 種類 | 例 | 判定との関係 | 位置づけ |
|---|---|---|---|
| 法令 | 航空法、小型無人機等飛行禁止法、同施行規則 | 結論を決める | 判定の土台。出典の条文を示す |
| 条例（と施設管理者の定め） | 都市公園条例、文化財保護条例、迷惑行為防止条例 | 結論を決める（収録済みの範囲で） | 収録範囲を明示。収録していない所は「収録なし」と示す |
| 判例 | 裁判所が公開している裁判例 | **結論を決めない。参考として示す** | 規制の解釈や運用の考え方を知る手がかり。判定の自動化には使わない |

判例を判定に使わない理由：判例は個別の事件に対する判断であり、「この条件ならこの結論」と機械的に当てはめられるものではない。誤った当てはめは、利用者に誤った安心を与える。参考として示し、判断は人が行う。

### 3.2 出典の持ち方（記録する項目）

すでにある出典の台帳（`packages/regulations/data/sources.json`）の考え方を、条文単位まで広げる案。

| 項目 | 内容 | 例 |
|---|---|---|
| 種類 | 法令／条例／判例／通達・告示／行政の案内 | 法令 |
| 名称 | 正式名称 | 航空法 |
| 条・項（判例は裁判所・事件番号・日付） | 条番号、項、号 | 第 132 条の 85 |
| 引用した文言 | 原文の該当部分（短く） | — |
| URL | 一次情報のページ。e-Gov、自治体の例規集、裁判所サイトなど | — |
| 版 | 施行日、改正日、告示番号、判決日。ない場合は「版の記載なし」と書く | 令和○年○月○日施行 |
| 取得日 | 当方が取得した日 | 2026-10-25 |
| 確認日・確認者 | 人が原文と照合した日と人 | — |
| 確認の状態 | **確認済み／要確認／未確認**（下の 3.5） | 確認済み |
| 取得元の利用条件 | ライセンス、出典の明記の要否 | — |
| 本文のハッシュ | 取得した本文の指紋。変わったことを検知する | — |

画面では「条文名＋条番号＋確認日」を常に見せ、タップで原文・URL・版を開く。計画・日誌のスナップショットには、**当時の版の情報を保存**する（あとで法令が改正されても、当時の根拠が読める）。

### 3.3 条例の全国収集：現実的な方法と限界

**確認済み・既知のこと**

- 自治体の条例は、各自治体の例規集（インターネットで公開されている条例・規則の集まり）で公開されている。ただし、構造化された API は限られている（現行 §7.3 の記述）。
- 国の法令は、e-Gov 法令検索で公開されている（法令 API の存在は当方の知識。**今回は e-Gov に接続できず、利用条件を未確認**）。

**現実的な方法（案）**

| 段階 | 方法 | 補足 |
|---|---|---|
| ① 国の法令 | e-Gov の法令データを取得し、版と施行日を持たせる | 一次情報。改正の検知がしやすい |
| ② 全国の飛行禁止エリア | DIPS の飛行禁止エリア情報取得 API（種別「条例等で定めるエリア」を含む）を取り込む | **条例等の登録範囲・更新頻度は、ガイドラインに書かれていない（未確認）**。航空局への確認事項（FPR 所見の不明点 6） |
| ③ 重点の条例 | 観光地・国立公園・世界遺産・文化財・都市公園・港湾・重要施設の周辺など、飛行が実際に多い場所に絞って、人が原文と照合して収録する | 山陰で現行方式（出典・確認日・確認者）を確立してから広げる |
| ④ 地域の協力 | 自治体や観光協会が自ら情報を出せる窓口を用意する（仮説。§4） | 網羅の近道になりうるが、相手の合意が要る |

**限界（正直に書く）**

- 全国には約 1,700 の市区町村（数字は当方の知識で、今回は一次確認していない）があり、すべての例規を人が照合するのは現実的でない。LLM（文章を理解する AI）による抽出は下書きに使えるが、**誤りうるので、人の照合なしで判定に使わない**（現行 §9 のリスク表と同じ考え方）。
- 条例に直接「ドローン」と書かれていなくても、公園条例の「行為の制限」などで規制されることがある。キーワード検索では取りこぼす。
- 区域が「地名」だけで書かれていて、地図上の範囲にできないものがある。
- 自治体のサイトの利用条件・機械的な取得の可否は、自治体ごとに違う。取得前に確認する（§6）。
- 条例ではなく、施設管理者の「お願い」や掲示で規制される場所も多い。これは法令・条例の形では取れない。
- **収録なしを「規制なし」と表示しない。** 画面には「この地域の条例は収録していません。自治体に確認してください」と出す。

### 3.4 判例の扱い

| 論点 | 方針（案） | 確認の状況 |
|---|---|---|
| どこから取るか | 裁判所の判例検索（courts.go.jp）で公開されている裁判例を、一次情報として使う。商用の判例データベースの転載はしない | 判例検索は「すべての判決等が掲載されているわけではない」と案内されている（検索で確認）。年間の公式判例集の収録数は限られる、という図書館資料の記述もある。**裁判所サイトの二次利用の条件は、今回は接続できず未確認** |
| 件数の現実 | ドローンに関する公開裁判例は、多くないと予想される（**仮説**）。まず調べて件数を数える | 確認方法：判例検索で「無人航空機」「小型無人機」などを検索し、件数と内容を記録する |
| 判定との関係 | **参考として示す。結論は決めない。** 「関連する裁判例」の欄に、事件名・裁判所・日付・要旨（当方が要約したものと明記）・原文へのリンクを出す | 方針 |
| 要旨の書き方 | 当方の要約は、**要約であることと、原文を確認するべきことを必ず併記**。争点と結論の取り違えを避けるため、人が原文と照合してから載せる | 方針 |
| 誤りの責任 | 掲載内容の正確さは当方が努める一方、**利用者の判断の責任は利用者にある**ことを、免責に明記する。誤りの連絡窓口と、訂正の記録（いつ何を直したか）を用意する。法的な責任の範囲は、専門家に確認する（§6） | 要・専門家確認 |
| 更新 | 新しい裁判例を月 1 回確認する（現行 §0.1.5 の「制度の月次確認」に含める）。上級審で覆った場合に備え、**審級と確定の状況**を持たせる | 方針 |
| 行政の解釈 | 判例のほか、国交省の通達・審査要領・Q&A も「根拠」として扱う（実務ではこちらが効く場面が多い）。種類を分けて表示 | 方針 |

「判例を根拠にする」ことの意味の整理：のりさんの指示は、条例・法令・判例を「根拠として挙げる」ことだった。**挙げる＝出典として示すことであり、判例に基づいて自動的に結論を出す、という意味ではない**と受け取って設計している。もし後者を意図しているなら、教えてほしい（§8 の質問 6）。

### 3.5 「確かな事実」と「要確認」の区別

3 段階で表示し、色と文字の両方で区別する。

| 状態 | 意味 | 付与の条件 | 画面での扱い |
|---|---|---|---|
| 確認済み | 一次情報の原文と人が照合した | 出典 URL、版、確認日、確認者がそろっている | 通常表示 |
| 要確認 | 一次情報は見たが、照合が不十分、または解釈に幅がある | 確認日が古い（90 日超）、条番号が未照合、など | 「要確認」の印を付け、結論は安全側（厳しい側）に倒す |
| 未確認 | 一次情報で確認できていない | 二次情報のみ、取得できていない | 根拠としては出さず、「確認中」と表示。判定では安全側に倒す |

ルール：

1. **一次情報（官公庁・裁判所・自治体の公式文書）で確認できていない事実は、断定しない。**
2. 見つからないことは、「存在しない」ではなく「見つからなかった（確認の日付と範囲を併記）」と書く。
3. 現行の「※要確認」運用（例：100g 未満の機体の条文、HANDOFF §6）を、この 3 段階に整理して引き継ぐ。
4. 状態は台帳のデータで管理し、画面の文言にベタ書きしない。

### 3.6 誤りを見つけたときの流れ

誤りの連絡 → 原文と照合 → 直す → 直した日・内容を履歴に残す → すでに作った計画・日誌には、元の版で作られたことを残したまま、**影響のある記録に印を付けて知らせる**。過去の記録を書き換えない（追記専用の方針と同じ）。

## 4. 観光庁・自治体・業界への訴求の可能性

**この節の内容は、すべて仮説。** 観光庁や自治体が、そらばんのようなものを求めているかは、確認できていない。今回の検索でも、観光庁そのものの飛行ルールに関する文書は見つからなかった（検索で確認）。一方、自治体が観光地や公園で独自に飛行を制限・許可制にしている事例は、公開資料に見つかった（広島市の原爆ドーム周辺、恵那市の観光施設のガイドライン、下田市の海水浴場・公園など。いずれも資料の年次が古いものを含み、現行の規定は未確認）。

### 4.1 訴求できそうなこと（仮説と確認方法）

| # | 仮説 | 想定する相手 | 確認の方法 |
|---|---|---|---|
| H1 | 観光地は、地域ごとにドローンの規制がばらばらで、事業者も旅行者も把握しにくい。**飛行ルールを根拠つきで見える化**する価値がある | 観光庁、自治体の観光部門、観光協会 | 数か所の観光地を選び、現行の規制を一次情報で調べ、実際にどれだけ散らばっているかを示す資料を作る（これ自体が実績になる）。自治体の観光部門に 30 分ヒアリング |
| H2 | 地域差を吸収し、事業者が「この場所で何の手続きが要るか」を事前に知れることが、観光地での事故やトラブルの予防になる | 自治体、観光協会、保険会社 | 事故・苦情の件数や内容を、自治体に尋ねる。公開されているトラブル事例を集める |
| H3 | 自治体が自ら条例・運用を更新・公開できる窓口があれば、収録の鮮度と網羅が上がる | 自治体 | 山陰の 1〜2 市町で試行し、更新にかかる手間を測る |
| H4 | 観光目的のドローン撮影（プロモーション動画の制作など）を行う事業者の需要がある | 観光事業者、制作会社 | 山陰の観光協会・制作会社に聞く。自社の点検業務とは顧客が異なるため、**北極星に入れる前に需要を確認する** |
| H5 | 国の側（観光庁、国交省）にとって、地域のルールの集約は、既存の取り組みとの重複でなく補完になる | 観光庁、国土交通省航空局 | 国交省・観光庁の公開施策を調べ、重複の有無を確認する。担当課に意見を聞く |

### 4.2 訴求の前に必ず確認すること

- **すでに同様の取り組みがないか。** DIPS 2.0 の飛行禁止エリア情報に「条例等で定めるエリア」の種別がある（確認済み）。国や民間が条例情報をどこまで集約しているかを調べる。調べずに「よそにない」と書かない（「日本初」「唯一」などの表現は、裏付けができるまで使わない）。
- 国や自治体に訴求するときは、**社名と個人名を使った営業・提案としての適否**（公的機関への働きかけの作法、利益相反の懸念など）を、会社として確認する。
- 実績として示すときは、数字（収録数、確認日、検証した件数）で語り、成果を盛らない。

### 4.3 訴求の道筋（案）

1. 山陰の観光地数か所で、一次情報に基づく「飛行ルール一覧」を作る（人が照合）。
2. それを持って、自治体・観光協会に見せ、ヒアリングで仮説 H1〜H3 を検証する。
3. 手応えがあれば、観光庁・航空局に意見を求める。
4. 公表する資料は、事実と仮説を分け、出典を付ける。

## 7. 既存の資産への影響

2026-10-25 時点で、すでに main に入っているもの（HANDOFF §3）を、北極星の変更の観点で仕分ける。**すべて案**であり、コードはこの作業では変更していない。

### 7.1 そのまま使う

| 資産 | 理由 |
|---|---|
| 判定エンジン（航空法、飛行禁止法、条例、緊急用務空域、4 段の判定） | 「根拠つきの部品」として、中身はそのまま使える |
| 出典・確認日の台帳（`sources.json` など）と証跡 ID | 根拠の設計（§3）の土台。広げる |
| 飛行計画、判定スナップショット（追記専用）、運航管理者の確認 | 背骨（運用の流れ）そのもの |
| 通報の準備・記録・期限、通報ゲートウェイ（手動・模擬） | DIPS 連携の差し込み口として設計済み |
| 日常点検、飛行記録、事故・ヒヤリハット、許可・承認の登録 | 背骨の一部 |
| 利用者・組織・役割・版の履歴 | 監査可能性（§5.3）に直結 |
| 現場モード、「今日」 | 毎日開かれる側。背骨の入口 |
| 行政書士法への配慮（本人入力・本人名義、「代行」不使用） | 引き続き外せない |
| デザイン v1・v2 草案の基本（判定色は橙と別系統、現場モードの扱い） | 変更不要 |

### 7.2 変えるもの

| 資産 | 変更の内容（案） |
|---|---|
| 文書：北極星 §0、§1、§3.1、§10 | 改訂案に合わせて直す（チェックリスト参照） |
| トップ画面の位置づけ | 今は判定画面 `/` が玄関。背骨を運用の流れにするなら、**玄関を「今日」（次にやること）にして、判定は計画の入口に置く**ことを検討（画面は 12g・12h のデザイン計画と整合させて決める。**この提案ではまだ決めない**） |
| 機体・操縦者の台帳 | 「DIPS から取り込んだ値」と「手入力の値」を区別する項目（由来、取得日時）を足す。取り込みの差異を示す画面 |
| 根拠の表示 | 条文単位の出典（条・項・版・URL・確認の状態）、判例の「参考」欄、「収録なし」の表示を追加 |
| 台帳の「確認の状態」 | 「※要確認」を 3 段階（確認済み・要確認・未確認）に整理 |
| DIPS 申請書の用途欄・サービス概要 | 機体・操縦者の読み取りを使う場合は API 欄（5-1 など）と利用目的の見直し（チェックリスト参照） |
| 公開ページの文言 | 「当面は社内」「山陰」の記載を段階に合わせて直す。noindex は当面維持 |

### 7.3 保留・新規

| 項目 | 扱い |
|---|---|
| 条例データの全国収集 | 新規の大きな作業。山陰で方式を固めてから。優先順位つき |
| 判例の収録 | 新規。まず件数と内容を調べる（§3.4）。小さく始める |
| 観光向けの機能（観光地の飛行ルールの見える化） | 仮説の検証が先（§4） |
| 100g 未満の機体、条文の一次照合の残り | 継続（HANDOFF §6） |
| 特許関連、料金プラン | 変更なし。保留 |
| 画面デザインの刷新（12g・12h） | 方針は変えない。玄関の扱いだけ §7.2 のとおり調整が必要になりうる |

### 7.4 影響の大きさ（見立て）

- **コードの大きな作り直しは要らない**見込み。判定・運航管理・台帳は、すでに「流れの中で判定を使う」構造になっている。
- 主な追加は、根拠の台帳の拡張（条文単位・判例）、DIPS 取り込み（認可できた場合）、「収録なし」の表示、検証事例集（§5.1）。

## 8. 決めてほしいこと（のりさんへの質問）

質問は 8 つ。各質問に推奨案を付けた。

| # | 質問 | 推奨案 | 理由 |
|---|---|---|---|
| 1 | **背骨は「運用の流れ」で、判定は根拠つきの部品、でよいか。** | はい（案 B） | §1 のとおり。現行文書の食い違いも解消する |
| 2 | **DIPS から機体・操縦者を読み取れない場合、手入力で運用を続けてよいか。** また、固定 IP の手配（保留中）をいつ進めるか | 手入力で進める。固定 IP は、航空局の回答（機体・操縦者の読み取りの可否）を待ってから手配する | 取れない API のために先に費用をかけない。ただし、API を使う前提なら申請に 1 か月程度かかるので、回答が出たら速やかに進める |
| 3 | **「全国」の意味は、「全国の条例を網羅」ではなく、「国の法令と DIPS の全国データで全国をカバーし、条例は収録範囲を明示して広げる」でよいか。** | はい | 条例の全国網羅は現実的でない（§3.3）。「収録なし」を正直に出すほうが、実務にも安全 |
| 4 | **判例は「参考として示す」でよいか（判定の結論には使わない）。** | はい。まず公開裁判例の件数と内容を調べてから、載せるか決める | 件数が少ない可能性がある。解釈を誤ると誤った安心を与える |
| 5 | **観光庁・自治体への訴求は、まず山陰の観光地数か所で資料を作り、ヒアリングで仮説を確かめてから進めてよいか。** 観光向けの機能は、需要が確認できるまで北極星に入れない | はい | 確認できていない事実が多い（§4）。資料づくり自体が実績になる |
| 6 | **「判例を根拠にする」は、「出典として挙げる」ことで合っているか。判例に基づいて自動で結論を出すことまで求めているか。** | 出典として挙げることで合っている | 自動での当てはめは、誤りの責任が重く、技術的にも現実的でない |
| 7 | **「実績として追加できる品質」の基準（§5）の水準を、どこまで求めるか。特に、専門家（行政書士・弁護士）の確認と、外部のセキュリティ診断に、費用と時間をかけてよいか。** | 最低限、法務の確認 1 回と、判定の事例集（50 件以上）の整備。外部診断は段階 2（山陰）の前に 1 回 | 社内利用の段階では全部は要らない。ただし社外に出す前に法務の確認は必須 |
| 8 | **段階の時期（§2）と、年度末（2027-03 末）の見直し基準（現行 §0.1.4）に「DIPS 連携の可否」「根拠の台帳の整備率」を加えてよいか。** | 加える。段階 1 の時期は、航空局の回答後に決める | DIPS 連携は相手次第で、時期を今は決められない |
