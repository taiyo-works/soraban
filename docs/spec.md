## 0. 1行で言えば

> 既存の信号機判定の結果（DID・夜間・目視外等の理由）から、**必要な申請・登録・手続きを機械的に診断し、提出期限カレンダー・申請内容プリフィル・各種書類ドラフトを生成して、DIPS / DRS への手入力をコピペ／PDF で支援する**機能。

自動申請はしない。DIPS は公式 API がなくログイン制のため、**手入力を埋めるプリフィル表 ＋ PDF 出力**で支援する（規約リスク回避のため自動操作は一切しない）。

## 1. 背景と機能ゴール

### 1.1 背景

- そらばんの信号機判定は「飛ばしてよいか（可否）」を即答するが、`red`／`yellow` の場合に「**では実際に何をすれば飛ばせるのか**」（許可・承認・登録・期限・書類）はユーザーが DIPS と航空局の手引きを自力で読み解く必要がある。
- 商用ドローン事業者（North Star §1.1）の痛点 #3「DIPS 申請書類作成の手間」（入力項目の重複・案件単位の保管不可）を直接解く。
- 制度は 2 系統に分かれ、導線が混乱しやすい（後述 §3）。**機体登録（DRS）と飛行許可・承認（DIPS2.0）を別物として案内する**。

### 1.2 機能ゴール

既存の飛行可否判定の結果を引き継ぎ、以下を提供する：

1. **必要手続きチェックリスト** — 信号機判定の理由から、必要な申請・登録・手続きを機械的に導出（§4 マッピング表）。
2. **期限カレンダー** — 飛行予定日から逆算し、提出期限（飛行開始の **10 開庁日以上前**・土日祝除く）をアラート表示。
3. **カテゴリー切り分け** — その飛行が「申請で済む（カテゴリー II）」のか「機体認証・上位ライセンスが要る領域（III／レベル4）」なのかを最初に提示。
4. **申請内容プリフィル表** — DIPS の入力項目に対応した値を表で提示し、コピペで DIPS のフォームを埋められるようにする。
5. **書類ドラフト** — 独自飛行マニュアル等のドラフトを生成。
6. **束ね PDF** — 上記を 1 つの PDF として出力（既存 `regulation-pdf.tsx` の作法に合わせる）。

### 1.3 「役立った」の操作的定義

以下を満たすときに本機能は価値を出したと判定する：

1. 信号機判定で `red`／`yellow` が出たら、**追加入力なしで必要手続きチェックリストが即座に表示される**。
2. 提出期限が**飛行予定日から逆算した具体的な日付**で出る。
3. プリフィル表の各項目が**コピペでき、DIPS のどの入力欄に対応するか**が明記されている。
4. 全画面・全 PDF に**免責**と**各手続きの出典条文・URL**が併記されている。

## 2. スコープ / 非スコープ（ユーザー確定済み・不可侵）

### 2.1 スコープ ＝ 診断 ＋ 書類ドラフト

- 必要手続き・期限の診断（チェックリスト ＋ 期限カレンダー）
- 申請内容／独自飛行マニュアル等のドラフト生成
- DIPS 入力プリフィル補助（コピペ用表 ＋ PDF）
- 起点は**信号機判定から自動導出**：地図判定の理由（DID・夜間・目視外等）から必要手続きを機械的に導出。独立ウィザードではなく、既存フローと地続き。

### 2.2 非スコープ（やらない）

- **DIPS／DRS への自動申請・自動入力・自動ログイン・スクレイピング操作**は一切しない（公式 API なし・ログイン制・規約リスク回避）。
- 申請の代行・提出の代行はしない（あくまで事業者が自分で DIPS／DRS に入力する前提の補助）。
- 法令の確定的な保証・法律相談はしない（免責の全面表示）。
- 技能証明・機体認証そのものの取得手続き（試験予約等）の実装は本機能の範囲外（必要性の**提示**のみ行う）。

## 3. 裏取り済みの現行制度事実（2026年6月時点・一次情報）

> ここに列挙する事実は構造化データ（§6 のデータモデル）として保持し、各レコードに出典 URL を持たせる。**コードに直書きせず、改正時に差し替え可能にする。**

### 3.1 システム構成（2系統を別物として扱う）

- **機体登録は別ドメインの独立系統 DIPS-REG / DRS**（`https://www.dips-reg.mlit.go.jp/drs/`）。100g 以上が対象、原則リモートID搭載義務、有効 3 年、手数料 900 円〜。
- **飛行許可・承認／飛行計画通報／飛行日誌／事故報告は DIPS 2.0 本体**（`https://www.ossportal.dips.mlit.go.jp/`、申請者向け手引き `https://www.uafp.dips.mlit.go.jp/`）。技能証明・機体認証も DIPS2.0 内。

### 3.2 特定飛行（航空法）

下記いずれか該当で「特定飛行」フラグ。該当すると**飛行計画通報・飛行日誌も義務**。

- **許可が必要な空域 4 種（航空法 132条の85）**：①空港等周辺 ②150m以上 ③DID上空 ④緊急用務空域（原則禁止）
- **承認が必要な方法 6 種（航空法 132条の86）**：①夜間 ②目視外 ③人・物件 30m未満 ④催し場所上空 ⑤危険物輸送 ⑥物件投下
- 出典：`https://www.mlit.go.jp/koku/koku_fr10_000041.html` ／ `https://www.mlit.go.jp/koku/koku_fr10_000042.html`

### 3.3 カテゴリー制度

- **I**＝特定飛行に非該当（手続き不要）
- **II**＝立入管理措置あり（第三者上空でない）
- **III**＝立入管理措置なし＝第三者上空（レベル4を含む）
- II は **IIA**（許可・承認の申請が必要）と **IIB**（技能証明 ＋ 機体認証 ＋ 飛行マニュアル等で申請を"不要化"できる：DID／夜間／目視外／30m かつ 25kg未満）に分かれる。
  - ※ **IIA／IIB の呼称が国交省の正式名称か運用通称かは要再確認。制度実体（申請が要るカテゴリーと不要化できるカテゴリーが分かれること）は確実。**
- **III＝レベル4** は **一等無人航空機操縦士 ＋ 第一種機体認証** が必須。出典：`https://www.mlit.go.jp/koku/level4/`

### 3.4 申請の種類・期限

- **個別申請** vs **包括申請**（期間包括／飛行経路包括）。
- 提出は飛行開始の **10 開庁日以上前**。
- 有効期間は**最大 1 年**（経路非特定は原則 3 か月）。
- 出典：`https://www.mlit.go.jp/koku/koku_fr10_000042.html`

### 3.5 必要書類・情報

- 機体の機能性能基準適合（**DIPS 登録機体一覧にあれば省略可**）
- 操縦者の飛行経歴（**目安 10 時間以上・一律必須ではない**）
- 飛行マニュアル（航空局 **標準マニュアル01・02** か独自マニュアル）
- 賠償責任保険は**原則任意**。ただし**総重量 25kg 以上**の無人航空機は、**令和7年（2025年）10月1日以降の新規**飛行許可・承認申請で**第三者賠償責任保険の加入が必須**（国交省 https://www.mlit.go.jp/koku/koku_fr10_000042.html 、2026-10-14 確認）

### 3.6 既知の訂正候補・要再確認事項（確定事実として書かない）

これらは本機能の出力に**確定事実として表示しない**。表示する場合は「※要再確認」を付すか、当面非表示とする。

| # | 事項 | 状態 | 扱い |
|---|---|---|---|
| A | ~~「総重量 25kg 以上は 2026/10/1 以降の申請分から第三者賠償責任保険が必須」~~ → **訂正：2025/10/1（令和7年10月1日）以降の新規申請分から必須** | **確証取得済み（2026-10-14, 国交省 koku_fr10_000042）** | Sprint 6 で確定事実として手続き化（`insurance-third-party-25kg`）。日付は 2026 ではなく 2025。 |

## 4. コアロジック（判定理由 → 手続きのマッピング）

既存エンジンが出す `RegulationWithStatus` の理由（および新たに収集する「飛行方法」フラグ）から、必要手続きを機械的に導出する。**このマッピング自体を出典付き構造化データとして保持する。**

| 判定理由 | 特定飛行 | 導かれる手続き |
|---|---|---|
| 空港等周辺 | 空域① | 飛行許可（IIA・不要化不可） |
| 150m以上 | 空域② | 飛行許可（IIA） |
| DID上空 | 空域③ | 飛行許可（IIB条件で不要化可） |
| 緊急用務空域 | 空域④ | 原則飛行禁止 |
| 夜間／目視外／30m未満 | 方法①②③ | 飛行承認（IIB条件で不要化可・目視外は補助者有無で別扱い） |
| 催し上空／危険物／物件投下 | 方法④⑤⑥ | 飛行承認（IIA・不要化不可） |
| （常時）機体100g以上 | — | 機体登録（DRS）＋リモートID |
| 条例（公園等） | — | 各管理者への申請／協議（既存条例レイヤーから引き継ぎ） |

**横断的に常に出すもの**（特定飛行に該当する場合）：

- **飛行計画通報**（DIPS2.0）
- **飛行日誌**（DIPS2.0）
- **保険**（原則任意だが推奨。総重量 25kg 以上は 2025/10/1 以降の新規申請で第三者賠償責任保険が必須＝§3.6-A、確証取得済み）

### 4.1 導出の入力源

| 入力 | 取得元 | 備考 |
|---|---|---|
| 空域フラグ（空港・150m・DID・緊急用務） | 既存 `RegulationCheckResult.regulations`（`aviation-law-did` / `aviation-law-airport` / 緊急用務） | 150m は高度入力が必要（既存に高度入力なし → 新規フラグ入力を追加） |
| 方法フラグ（夜間・目視外・30m・催し・危険物・投下） | **新規入力**（飛行方法チェックボックス群。既存 `FlightContext` を拡張） | 既存エンジンは方法フラグを持たないため新設 |
| 機体重量 100g 以上 | 既存 `FlightContext.droneWeightG` | 100g 未満は航空法上の無人航空機に非該当（既存の例外節と整合） |
| 条例（公園等） | 既存 `RegulationCheckResult.regulations`（市町村レイヤー） | 既存の `note` と `url` を引き継ぐ |
| 飛行予定日 | **新規入力**（期限逆算に使用） | 任意。未入力時は期限カレンダーをスキップし「飛行日を入力してください」と促す |
| 立入管理措置の有無／第三者上空か | **新規入力**（カテゴリー切り分けに使用） | II か III かの分岐に使う |

## 5. ユーザーストーリー

1. **米子市役所で夜間＋目視外の点検をしたい事業者**：地図で米子市役所をタップ → 信号機 `red`。飛行方法で「夜間」「目視外」をチェック → 必要手続きに「飛行許可（DID）」「飛行承認（夜間）」「飛行承認（目視外）」「機体登録（DRS）」「飛行計画通報」「飛行日誌」が並ぶ。飛行予定日を入れると提出期限が「飛行日 − 10 開庁日」で表示される。
2. **100g 未満のマイクロ機しか飛ばさない人**：機体重量 80g を入力 → 「航空法上の無人航空機に非該当」となり、飛行許可・承認・機体登録の手続きが消える（条例の協議は残る）。
3. **第三者上空（レベル4）を検討している事業者**：「立入管理措置なし（第三者上空）」を選択 → 最初に「これはカテゴリー III＝レベル4 の領域。一等無人航空機操縦士 ＋ 第一種機体認証が必須」と切り分けが提示され、単純な申請では済まないことが分かる。
4. **申請書類を作りたい事業者**：診断後、プリフィル表をコピペで DIPS に貼り、独自飛行マニュアルのドラフトと束ね PDF をダウンロードして社内稟議・依頼主提出に使う。

## 6. データモデル（現行構成に整合：静的 JSON / TS モジュール）

> **重要**：制度データ（特定飛行の定義・カテゴリー・必要書類・手続き定義）は**コードに直書きせず、出典付きの構造化データとして保持**し、改正時に差し替え可能にする。配置は現行構成に合わせて `packages/regulations/`（型・ロジック）と `packages/regulations/data/`（JSON）。Supabase / PostGIS は使わない。

### 6.1 新規の型（`@soraban/regulations` に追加）

```
// 特定飛行の区分（航空法 132条の85=空域 / 132条の86=方法）
SpecificFlightFlag =
  | "airspace_airport"      // 空域① 空港等周辺
  | "airspace_150m"         // 空域② 150m以上
  | "airspace_did"          // 空域③ DID上空
  | "airspace_emergency"    // 空域④ 緊急用務空域
  | "method_night"          // 方法① 夜間
  | "method_bvlos"          // 方法② 目視外
  | "method_30m"            // 方法③ 人・物件30m未満
  | "method_event"          // 方法④ 催し場所上空
  | "method_dangerous"      // 方法⑤ 危険物輸送
  | "method_drop"           // 方法⑥ 物件投下

// 手続き（申請・登録・通報・書類）。各レコードは出典 URL とシステム系統を必ず持つ。
RequiredProcedure = {
  id: string
  kind: "flight_permission" | "flight_approval" | "drone_registration"
      | "flight_plan_report" | "flight_logbook" | "insurance"
      | "ordinance_coordination"
  title: string                 // 例: "飛行許可（DID上空）"
  system: "DIPS2.0" | "DRS" | "条例（各管理者）"
  systemUrl: string             // DRS と DIPS2.0 を別 URL で持つ
  legalBasis: string            // 例: "航空法 第132条の85 第1項第3号"
  sourceUrl: string             // 出典 URL（条文・手引き）
  waivableByIIB: boolean        // IIB 条件で不要化できるか
  leadTimeBusinessDays: number  // 提出期限の逆算日数（通常 10）
  note?: string
  needsReverify?: boolean       // §3.6 の要再確認事項に紐づくなら true
}

// 飛行方法・運航条件（既存 FlightContext を拡張）
FlightMethodContext = {
  flags: SpecificFlightFlag[]   // ユーザーが選んだ飛行方法 + 判定由来の空域フラグ
  plannedDate?: string          // ISO 日付。期限逆算に使う
  thirdPartyOverflight?: boolean// 第三者上空（III 判定用）
  accessControl?: boolean       // 立入管理措置の有無（II/III 切り分け）
  bvlosWithObserver?: boolean   // 目視外: 補助者の有無（別扱い）
}

// 診断結果（API レスポンス。既存 RegulationCheckResult と並走 or 内包）
ApplicationDiagnosis = {
  category: "I" | "II_A" | "II_B_eligible" | "III_level4"  // 呼称は §3.6 要再確認
  categoryNote: string          // 切り分けの根拠説明
  procedures: RequiredProcedure[]
  deadlines: { procedureId: string; submitBy?: string; basis: string }[]
  prefill: PrefillField[]       // DIPS 入力項目対応
  disclaimer: string            // 既存 DEFAULT_DISCLAIMER を流用・拡張
}

PrefillField = {
  dipsFieldLabel: string        // DIPS のどの入力欄か
  value: string                 // コピペ用の値
  source: string                // どこから来た値か（判定 / 入力 / 既定）
}
```

### 6.2 制度データファイル（出典付き JSON / TS）

- `packages/regulations/data/procedures/*.json` … 手続き定義（`RequiredProcedure` の素データ。出典 URL・法的根拠を必ず含む）。
- `packages/regulations/data/categories/*.json` … カテゴリー定義と切り分けルール（IIA/IIB/III、レベル4 要件、出典 URL）。
- マッピング表（§4）は TS モジュールまたは JSON で保持し、`SpecificFlightFlag → RequiredProcedure[]` の対応を表現する。

### 6.3 既存資産との接続点（コードに直書きしない方針を維持）

- 判定 API：`apps/web/src/app/api/check/route.ts`（新規に `apps/web/src/app/api/diagnose/route.ts` を追加するか、既存 `/api/check` のレスポンスを拡張する。**どちらにするかは未決事項 §10-1**）。
- 信号機判定ロジック：`apps/web/src/lib/check.ts`／`apps/web/src/server/regulation-check.ts`。
- UI：`apps/web/src/components/regulation-checker.tsx`（既存の `FlightContext` 入力 UI に飛行方法・飛行予定日の入力を追加）。
- PDF：`apps/web/src/components/regulation-pdf.tsx` の作法（`@react-pdf/renderer`・Noto Sans JP・デザイントークン整合）に合わせて束ね PDF を生成。
- 証跡：既存の `evidenceId` / `engineVersion` の仕組みに、診断結果も含める（監査・損保引受で「いつのロジックの診断か」を同定可能に）。

## 7. UI 構成

既存の `RegulationChecker` のフローに地続きで追加する（独立ウィザードにしない）。

1. **入力（既存フォームを拡張）**
   - 既存：住所／座標／緯度経度／機体重量／許可保有／目的。
   - 追加：**飛行方法チェックボックス群**（夜間・目視外・30m未満・催し上空・危険物・物件投下・150m以上）、**飛行予定日**、**立入管理措置の有無／第三者上空か**。
2. **カテゴリー切り分けバナー**（結果セクション先頭）
   - 「申請で済む（II）」か「機体認証・上位ライセンスが要る（III／レベル4）」かを最初に提示。III の場合は強い警告。
3. **必要手続きチェックリスト**
   - `RequiredProcedure` をカードで列挙。各カードに：手続き名・**システム系統（DRS／DIPS2.0／条例）と URL を別導線で**・法的根拠・出典 URL・IIB で不要化できるか・チェックボックス（完了管理）。
4. **期限カレンダー**
   - 飛行予定日が入っていれば、各手続きの提出期限（飛行日 − 10 開庁日、土日祝除く）を日付で表示し、近接時はアラート色。
5. **申請内容プリフィル表**
   - DIPS の入力欄ラベルと値の対応表。各行に**コピペボタン**。
6. **書類ドラフト**
   - 独自飛行マニュアル等のドラフト（テキスト）を生成・表示・編集可能に。
7. **束ね PDF 出力**
   - 上記 2〜6 を 1 PDF に。既存 PDF ボタンの隣に配置。

### 7.1 設計制約（North Star §4 と本機能固有）

- **免責の全面表示**必須：「本機能は補助であり、最終確認は DIPS／航空局で行う」を全画面・全 PDF に表示。
- **各手続きに出典条文・URL を併記**。
- **DRS（登録）と DIPS2.0（許可承認）を別導線**として明確に分けて案内（同じ「DIPS」と混同させない）。

- **まず切り分け**：II か III／レベル4 かを最初に提示。
- North Star §4.1 デザイン4原則（モノクロ＋単一アクセント／タイポグラフィ・ファースト／余白は機能／動きは最小限）を踏襲。

## 8. 法令正確性・免責方針（安全クリティカル）

- **推測で法令を書かない。** 確証のない事実は「※要再確認」を付すか非表示にする（§3.6）。
- すべての手続き・カテゴリー・期限は**出典 URL と法的根拠**を構造化データに持ち、UI／PDF に併記する。
- 制度データは**人手で改正レビューできるよう構造化**し、`verifiedAt` 相当のメタを持たせる（既存 `confidence.verifiedAt` の作法に倣う）。
- 免責文言は既存 `DEFAULT_DISCLAIMER` を基礎に、本機能向けに「最終確認は DIPS／航空局で」を追記する。
- 自動申請・自動操作は実装しない（規約・法的リスク回避）。
