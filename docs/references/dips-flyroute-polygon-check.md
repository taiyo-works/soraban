## 1. 主張ごとの確認結果

### 1. 多角形の環の閉じ方（項番 23、サンプル p56〜58・p60）

| 論点 | 結果 | 出典・読み |
|---|---|---|
| 項番 23 に「Polygon 指定時は設定必須。3点以上」と「終点は始点と同じ座標をサーバー側で生成」の趣旨がある | 確認できた（精読記録。原本は未再照合） | ガイドライン 1.10 版 p46〜52 の項目表 項番 23。findings §5.2 の行 23 |
| Polygon のリクエストサンプルの座標は 3 点で、閉じていない（始点が最後に繰り返されていない） | 確認できた（精読記録） | p56〜58。findings §5.2「リクエストサンプル」: `coordinates` は 3 点、`properties` は `{}` |
| 以上から「送るときは環を閉じない（open）」が文書と整合する | **確認できた（文書の読みとして整合）。ただし「閉じて送ってもよいか／閉じて送ると拒否されるか」は記載なし** | 項番 23 は「サーバー側で生成」と述べるだけで、クライアントが閉じた環を送った場合の扱い（そのまま受理・重複点として扱う・エラー）の記載は精読記録に無い |
| 項番 23 の「3点以上」が、閉じる前の点数か、閉じた後の点数か | **確認できない** | サンプルが 3 点（閉じていない）であることから、閉じる前の点数と読むのが自然だが、原文の文言そのものは精読記録に無い。※要再確認 |
| レスポンス側（p60〜63、`duplicateFlightPlan[].flyRoute`）の Polygon の座標が閉じた形で返るか | **確認できない** | findings §6 は `coordinates` の項目があることしか記録していない。サーバーが終点を生成するなら返却は閉じた形かもしれないが、記録に無く推測になる。※要再確認 |

注: GeoJSON の一般仕様（RFC 7946）は線形リングを閉じた形（先頭と末尾が同じ）と定めるが、DIPS はサーバー側で閉じると述べているので、DIPS が GeoJSON の厳密な検証をするかは別問題。RFC の内容は今回取得しておらず、記憶に基づく一般論であり、DIPS の仕様の根拠にしない。

**結論（読みの範囲）**: 文書（項番 23 とサンプル）は「開いたまま送る」ことを示す。sprint-19 §3.3 と §2 の「既定は `open`」は、文書と矛盾しない。「閉じて送った場合の受け入れ」は文書から決められないので、`closed` の設定は検証環境で確かめるまで使わない扱いが妥当。

### 2. 円の radius の置き場所

| 論点 | 結果 | 出典・読み |
|---|---|---|
| リクエストのサンプル（Circle、p52〜55）では `radius` が `properties` の中にある | 確認できた（精読記録） | findings §5.2「リクエストサンプル」と「本文上の気づき」5。サンプル形: `properties: {radius: 10.0}`、`geometry: {type: Circle, center: [経度,緯度]}` |
| レスポンス（p60〜63、重複計画の `flyRoute`）では `radius` が `geometry` 側に載る | 確認できた（精読記録）。ただし**記述が揺れている** | findings「気づき」5 は「レスポンス側の radius の説明は別途 geometry 内（p60 項目16）」と記録。§6 は duplicateFlightPlan の flyRoute に type・center・radius・coordinates を並べている |
| リクエストの項目表（項番 21 `radius`）が geometry 配下の項目として定義されているか | **確認できない** | findings の項目表（§5.2）は階層（インデント）を記録しておらず、項番 21 が `properties` 配下か `geometry` 配下かは読み取れない。`report-fields.json` の `routeFormat.note` と sprint-12b・sprint-19 は「項目表は geometry」と書いているが、その根拠は findings には**書かれていない**（食い違い候補 D-1、§3） |
| ガイドライン 1.10 版でサンプルが直された | 確認できた（改訂履歴）。**影響は未確認** | p3 の履歴: 1.10 は「2.3.8: サンプル修正（flightPlanId, flightPlanRegistrationResult, existOtherFlightRoutesCount, radius）」。どのサンプル（リクエスト／レスポンス）の radius をどう直したかは記録に無い。p53 の `properties.radius` が修正後か修正前かは判断できない。※要再確認 |

**結論**: リクエストのサンプルは `properties.radius`、レスポンスは geometry 側、という読みは精読記録で一致している。リクエストで本当にどちらを受け付けるか（または両方）は文書だけでは確定しない。現行の既定（`circleRadiusPlacement: "properties"`、他に `geometry`・`both`）は、サンプルに合わせた選択として整合する。

## 2. 19-1c の設定の既定への含意

| 設定 | 既定（sprint-19 §3.3） | 文書との整合 | 含意 |
|---|---|---|---|
| `routeFormat.polygonRing` | `open` | 整合（項番 23 とサンプル p56〜58）。ただし原本は今回未再照合 | 既定は `open` でよい。`closed` は、検証環境で受理されることを確かめるまで、本番の通報用の既定にしない。設定の注記には「※要再確認（検証環境）」と、出典「ガイドライン 1.10 版 項番 23、p56〜58」を書く。**「閉じて送ると受理される」「サーバーが重複点を取り除く」とは書かない**（記載なし） |

| `circleRadiusPlacement` | `properties`（既存） | リクエストのサンプルと整合。項目表の階層は未確認 | 円の出力を 1 文字も変えない（C1-3）方針と矛盾しない。多角形の `properties` は `{}`（サンプル p56〜58 と整合） |

## 6. 専門家に回す論点

法的な結論ではなく、確認してもらう論点のみ。

- 利用者の飛行範囲の座標を、利用者本人の DIPS 認証のもとで通報用に整形して送ることが、行政書士法上の「申請の代行・支援」に当たらない範囲か（通報であり許可・承認の申請ではないという境界の整理。既存の質問票に追加するかは別途）。
- 範囲を複数持つ計画を、DIPS には 1 つだけ出す形（`first_only`）にしたとき、通報内容が実際の飛行範囲より狭くなる点の説明と、利用者に出す文言の妥当性（「通報済み」と読ませないこと、複数を出せるか未確認であることの表示）。
- DIPS API の利用規約の範囲で、飛行範囲の整形・保存・表示をどこまで行ってよいか（利用規約の本文は本リポジトリに無い。URL: https://www.ossportal.dips.mlit.go.jp/contents/portal/termsDetails.html、ガイドライン p5。今回は取得できていない）。
