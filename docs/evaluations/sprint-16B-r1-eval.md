## 4. 本文と補足の振り分け（観点 2）

静的に `data-note` の 135 箇所を読み、画面（390）の `data-note` の p・li・dd のうち 45 字以上のものを抜き出して（`-long-notes.log`）、契約の表・定義と突き合わせた。表にあるものは表どおり。表にない長い補足（`plan-report-penalty`・`outageNote`・`smallDroneLawNote`・`report-map-info`・`plan-dips-notice`・`plan-permit-format-note`）は、いずれも「※要確認」付きの断り書き・定型の注記で、定義の「注記」に当たると判断した。補足にしたことで隠す・畳む・薄くすることはない（文字色は `ink-2`、4.5 以上）。画面で目視（`r1-eval-pub-top-390.png`・`r1-eval-pub-footer-390.png`・`r1-eval-ops-judge-390.png`・`r1-eval-ops-home-390.png`）しても、導入文・結論の導き文・説明が 16px、免責・出典・日付が 14px で、前回の「導入文が小さく階層が逆転する」は解消している。

観点の 3 点:
1. **`site-facts` の `dd`（太字 700 のまま 14px）**: 自然。ユーザーの決定どおり、短い値（提供元・利用の範囲・対象地域）が丸いタグの中に入り、項目名（dt）と同じ 14px で 1 つの札として読める（`r1-eval-pub-top-390.png`）。太字が補足より強いのは、値を主情報として読ませる意図で矛盾しない。ただし `.sb-facts dd:not([data-note])` という CSS の分け方は、`dd` の印のない本文用の規則が今は使われていない（`dd` が `site-facts` 以外に無い限り死んだ規則）。無害。
2. **行程 `route` の `ol`**: 許容。段の名前と「済・次・未」という短いラベルの並びで、定義の「ラベル・件数・タグ」に当たる。7 列の幅（375px）に 16px では入らず、設計上も 14px のラベルが妥当。ただし「次の飛行」カードの主役の要素なので、読みやすさは 14px でぎりぎり。迷う例として挙げる（不合格ではない）。
3. **公開フッターの提供元 `dl`（`ProviderInfo compact`）**: **迷う例**。契約の表は「フッターの免責・境界の文」「出典・著作権」を補足とするが、提供元の 6 項目（所在地・電話・メール・受付時間）は列挙にない。値は日付・件数・出典・ID だけでもない。契約は「迷うものは本文」とするので、厳密には本文（16px）側に倒すべき。ただし提供元の表示は Sprint 18-3 の時点から 14px・詰めた行間で、画面の長さの上限を理由にその時に決めたもの（`provider-info.tsx` のコメント）。電話・メールが 14px でも読める（`r1-eval-pub-footer-390.png`）。**ユーザー判断**（§7-1）。

## 6. L-4 判定 375 の 4,600→5,300（観点 4）

**原因を特定した。判定画面の長さは、登録済みの許可・承認（候補）の件数で決まる。**

- 判定画面の「範囲に収まる登録済みの許可・承認（候補）」（`plan-permit-candidate`）は、DB にある許可の登録のうち範囲に収まるものを全部並べる。1 件 約 96px（375 幅・本文 16px で 2 行＋余白）。
- 計測（同じ計画の判定画面、375 幅）: **新しい DB（許可の登録 6 件）→ 候補 1 件・4,300px**。**全体実行のあとの DB（登録 19 件）→ 候補 10 件・5,161px**。差 9 件 × 約 96px ＝ 約 861px で、全体実行の 5,068 とも整合する。単独の `sprint17-2-db`（新しい DB）は 4,300（×3 回とも）、全体実行は 5,068（2 回とも同じ）、全体実行のあとの DB での単独は 5,161。generator の推定「他の spec のデータが残って判定の根拠が増える」は正しく、根拠とは許可の候補だった。
- 1280 幅の判定も同じ原因で、新しい DB 単独 2,715／全体実行 3,238／全体実行のあとの DB 3,303（上限 3,300 を **超えて失敗**する。使い回した DB での再実行の偽の失敗）。1280 の上限は変えていないが、全体実行の余裕は 1.9%（3,238／3,300）しかない。
- **評価**: 5,300 は「全体実行の実測 5,068 ＋ 4.6%」で、全体実行（CI と同じ）では、レイアウトが約 230px 伸びる退行は検出できる。単独実行では 4,300 に対し 23% の余裕があり、単独では約 1,000px の退行を見逃す。つまり**この上限は実装の長さではなく、前の spec が残した許可の件数に引きずられる値**で、全体実行でだけ意味がある。別の spec が許可を 3 件足せば（約 290px）、レイアウトが変わらなくても落ちる。今回は全体実行で通るため合否には影響しないが、**検査として脆い**（改善案: 判定の長さを測る前に候補の件数を数えて 1 件分に換算する、または候補を除いた高さを測る。16-H2 で上限を戻すときに直す）。ユーザー判断（§7-2）。
