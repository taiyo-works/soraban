# レビューチェックリスト（Codex 後の独立レビュー用）

目的：2026-10-27 以降、ChatGPT を Free に下げると Codex の自動レビューが止まる可能性がある。
それまでに Codex が見つけた不具合の「型」を、独立レビュー担当（別のサブエージェント）が機械的に潰せる形で残す。

- 使い方：PR を出す前（generator 完了後・evaluator の前）に、レビュー担当へ「差分＋このチェックリスト」を渡し、各項目に該当／非該当と根拠（ファイル・行）を返させる。
- 該当が見つかったら、同じ型の箇所を差分全体から探し直し、まとめて直す（1件ずつ直すと指摘が何周も続く）。
- 理論上のミリ秒単位の競合だけが残った場合は、直す前にユーザーへ「直す費用と防げる害」を示して判断を仰ぐ。
- 実際に不具合を見つけた型は、このファイルへ追記する。

## A. データの取り出し（ページング・件数）

1. **LIMIT を絞り込みの前に掛けていないか。** `LIMIT` の後でアプリ側が除外すると、該当データがあるのに空・欠けて見える。絞り込みは SQL 側で行うか、`collectMatching`（`server/ops/paging.ts`）のように条件を満たすまでページを進める。
2. **上限で黙って切り捨てていないか。** 上限に達したときは、画面に「他に N 件あります」と出す。切り捨てを利用者に隠さない。
3. **並び順が一意か。** ページングする並びには、同値を割る列（id など）を必ず足す。

## B. 冪等性と二重実行

4. **作成・更新 API が `client_request_intent` を持つか。** 再送・二重クリック・ネットワーク再試行で、記録が二重にできない。
5. **冪等キーの「意図」まで照合しているか。** 同じキーで内容の違う要求が来たら、黙って前回の結果を返さず衝突として扱う。
6. **追記専用（append-only）の記録を UPDATE／DELETE していないか。** 訂正は新しい版（`record_versions`）として追記する。不変トリガ（SB409）に頼らず、コードでも守る。

## C. 競合と整合（読んでから書く処理）

7. **同じ行を2回読んでいないか。** 検査と書き込みで別々に読むと、間に別処理が入る。1回の読み取りの結果を使い回すか、ロック下で読み直す。
8. **ロックを取った後に、権限と状態を再確認しているか。** `lockAndReauthorize` を通す。ロックの前の判定を信用しない。
9. **ロックの種類と順序は適切か。** 同じ対象を複数ロックするときは順序を固定する（デッドロック防止）。操縦者の在籍確認のような「読むだけの保護」は共有ロック（`lockPilotMemberOn`）。
10. **初回ログインや初期作成のような「無ければ作る」処理が、同時に走っても壊れないか。** 一意制約と `ON CONFLICT` で受ける（`resolveMember` の事例）。

## D. 認可と対象範囲

11. **すべての API・Server Action で、組織・メンバー・機体の所属を検査しているか。** 画面で隠すだけでは足りない。ID を直接指定された場合も弾く。
12. **フィーチャーフラグ（`OPS_ENABLED`）が本番で閉じているか。** 新しいルート・API・カタログ画面も、本番では 404 になるか。
13. **本番に出してはいけない画面（`/ops/design` など）が、環境変数の組み合わせで漏れないか。**

## E. 文言と安全性

14. **禁止語・断定表現がないか。** 「安全です」「許可不要」「報告義務なし」など、法的・安全上の断定は禁止。事故・ヒヤリハットは固定文（N1–N7、G1）以外を足さない。禁止語テスト（`incident-words.test-helpers.ts`）に新しい文言が載っているか。
15. **外部へ送信しない約束を守っているか。** DIPS・国への送信機能を作らない。下書きは下書きと明示する。

## F. 画面・操作（UI）

16. **状態機械の穴。** 開閉・選択・タブの状態に、「開いたまま別の操作」「二重に開く」「戻る」で矛盾する遷移がないか。`useDismiss`・InfoPopover の既存の仕組みを使っているか。
17. **ARIA。** `role`・`aria-controls`・`aria-labelledby` の参照先 id が実在するか（`panelId`／`tabId`）。非表示の層は `inert` と `aria-hidden` を併用しているか。
18. **キーボードだけで操作できるか。** フォーカス順、Esc で閉じる、閉じたらトリガにフォーカスが戻る。
19. **コントラストと3モード。** ライト・ダーク・現場モードのすべてで、文字と背景が基準を満たすか（`design-tokens.test.ts`）。新しい色は必ずトークン経由にする。
20. **ハイドレーション前後で壊れないか。** E2E は `next start` で動かす。操作前に水和を待つ。

## G. テスト

21. **競合・冪等・認可の不変条件に、DB テストがあるか。** 画面テストだけでは守れない。
22. **E2E がタイミング頼りになっていないか。** 固定待機ではなく `expect.poll` など、条件を待つ。
23. **新しい不具合の型を見つけたら、再発を防ぐテストを足したか。**

## 運用メモ

- CLAUDE.md の「Codex を待つ」規則は、Codex 停止が確定した時点で、本チェックリストを使う独立レビュー担当（サブエージェント）の合格に置き換える。置き換えは、ユーザーの了承を得てから行う。
- 追記先の目安：型が増えたら、該当する節（A〜G）へ1行で足し、事例のファイル名を括弧で添える。
