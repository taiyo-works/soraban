# そらばん UX 点検：メニュー・ホーム・導線

作成 2026-10-24 ／ 対象ブランチ `design/12g-journal-style-trial`（b3f0e10 時点）／ 宛先 のりさん

方法：コードと文書の読み取りだけ。実機でも、画面の撮影でも測っていない。操作数は導線から机上で数えた値で、スクロールの長さは入っていない。コードで確認できないことは「未確認」と書いた。

## 結論

1. 現場のスマホは骨組みがほぼ合っている。日常点検と日誌には「今日」から 2〜4 タップで着く（机上）。直すのは名前と、予定のない日の中身。
2. 名前が揃っていない。ホームにあたる場所を「今日」「運航管理のトップ」「運航管理へ」「そらばん 運航管理」と呼び、判定を「判定」「地点判定」「規制をチェック」と呼んでいる。
3. 事務所の PC がスマホ用の骨組みのまま。地図は判定画面だけにあり、入力フォームの後ろにある。計画と地点の登録に地図はなく、座標を打つ。機体・操縦者・許可の登録は「その他」の奥で、3 クリックかかる。地図への書き込み・描画は、コード上は見当たらない。
4. 予定のない日に「次の期限」を見る場所がない。期限の列があるのは技能証明と許可・承認だけで、横断の一覧（12f）は未着手。
5. 推奨：名前を「ホーム」「判定」「計画」「日誌」「登録」に揃える。PC は業務の流れ順の左メニュー、スマホは下タブ 5 つのまま中身を直す。DIPS 連携は未実装・保留で、入る場所は上の案に足せる。ただし DIPS から機体・操縦者を読み取れるかは、手元の資料では確認できていない。

事実メモ：
- 「その他」の中の機体・操縦者・地点の一覧は、戻る先が「その他」ではなく「運航管理のトップ」（＝今日）。許可と事故だけ「その他」に戻る。メニューの現在地と戻る先が食い違う。
- 「今日」の並び：見出しと日付 → 今日の飛行のカード 1 枚（または空の状態）→ 今日の残り → 次にやること（最大 8 件）→ 記録を入力（3 ボタン）→ 免責。
- 「次にやること」の対象：7 日以内に始まる計画、飛行中・日誌待ちの計画、直近 3 日の日誌の食い違い、事故・ヒヤリハット、技能証明（7 日以内に飛ぶ操縦者だけ。期限の 60 日前から）。機体登録・許可・保険・点検整備の期限は出ない。
- 期限の列があるのは、技能証明（`pilots.license_expires_on`）と許可・承認（`valid_to`）だけ（マイグレーションの範囲）。機体の登録や保険、点検整備の期限の列は見当たらない。点検整備の画面もない。
- 判定画面 `/` の並び（DOM 順）：説明と免責 → 住所／座標貼り付け／緯度経度／機体・運航条件（折りたたみ）／飛行方法／「規制をチェック」／地点の例 → **地図** → 結果。レイヤーの凡例は地図の下にあり、7 種すべてが初期表示。地図は 2:3（スマホ）、16:9（広い画面）。
- 地図の地点指定（クリック、右クリック、長押し、現在地の確定、住所の候補選択）は、押すと判定が自動で走る。
- 地図のレイヤー 7 種：DID、工業専用地域、空港等周辺、小型無人機等飛行禁止法の対象施設、都市公園、指定史跡、公衆密集地。緊急用務空域は地図に無い（免責に「動的情報は反映していません」）。現場モードで手入力の確認欄がある。
- 飛行計画の入力に地図は無い。必須 10 欄（計画名、機体、操縦者、日付、時刻、所要時間、目的、場所名、緯度、経度）。登録地点を選ぶと名称と座標が入る。判定画面の「この判定で飛行計画を作る」から来ると、地点・飛行方法・許可・予定日だけが入る。
- 本番は運航管理が停止のまま（HANDOFF §5）。社内の実利用の記録は無い。

## 3. 点検表

各項目 0〜2 点（2 が良い）。机上の評価で、実機での確認前の点数。

| 項目 | 点 | 理由 |
|---|---|---|
| いまの場所の分かりやすさ | 2 | メニューの現在地は文字・形・`aria-current` の 3 重。現場モードはメニューを出さず「今日へ戻る」で退路を示す |
| 名称の分かりやすさ | 1 | ホームに 4 つの名前、判定に 3 つの名前。「その他」は中身が見えない。ヘッダーの小見出し（英語、9px）は日本語の画面に合わない |
| 主要な移動先の見つけやすさ | 1 | 点検・日誌・計画は 1 段目。登録（機体・操縦者・許可・地点）は「その他」の奥。期限はどこにも無い |
| 次の一手の明確さ | 2 | 飛行がある日は、カードの主ボタン 1 つと動詞で始まる「次にやること」。弱いのは予定のない日（空の状態は 2 ボタンだけ） |
| 戻りやすさ | 1 | 戻る先がメニューの分類と食い違う。戻りリンクは 12px の小さな文字（高さ 44px は確保）。点検の保存後に現場へ戻る点はよい |
| 押し間違いの起きにくさ | 2 | 確認ダイアログの代わりに「取り消す」、離陸の二度押し防止、入力の下書き保持。懸念：「すべて正常」で全項目が埋まる |
| 片手・屋外 | 1 | 現場モードは 56px（離着陸 80px 以上）で 2 点相当。それ以外は 44px 止まりで、11〜13px の文字が多い（判定画面のフォーム、凡例、戻りリンク） |
| PC の効率（地図の流れ） | 1 | 判定から計画への引き継ぎはある。地図がフォームの後ろ、計画と地点登録に地図なし、凡例は地図の下、描画なし、幅 896px の 1 本の列 |
| 空・エラー・読み込み中 | 2 | 「今日」の空は理由と次の 2 手を書く。判定の失敗に再試行。弱い電波の現場で読み込みが遅いときは「読み込み中…」の 1 行のみ（実機未確認） |

## 4. DIPS 連携の観点

### 4.1 事実（連携は未実装・保留）

- DIPS 連携は保留。API の申請と固定 IP は決めず、アプリを先に完成させる方針（HANDOFF §5・§6、2026-10-21）。利用は当面社内のみ。
- 機体・操縦者は、当面アプリ内で登録する（のりさんの説明）。
- 通報は、手動アダプター（既定）と模擬アダプター（開発・CI・E2E 専用）まで（`docs/sprints/sprint-12b.md`）。API アダプターは作っていない。そらばんは DIPS に送信せず、利用者が DIPS で通報した結果（日時・番号）を手で記録する。記録は「利用者の申告」と表示する。
- データ側：機体・操縦者の表（`0005_ops_aircraft_pilots.sql`）に、登録元（アプリ／DIPS）を示す列は見当たらない。
- DIPS の API（`docs/references/dips-fpr-guideline-findings.md`、飛行計画通報ガイドライン v1.10 の精読）：API は 3 つ（飛行計画情報取得、飛行禁止エリア情報取得、飛行計画通報受付）。通報の取消・削除の記載なし。結果の照会専用 API は無く、事後の確認は飛行計画情報取得で自分の計画を引く形。
- **DIPS に登録済みの機体・操縦者を読み取る API は、上の精読の一覧に出てこない。**許可・承認の取得（FPA）には機体情報が含まれると書かれているが、これは `dips-api-notes-external.md`（のりさん提供の外部調査）にだけあり、原本と照合していない。読み取りができるかは未確認。しかも、現在の航空局への確認事項（`dips-api-application-draft.md`、6 項目）にこの点は入っていない。
- トークンの有効時間は例示値（300 秒・3600 秒）だけで、保証値かは不明（外部調査、未検証）。再ログインが頻繁に要る可能性があり、連携切れは日常的に起こるものとして設計するのが安全、というのは私の見立て。

### 4.2 将来 DIPS 連携が入っても、作り直さずに済むか

| 観点 | 現状 | 判断 | 置き場の案 |
|---|---|---|---|
| 機体・操縦者の取り込み | 登録フォームのみ（運航管理者）。「その他」の奥 | メニューは作り直さずに済む。ただし取り込めるか自体が未確認 | 「登録」の機体・操縦者の一覧の上に「DIPS から取り込む」。連携が有効なときだけ出す |
| 登録元（アプリ／DIPS）の表示 | 無い（データ側にも無い） | 画面は足せる。データの列の追加が別途要る | 一覧・詳細・計画の選択肢・ホームのカードに、同じ小さな文字札 |
| 通報の状態の見せ方 | 状態語彙 6 つが既にある（準備済・手動記録・API 送信済・失敗・結果不明・取り下げ）。通報画面に「送信元」の札 | 作り直し不要。画面はアダプターの能力（mode）だけで分岐する設計（sprint-12b）で、通報画面には送信元（手動／模擬）の札が既にある | ホーム・計画一覧・計画詳細・通報画面で、同じ札と同じ語を使う。「申告」と「API で確認済み」を札で見分ける |

### 4.3 通報の流れ（計画 → 判定 → 準備 → 送信 → 結果）が現れる場所

現状は、計画の保存時にサーバーが判定を実行し、通報の準備（DIPS の入力順に整えてコピー）と結果の記録が `/ops/plans/[id]/report`。「送信」は無い（利用者が DIPS で通報する）。

| 段階 | PC（事務所） | スマホ（現場） |
|---|---|---|
| 計画 | 計画の入力 | 見るだけ（ホームのカード） |
| 判定 | 計画の保存時に自動。判定画面で事前に確認 | 現在地の判定（判定タブ） |
| 通報の準備 | 計画詳細の「通報」節と通報画面 | 出さない |
| 送信（将来）／DIPS で通報して記録（現状） | 通報画面。送信は PC に寄せる（スマホの押し間違いによる二重通報を避ける案） | 出さない |
| 結果 | ホームの「次にやること」、計画一覧の札 | 現場モードの「飛行前」で通報済みを再掲。未記録なら警告（記録は止めない） |

## 5. 案

### 5.1 名称の候補

| 現行 | 候補 | 利点 | 懸念 |
|---|---|---|---|
| 今日 | **ホーム** | 毎日予定がなくても成り立つ。「運航管理のトップ」「運航管理へ」の呼び方も 1 つにできる | 中身が名前から分からない |
| | やること | 中身が名前に出る。予定のない日は「ありません」と言える | 期限や直近の飛行が入りにくい |
| | 運航 | 事業の言葉 | アプリ名「運航管理」と重なる |
| | 今日（据え置き） | 変更なし | 予定のない日に合わない |
| 判定 | 判定（据え置き） | 製品の核の語。4 段の判定と同じ語 | PC では「地図」を探す人がいる |
| | 地図・判定 | 地図の作業が見つかる | 5 文字で、スマホの 1 項目（約 75px）に収まるかは未確認 |
| その他 | **登録** | のりさんの言葉（登録する）と合う。機体・操縦者・許可・地点 | 利用者・ログアウトの置き場が別に要る |
| | 台帳 | 事務の言葉 | 馴染みの度合いは未確認 |
| | その他（据え置き） | 変更なし | 中身が分からない |

「その他」の中身：登録（機体、操縦者、許可・承認、よく使う地点）／記録（事故・ヒヤリハット。日誌の 3 つ目の種類にする案もある）／管理（利用者）／アカウント（ログイン中、ログアウト）。
判定の呼び方は「判定」に揃える（ヘッダーの「地点判定へ」、ボタンの「規制をチェック」）。

外部の原則（確認した範囲）：Apple の指針は、検索結果の要約によると iOS のタブを 3〜5 個とし、2025 年 7 月の更新版では数を固定せず「端末の大きさで見える数が変わる」書き方になった。本文は取得できず、要約のみ。https://developer-rno.apple.com/design/human-interface-guidelines/components/navigation-and-search/tab-bars ／ ほかの原則（Material、WCAG）は取得できなかったので書かない。タップ領域の 44／56px は本プロジェクトの基準（ui-direction、sprint-12c）。

### 5.2 軸にする考え方：飛行の「行程」

業務の流れ（判定 → 計画 → 確認 → 通報 → 点検 → 飛行 → 日誌）は、既にデータから導出されている（spec §13.10。状態は保存せず記録の有無から出す）。これを 1 本の行程として 1 行に並べ、ホームの主役にする案。メニューの並びも同じ順にする。新しい機能は足さず、既存の導出の見せ方を変えるだけ。

```
10:30  ○○公園  JU1234   判定 済 → 計画 済 → 確認 済 → 通報 済 → 点検 未 → 飛行 → 日誌
```
（例。数字は仮）。1 行に 7 段は 375px で窮屈になり得る。見本で確かめる。

### 5.3 PC の案

**PC-1　流れ順の左メニュー**（幅約 200px、ラベル常時）

```
そらばん
  ホーム
  調べる   地図・判定
  飛ばす   計画
           日誌（飛行記録／日常点検／事故）
  台帳     機体  操縦者  許可・承認  地点
  管理     利用者  ログアウト
```
- 利点：業務の流れで読める。登録が 1 段目に出る（3 クリック → 2）。スマホと同じ語と順。12g の方針（左サイドバー）と同じ。
- 欠点：項目が約 10。地図の幅が左メニュー分だけ狭くなる。12g の 1b の実装が前提。
- 適合：登録と計画は速くなる。地図の作業は変わらない。

**PC-2　地図を土台にしたワークスペース**

```
[細い左レール]  [ 地図（常に主役）                     ]  [作業パネル]
 ホーム 判定     [ レイヤー  現在の判定  描画（将来） ]   判定／計画／登録の
 計画 日誌 登録                                          フォームが右に開く
```
- 利点：地図とレイヤー、将来の描画、DIPS の飛行禁止エリア、計画の地点指定が 1 つにまとまる。
- 欠点：地図が要らない画面（登録、日誌の一覧）で地図が居座る。作る量が最大。描画は現状ほぼ未実装で、先に枠だけ作ることになる。
- 適合：「規制を地図で確認する」作業には最も合う。

**PC-3　横タブのまま、名前と中身だけ直す**（ホーム／判定／計画／日誌／登録）
- 利点：変更が最小で、スマホと同一。
- 欠点：896px の 1 本の列のまま。登録は 3 クリックのまま。地図の問題は残る。
- 適合：事務所の作業の効率は上がらない。

PC のホーム案（例。数字は仮）：
```
ホーム                                       10/24
次にやること (3)                  │ 近づく期限
  日常点検をする   ○○公園 10:30 │   技能証明  山田   あと 21 日
  通報の内容を確認  11/02 橋梁    │   許可・承認  包括  あと 40 日
  日誌を記入する   昨日 ○○       │   機体・保険・整備（12f 以降）
────────────────────────────
直近の飛行（行程）
  10:30 ○○公園   判定 済 計画 済 確認 済 通報 済 点検 未 飛行 日誌
  11/02 橋梁      判定 済 計画 済 確認 未 通報 未 …
```
DIPS 連携が切れたときは、ホームの上に細い帯を出す（§4.2）。

### 5.4 スマホの案

**SP-1　5 タブのまま、名前と中身を直す**（ホーム／判定／計画／日誌／登録）

```
ホーム  10/24
次の飛行  10:30 ○○公園  JU1234
  判定 手続き済 ／通報 済 ／確認 済
  [ 現場モードを開く ]
次にやること (3)
  日常点検をする …
近づく期限
  技能証明 山田 あと 21 日
────────────
 ホーム  判定  計画  日誌  登録
```
- 利点：変更が小さい。点検・日誌までの操作数は今のまま 2〜4。予定のない日も「次の予定」と「近づく期限」が出る。
- 欠点：現場の 3 作業（点検・飛行・日誌）への入口は、ホームのカード経由のまま。

**SP-2　「飛ぶ」を中央に置く 5 タブ**（ホーム／判定／**飛ぶ**／日誌／登録。計画はホームの中）
- 利点：現場の流れ（点検 → 離着陸 → 日誌）に 1 タップで入れる。
- 欠点：計画の一覧が 1 段深くなる。飛行のない日の「飛ぶ」の中身が決まらない。現場モードは意図してメニューを出さない作りで、そことの関係の整理が要る。

**SP-3　4 タブ＋「次の飛行」の帯**（ホーム／判定／日誌／登録。計画はホームに統合）
```
┌ 10:30 ○○公園  点検 未  通報 済  [現場モードへ] ┐  ← 飛行日だけ、全画面の上に固定
```
- 利点：どの画面にいても現場に戻れる。タブが 4 つで 1 項目が広い（約 94px）。
- 欠点：帯が常に 48px 前後を占める。画面が日によって変わる。計画の一覧とホームが重なり、重くなる。

### 5.6 推奨と自問自答

**推奨**：名前は「ホーム／判定（PC は地図・判定も可）／計画／日誌／登録」。PC は PC-1。判定画面だけ先に PC-2 の作法（地図を主役に、入力と結果を横の板に）へ進める。スマホは SP-1。SP-3 の帯は見本で試してから決める。

理由：
- 5 タブは社内の現場作業をすでに 2〜4 タップで通している。変える価値が高いのは構造より名前と中身（予定のない日、期限、登録の置き場）。
- 事務所の問題は「地図の置き場」と「登録の深さ」。PC-1 で登録の深さを、判定画面の再構成で地図の置き場を、順に直せる。
- スマホと PC で語と順を揃えると、のりさんが両方を使うときに迷わない。

自問自答：
- 本当に「ホーム」でよいか。反対：中身が見えない名前で、タブを押す理由にならない。毎日は飛ばないので「やること」の方が目的に近い、という見方もある。答え：ホームの中身は「次にやること」「近づく期限」「直近の飛行」の 3 つで、1 語の「やること」には収まらない。ただし決め手は実機で、見本で 2 語を並べて台本 S-D（予定のない日）を試して選ぶ。
- PC だけ別構成にすると、スマホと別物にならないか。答え：語と順は同じにし、PC は「登録」を展開して見せるだけ。
- 地図を中心にした PC-2 の方が、のりさんの作業に合うのでは。答え：合う。ただし地図が要るのは判定と計画の地点、将来の描画。登録と日誌には要らない。左メニューは地図の左に付く形になるので、先に PC-1 を作っても無駄にならない。
- 行程の 1 行表示は作りすぎでは。答え：新しい機能は無く、既存の導出の並べ替え。ただし 375px で 7 段が読めるかは未確認なので、見本で確かめる。
- 机上の操作数は当てになるか。答え：スクロールの長さが入っていない。操作数が少なくても遅い可能性がある（判定画面の地図は特に）。実機で測るまで目安にとどめる。

## 7. 確認できていないこと

- 実機での見え方：375px のスクロール量、凡例と地図が同時に見えるか、屋外での読みやすさ。
- 起動時に最初に開く画面（ブックマークかホーム画面のアイコンか）。台本は「今日」から始めると仮定した。
- 計画の「場所の名称」、日常点検の「実施場所」の必須の扱い。
- 戻りリンクの行き先：通報画面、判定の記録、日常点検、利用者の各画面。
- 12f（期限一覧）の中身と、12g の 1b（シェル）の最終形。
- DIPS 側：機体・操縦者を読み取れる API の有無、トークンの実際の寿命、取消の扱い。外部調査（`dips-api-notes-external.md`）は原本と照合していない。
- 外部アプリの原則は、Apple の指針の要約のみ確認（§5.1）。
- 社内の実利用の記録（本番は停止のまま）。この点検は机上の評価で、利用者の声が入っていない。
