# 通報・点検・日誌を主役にした UI の設計（設計フェーズ。アプリのコードは変えていない）

> 状態: 設計書と静的プロトタイプ（2026-10-31、designer 作成。ユーザーの見本選びと承認の前）。
> 範囲: `docs/design/ops-core-ui/` のみ。`apps/` は変更していない。コミット・push はしていない。
> 方針（ユーザー原文の要旨）: 「飛行前の点検、飛行後の点検、日誌をつける義務を理解した上で UI を設計。**この飛行計画の通報、飛行記録や点検がメインのサービス**」。判定は補助。許可・承認の申請は一切扱わない。DIPS を置換せず、DIPS の「飛行計画の登録（新規作成）」の流れをアプリの中で代替する（送信は本人の DIPS 認証と最終確認。P1 手動、P2 API 後）。
> 読み方: 【測定】は `shots/` を撮った Chromium（1280×800・375×812）で測った値。【設計】は目標・方針で、実機では未検証。※要再確認は一次資料・専門家の確認待ち。新しい日付の計画書の記述を正としている。
> 見るファイル: `01-home-today.html` 〜 `08-aircraft-inspection.html`（共通 `tokens.css`、動きは `proto.js`）。ブラウザで直接開ける。`02-report-new.html#s2`〜`#s6` で手順の各段、`05-flight.html#before|#air|#landed` で状態を切り替えられる。

## 0. 要点

1. **主役は「通報 → 点検 → 飛行（離陸・着陸）→ 点検 → 日誌」の 1 本の流れ**。地図は通報の入力、判定は 1 行の入口だけ（画面の主役にしない）。
2. 画面の長さは「**1 画面 = 1 つの仕事**」で解く。通報の新規登録は 6 手順のウィザード（スマホは 1 手順 = 1 画面、PC は左に手順の一覧）、確認は折りたたみ、点検は「一括で異常なし + 異常の項目だけ展開」。
3. 意匠は**白と墨が主、橙は「次の 1 つの操作」と、ロゴの円から取った小さな印（現在の手順の丸、見出しの短い線、離陸の水平線の日の出）**だけ。カード・グラデーション・飾りのアイコンを使わず、罫と余白で区切る（航空日誌の紙面の落ち着き）。
4. 現場の画面（点検・飛行）は同じ部品のまま寸法だけを現場の値（押す面 56〜64px、本文 18px、7:1）にする。

### 2.1 1 本の導線

仕事・企画（案件）→ **通報の新規登録**（範囲・日時と高度・機体と操縦者・飛行の内容・安全と保険・連絡先と名称）→ **確認**（DIPS で出す、受付番号を記録）= 通報の控え → 当日: **飛行前点検 → 離陸 → 着陸（飛行時間を自動計測）→ 飛行後点検 → 日誌の確定** → 次の飛行（繰り返し）。各画面の上に 6 つの丸の「流れ」を置き、いまの位置を橙の丸、済みを墨の丸（チェック）、これからを白抜きの丸で示す（色だけに頼らず、記号と数字・ラベルを併用）。

### 2.2 通報の新規登録のウィザード（手順の分け方）

DIPS の入力の順（`docs/references/dips-fpr-screens.md` §3）を保ちつつ、**手元で決めるものを前に、DIPS の区分（中身未確認）を後ろに**寄せ、6 つに分けた。名称は既定値のまま通せるので最後。

| 手順 | 内容（DIPS の項番） | 既定・省略 |
|---|---|---|
| 1 範囲 | 地図（1）、参照飛行経路（4）= 「保存した飛行経路から選ぶ」 | 前回の計画の複製で流用 |
| 2 日時と高度 | 開始・終了（16。終了は自動）、定期・複数日（17）、最大飛行時間・所要時間（15）、飛行速度（18）、飛行高度（19） | 開始時刻と所要時間は候補のボタン |
| 3 機体と操縦者 | 機体情報（5）、操縦者情報（6）、飛行許可番号（3） | 前回と同じ機体・操縦者を既定 |
| 4 飛行の内容 | 飛行目的（7）、飛行空域（8）、飛行方法（9）、出発地・目的地（14） | 未確認の区分は枠のみ |
| 5 安全と保険 | 立入管理措置（11）、係留飛行（12）、補助者人数（13）、保険（10） | 補助者はステッパー |
| 6 連絡先と名称 | 連絡先（20）、その他・カテゴリー（21）、飛行計画名称（2） | 自アカウントを既定 |

- 最短の操作回数の設計: 各手順で必須が埋まっていれば**どの手順からでも「確認へ進む」**を出す（プロトタイプには未実装。【設計】）。**複製ルートは 6 タップ以内**（通報を作る 1 + 前回の計画を選ぶ 2 + 開始候補 1 + 所要時間 1 + 確認へ 1）、**新規（既定値を使う）は 10 タップ以内**（文字入力を除く。通報を作る 1 + 点 4 + 完了 1 + 開始候補 1 + 所要 1 + 確認へ 1 = 9 を最短と見る）。**実測は未実施**。
- DIPS の区分（機体情報・操縦者情報・飛行目的・飛行空域・飛行方法・保険・カテゴリー）は**中身未確認**のため、項目を創作せず「中身を確認できていない」旨の破線の枠（鍵の印）だけを置く。

### 2.3 通報の確認と DIPS への出し方（03）

- 上に固定の 1 文（「そらばんは DIPS に送信しません。…記録するまで『通報済み』にはなりません」）。
- 要点（略図・日時・場所）→ 入力の状況（入力済み／要確認／DIPS で入力／未確認の区分の件数）→ **要確認だけを先に**行で出す → 全項目は DIPS の順の折りたたみ（各項目にコピー）。
- **P1（いま。手動）**: ① 内容を整える → ② 「DIPS を開く」で本人が通報（送信と認証は本人）→ ③ 受付番号（飛行計画 ID）・登録日時・控えの保管場所を記録。記録するまで「通報済み」と出さない。番号なしは理由つきで記録。
- **P2（DIPS API 後）**: 本人の DIPS 認証 → 送信内容の確認 → 本人の最終操作で送信。受付番号は取り込み。可否と条件は確認中のため、折りたたみの中に小さく置き、**手順の主役にしない**。
- 受付のあと: 変更（変更点を示し、変更の通報を促す）、取消（DIPS で本人が行い、取消済みを記録）、重複（同じ内容の記録を一覧に「重複」と表示。API で重複の調整内容を取得できるかは要確認）。

## 3. 地図の範囲選択の操作設計

プロトタイプ（`02-report-new.html` 手順 1）で動くもの: 頂点のドラッグ、辺の「＋」で頂点追加、頂点の選択・削除（取り消すトースト付き）、点を打つ→完了で範囲の追加、円（中心をタップ、半径は数値）、複数範囲と一覧、戻す・やり直す（Ctrl/Cmd+Z、80 回分）、面積・周長・頂点数・座標（小数 6 桁）の表示。**見た目のみ・未実装**: スナップ（吸着）、地図のパン・ズーム、頂点の座標の直接入力、範囲の分割、自己交差の警告。

| 操作 | PC | スマホ |
|---|---|---|
| 点を打つ | 「点を打つ」を選び、クリック。3 点以上で「完了」（地図右下に出る橙の面） | 同じ（タップ）。下の操作列は常に見える（戻す・やり直す含む） |
| 頂点の移動 | ドラッグ | 頂点を押してドラッグ。**頂点の当たり判定は 48px（見た目 28px）**で、見た目より大きい。地図のパンは**頂点以外の場所を 1 本指で**（実機で検証） |
| 頂点の追加 | 辺の中点の「＋」をクリック（辺が短いときは出さない） | 同じ（当たり判定 44px） |
| 頂点の削除 | 選んで「頂点を削除」または Delete。**3 頂点以下では押せない** | 選んで「頂点を削除」（地図の右下）。直後に「取り消す」トースト（6 秒） |
| 範囲の分割・複数範囲 | 「範囲を足す」。分割は範囲を選び 2 点指定（設計のみ） | 同じ |
| 円 | 「円」→中心をタップ→半径は −/＋（10 m 刻み）と数値（1〜10,000 m。上限は DIPS 側※要再確認） | 同じ |
| 取り消し・やり直し | ボタン + Ctrl/Cmd+Z（+Shift） | ボタン（常時表示、1 タップ） |
| スナップ・座標の確認 | 近い頂点・辺に吸着（Alt で解除）。選んだ頂点の座標を一覧で表示・入力 | 吸着は設定で切り替え。座標は一覧の行を押して選択 |
| 誤操作の防止 | 削除は選択→ボタンの 2 段、直後に取り消し。押した頂点は橙の面 + 点線の輪で示す（色だけにしない） | 同じ。描画中は他の操作列の項目を無効（破線）にする |
| 範囲の情報 | 地図の上に「範囲 n」「頂点数・面積」を常時表示。周長は一覧の下 | 同じ（一覧は折りたたみ） |

範囲ごとの高度・時間帯は控え（内部メモ）として持ち、DIPS には最大高度と全体の日時を送る（`sprint-19.md` §2）。複数範囲の送り方は未確認のため、確認画面で「DIPS に送るのは 1 つです」と確認させる設計（`sprint-19.md`）。地図の注記は「地図は参考。実際の飛行範囲の責任は利用者にあります」（プロトタイプでは小さく「地図は参考のモックです」）。

## 4. 点検の UI（04・06 で同じ部品）

- 点検項目の仮の例: 日常点検 9 項目（Sprint 11。機体全般・プロペラ・フレーム・通信系統・推進系統・電源系統・自動制御系統・操縦装置・バッテリー・燃料）。**設計上の注記: 項目は国家資格の教則に基づいて確定する（未確定。実装前に一次資料で確認）。**画面には項目名だけを出し、点検の内容の説明は載せない（Sprint 11 の方針）。
- **一括 + 異常のみ詳細**: 最上部に進み具合（5/9 と帯）と状態の文（「未選択 4 項目・異常あり 1 項目」）、「**未選択をすべて『異常なし』にする**」（64px。すでに付けた項目は変えない）。各項目は「異常なし／異常あり」の 2 択（全幅・56px 以上）。**既定は未選択で、付けていない項目を異常なしとして保存しない**。保存されるのは項目ごとの結果。
- 異常あり → その項目の下に赤系の囲みが開き、**内容（必須）**と**写真を添える**（任意。保存先は未決 = `ops-completion-plan.md` Q4）。内容が空なら主操作は無効のまま（理由を下に 1 行）。
- 主操作は画面の下端に固定（無効のときは破線でなく灰色の面 + 理由の文）。飛行前・飛行後で**同じ部品**。飛行後は、飛行時間（自動）と「安全に影響のあった事項」「不具合」の有無を足し、全項目が異常なしの状態では項目を折りたたむ。
- 状態は「記号 + 文字」: 異常なし = チェック + 墨の面、異常あり = 四角に「!」+ 赤系の文字と線、未選択 = 破線。

## 5. 日誌・飛行時間の UI

- **飛行（05）**: 離陸前は大きな「離陸」（高さ 96px、幅いっぱい）、飛行中は経過時間（72px、`H:MM:SS`）と「着陸」、着陸後は飛行時間と「飛行後点検へ」。押し間違いの取り消しは同じ画面の下に常設（誤タップを防ぐため主操作から離す）。離陸の水平線に小さな日の出（橙の半円）を置く。
- **圏外**: 画面の最上部に常に「圏外です。記録はこの端末に保存しています／送信待ち n 件／最後に保存 hh:mm:ss」。破線の枠 + 記号（電波なし）+ 文字。圏内では実線に変わる。
- **日誌（07）**: 確定待ちを最初に 1 件（主操作）→ 今月・機体別・操縦者別の総飛行時間 → 一覧。詳細は様式 1 の項目（日付・目的、離着陸の場所と時刻、飛行時間、総飛行時間、飛行前後の点検、安全に影響のあった事項、不具合）を、**値の出どころ**（ボタン計測／自動計算／通報から／点検から／入力）の札つきで並べる。
- **飛行時間の補正**: ボタンで測った時間と取り込んだ記録の時間を並べ、採る方・理由を選ぶ。元の時刻は版として残す。**確定したあとは書き換えず、訂正は理由つきの新しい版**（`ops-completion-plan.md` C-J5・C-J6）。
- 総飛行時間は機体別・操縦者別に `H:MM`（等幅数字）で大きく。点検整備の時期の基準は**利用者が登録**し、法定の間隔をこちらで決めない（C-J7）。
- 根拠条文は断定しない（※根拠は専門家確認）。様式 3 の項目は確認中のため枠のみ。

## 10. ユーザーに見本で選んでほしい論点

1. **橙の強さ**: 現在の「静」寄り（主操作と小さな印）に対し、見出しの帯や空の状態にもう少し橙を広げる案（`brand-visual-plan.md` の A「静」／B「帯」／C「地平」）。この見本は A に B を少し足したもの。
2. **通報のウィザード**: スマホは 1 手順 1 画面（この案）か、1 本の長いフォームを折りたたみで区切る案か。「確認へ進む」の近道の見せ方。
3. **点検の「異常なし」の選択面**: 墨の面（この案。橙の壁を避ける）か、橙の面（ブランド色を濃くする）か。
4. **離陸・着陸の大ボタン**: 橙の面（この案）か、墨の面に橙の縁か。直射日光の実機で見比べたい（橙の面の墨は模擬で 3.5:1）。
5. **ロゴとワードマーク**: ロゴの置き方（小さな単独のマーク + 文字「そらばん」）と書体。ロゴの使用ルール（余白・最小サイズ）は未確認。
