# そらばん UX 比較：判定画面（`/`）のスマホ案と PC 3 ペイン

作成 2026-10-25 ／ 対象ブランチ `design/12g-journal-style-trial` ／ 宛先 のりさん
前の文書：`docs/design/ux-compare.md`（メニューとホームの案）、契約 `docs/sprints/sprint-12g-1b.md` の PR B（B1〜B10）

## 0. 要点

- のりさんの指摘どおり、現状の `/` は縦に長い。375×812 でページ全体が 16,495px（画面の 20.3 倍）、1280×800 でも 9,819px（12.3 倍）ある。結論が出る場所は、375 で上から 3,903px（画面の 4.8 倍め）、1280 で 3,167px（4.0 倍め）。
- 現状で、地図と結論が同時に見える瞬間は、スマホにはない。PC でも、地図の下端 242px と結論の見出しだけがかろうじて重なる程度で、実用にならない。
- スマホ案は 3 つ作った（A シート、B タブ、C 折りたたみ）。台本 4 本のうち、現在地で判定する台本（②）は A・B・C とも 1 回押すだけで、スクロールは 0。現状は 2 回押して、約 4 画面分スクロールする。
- PC の 3 ペインは、入力・地図・結果・層の切り替えが 1280×800 のスクロールなしで同時に見える（B1 の完了条件を見本で確かめた）。
- 見本は `/ops/design?view=judge`（開発・プレビュー専用）。地図は絵、結果は見本データ。実画面（`/`、`/ops` 以下）と判定エンジンは変えていない。
- 数えたのは Chromium でマウスのクリックを再現した回数。指・手袋・屋外の日差し・片手での届きやすさは測っていない（§8）。

## 1. 見本の見方

| 見たいもの | URL の例（`DESIGN_CATALOG=1` のサーバー、開発・プレビューのみ） |
|---|---|
| スマホ A（シート） | `/ops/design?view=judge&sp=sheet` |
| スマホ B（タブ） | `/ops/design?view=judge&sp=tabs` |
| スマホ C（折りたたみ） | `/ops/design?view=judge&sp=fold` |
| PC の 3 ペイン | `/ops/design?view=judge&pc=three`（幅 1024px 以上で表示。下に幅 375px の枠でスマホ案も出る） |
| 暗い配色・現場モード | `&theme=dark`、`&field=1` を足す |

- 幅 1024px 未満では、スマホ案が画面いっぱいに出る。のりさんの端末でそのまま開いて押せる。
- 上の細い帯に「見本データ」の表示と、スマホ案の切り替えがある。現在地の精度（30m／150m）の切り替えは、スマホでは見本の下、PC では帯にある。
- シートの引き上げは、ハンドルを押す・ドラッグする・矢印キー（上下）・Enter／Space のどれでもできる。Esc で 1 行に戻る。`prefers-reduced-motion` では高さの移り変わりが止まる。
- 層の並びは、DIPS と同じ群の構成（航空法／小型無人機等飛行禁止法／その他）に、そらばん追加（都市公園・指定文化財・公衆が密集する施設）を足した形。群の名前は案で、DIPS 側の項目名は確かめていない。層のデータは変えていない。
- 見本の結果は短くしてある（手続き 2 件、規制の行 6 行）。実画面の結果はもっと長い（§3.2）。

## 2. 数え方

- Playwright（`e2e/sprint12g-judge.spec.ts`、補助は `e2e/judge-measure.ts`）が、台本ごとに最短の経路を押す。現状の `/` と案を、同じ台本・同じ数え方で測る。
- 押した回数：ボタン・タブ・チェック欄を押す回数。文字の入力は 1 回と数える。
- スクロール量：押す部品や、台本の最後に読む部分を、画面の中に出すために動かした量の合計（px。画面の高さの何枚分か）。ブラウザの自動スクロールには任せず、最小の量だけ自分で動かして数えた。画面の上に固定された帯がある案では、その下に出す。
- 同時に見える：台本が終わった時点で、地図が画面の 20% 以上、隠されずに見えていて、答え（結論）も隠されずに見えているか。地図の見える面積は、格子状に当たり判定して求めた。
- 画面の大きさはスマホが 375×812、PC が 1280×800。スマホ案の枠は、見本の上の帯を除いた高さ（812 − 52 = 760px）。ブラウザのアドレス欄の分は引いていない（実機ではもう少し狭い）。
- 台本（現状の `/` では、起動時に初期の地点が自動で判定され、結果は出ている状態から始める）：
  - ① 地点を住所で入れて判定する（住所を入れて、位置決定を押し、新しい結果を読む）
  - ② 現在地で判定する（位置情報はモック。精度 30m）
  - ③ 結果の詳細を確認する（「DID の判定の根拠」を読む）
  - ④ 層（DID）を切り替える（切り替えたとき、地図が見えるか）

### 3.1 ページの形

| 地図の位置（上から） | 2,613〜3,124px（3.2 倍め） | 2,147〜2,737px（2.7 倍め） |

| 地図の下端から結論の上端まで | 779px | 430px |
| 最初の画面で答えが見えるか | 見えない（見出しと入力欄の途中まで） | 見えない |

| 台本 | 375×812：押す回数／スクロール | 地図と結果が同時に | 1280×800：押す回数／スクロール | 地図と結果が同時に |

## 4. 案の設計（スマホ）

どの案も、紙面の方針（角丸 5px、影なし、藍 1 色、押す部品 44px・現場モード 56px、文字がはみ出さない）に合わせた。免責の語「参考情報」は、1 行の要約の中に常に出す（C7）。

### 案 A：地図を台紙に、結果は「判定票」を引き上げる

```
┌──────────────────┐
│[住所・座標][🔍][現在地で判定]│  ← 上の 1 行（紙色の帯）
│                    [層 7/7]│
│      地  図（全面）        │
│          ◉                 │
├──────────────────┤
│ ═══  (ハンドル)             │
│ [要手続き] DID の上空…   ^ │  ← 判定票（最初は 1 行）
└──────────────────┘
 1 行 → 半分（手続き・規制ごとの判定）→ 全体
```

- 地図が画面の土台。入力は上の 1 行だけ（住所・座標と、現在地で判定）。結果は下の「判定票」で、最初は 1 行の要約（判定の印・理由・地点・「参考情報」）。ハンドルを押す・引く・矢印キーで、半分、全体と上がる。
- 判定すると判定票は 1 行に戻り、ピンが見える位置に地図が動く。層は右上の「層 7/7」から、DIPS と同じ群の一覧を開く。
- 利点：最初の画面から地図と答えが同時に見える。現在地で判定が 1 回、スクロール 0。
- 欠点：入力欄と「現在地で判定」が画面の上端にあり、片手の親指では届きにくい（見本のまま実機で確かめていない）。判定票の中は、実データだと長く、シートの中でスクロールする。層の一覧を開くと地図の大半が隠れる（④で地図が見える面積は 21%）。実装は、`regulation-checker.tsx`（1,912 行）の入力・結果・地図を別の部品に分ける作業が最も大きい。
- 現場で現在地を確認する使い方への合い方：高い。開いてすぐ「現在地で判定」を押せば、1 行で答えが読める。屋外で最も多い場面（要るか要らないかだけ知りたい）に一番近い。

### 案 B：「入力／地図／結果」の 3 枚綴じと、常に見える要約の帯

```
┌──────────────────┐
│  入力 │ [地図] │ 結果      │  ← 3 つの綴じ
├──────────────────┤
│[要手続き] DID の上空… >   │  ← 要約の帯（どの綴じでも見える）
├──────────────────┤
│      地  図                │
│          ◉                 │
│[現在地で判定]       [層7/7]│
└──────────────────┘
```

- 上に 3 つの切り替え、その下に要約の帯を固定。帯を押すと結果の綴じが開く。最初は地図の綴じ。「現在地で判定」は地図の綴じの下（親指の位置）に置いた。住所の入力は入力の綴じにあり、判定すると地図の綴じに戻る。
- 利点：画面の役割がはっきりする。現在地で判定が 1 回、スクロール 0。親指で押せる位置にボタンがある。
- 欠点：詳細を読むと地図が見えない（③で地図 0%）。住所で判定するには、入力の綴じへ移る 1 回が増える（①は 3 回）。「結果」を開く必要がある操作が多い。
- 現場で現在地を確認する使い方への合い方：高い。要約の帯で答えは読め、詳細は 1 回で開ける。ただ、詳細を見ながら地図で場所を確かめることはできない。

### 案 C：縦の流れを残し、要約を最上部に固定し、詳細を折りたたむ

```
┌──────────────────┐
│[要手続き] DID の上空…      │  ← 固定の帯（スクロールしても残る）
├──────────────────┤
│[住所・座標][🔍][現在地で判定]│
│▸ 機体・飛行方法（既定のまま）│
├──────────────────┤
│  地図（画面の 4 割）        │
│▸ 層 7/7                    │
├──────────────────┤
│ 結論・手続き                │
│▾ 航空法（2 件）             │
│▸ 小型無人機等…／そらばん追加│
└──────────────────┘
```

- 現状の並び（入力 → 地図 → 結果）を残し、説明・機体条件・規制の行を折りたたんで短くする。要約の帯を上に固定し、どこまでスクロールしても答えが見える。
- 利点：実画面の構造を最も壊さない。移行が一番軽い。地図と答えが同時に見える（地図 41%）。
- 欠点：ページは縦にスクロールする形のまま。見本は短く作ってあるので、実データでは長くなる。入力も地図も上に固まるが、結果の詳細は下にあり、現状の「縦に長い」不満を一部残す。
- 現場で現在地を確認する使い方への合い方：中。帯と現在地のボタンが画面の上にあり、1 回で答えは見える。

## 5. 比較（台本を案ごとに数えた結果）

スマホは 375×812、押す回数／スクロール／地図と答えが同時に見える（地図の見える割合）。

| 台本 | 現状 | A シート | B タブ | C 折りたたみ |
|---|---|---|---|---|
| ① 住所で判定 | 2 回／4.1 画面／同時に見えない | 2 回／0／見える（75%） | 3 回／0／見える（74%） | 2 回／0／見える（41%） |
| ② 現在地で判定 | 2 回／4.0 画面／見えない | 1 回／0／見える（75%） | 1 回／0／見える（75%） | 1 回／0／見える（41%） |
| ③ 詳細の確認 | 0 回／7.1 画面／見えない | 2 回／0／見える（34%） | 2 回／0／見えない（0%） | 1 回／0.2 画面／見える（41%） |
| ④ 層の切り替え | 1 回／3.0 画面／地図は見え、結論は見えない | 2 回／0／見える（地図 21%） | 2 回／0／見える（27%） | 2 回／0／見える（41%） |

- ③の「見える」は、シートを半分に上げたとき、地図が上に残り、DID の行の展開が見える状態を指す。
- 見本の結果は短く作ってある。実画面の詳細はもっと長いので、③のスクロールと、シート・タブ・折りたたみの中のスクロールは、実装の段階で増える。ただし長さが増えるのは詳細の中だけで、結論・地図・入力の位置は変わらない。
- 現状は「①②は押す回数が同じで、スクロールが 3〜4 画面」、案は「回数は同じか 1 回減り、スクロールがほぼ 0」。回数よりスクロールの差が大きい。

## 6. PC の 3 ペイン

```
┌─────────┬──────────────────┬───────────┐
│ 入力     │      地  図       │ 結果       │
│ 住所     │         ◉         │ [要手続き] │
│ 現在地   ├──────────────────┤ 手続き     │
│ 条件     │ 航空法 [空港等][DID][工専除外] │ 規制ごと   │
│          │ 小型無人機等 [対象施設]       │ ▸ DID      │
│          │ その他／そらばん追加 [..]     │ 免責       │
└─────────┴──────────────────┴───────────┘
 左 19rem ／ 中央 残り ／ 右 22rem
```

- 1280×800 で、入力・地図・結果・層の切り替えがすべてスクロールなしで同時に見える。台本 ①〜④ はいずれも、押す回数 2・1・1・1、スクロール 0。現状は 2・2・0・1 で、スクロールが 2.6〜4.8 画面。
- 地図の幅は 624px（左右のペインを除く。見本）。ログイン済みで左メニューが付くと、さらに狭くなる。契約 B1 のとおり、実装時に実測して PR に書く。
- 結果欄のスクロール見積り（測っていない）：結論・手続き・規制ごとの判定の頭は右ペインの 1 画面目に入る。実画面の結果の高さは、現状で約 6,650px（1280 の結論から末尾まで）。右ペインは現状の本文より狭くなるので、折り返しが増えて、もっと長くなる。全部読むなら、右ペインの中で 6,650px 以上のスクロールが残る。ただし地図と入力は動かない。
- 層の切り替えは、群（航空法／小型無人機等飛行禁止法／その他／そらばん追加）ごとに 1 行。押す部品は 44px。

## 7. 採点（0〜2 点）

0 は現状より悪いか同じ、1 は改善するが課題が残る、2 はのりさんの使い方に十分。実装の重さは軽いほど高い点。

- 採点は、見本を動かして数えた結果と、実装の分量の見込みから私がつけた。のりさんの実機での感触（§8）が出れば変わる。

## 8. 自問自答と、確かめていないこと

**本当にこれでよいか。**

- 数字だけ見ると、案はどれも現状よりよい。ただし見本の結果は短く作ってあり、現状は実際のデータで測った。比較は案に有利に偏っている。実装後、実データで測り直す必要がある。
- 案 A は見た目の通りの型（地図を土台に下から引き上げる）で、他のアプリにもある。そらばんでの理由は、現場の用事が「要るか要らないか 1 行だけ知る」ことに偏っているため。のりさんの使い方が変われば（スマホでも詳細を丁寧に読む）、案 B か C のほうが合う。
- 案 C は点数が高いが、のりさんの指摘「縦スクロールが長すぎる」の解決としては弱い。点が高いのは移行の軽さと免責の見えやすさによる。
- 案 A の 1 行の要約に、免責と同じ「参考情報」の語を入れたが、免責の全文は判定票を開かないと読めない。契約 C7（運営者・範囲・対象地域・免責は常に見える）に照らして、この扱いで足りるかは決めが要る。

**反対の見方。**

- 「入力が上にあると、片手で届かない」は案 A の弱点。逆に、地図を土台にすると、地図の長押しや現在地の取得が自然にできる。
- 現場で押すのは現在地ボタンだけで、他は事務所の PC で済む、という見方もできる。その場合、スマホは案 B のような「大きなボタン 1 つ＋要約の帯」で十分で、シートは要らない。
- PC は、3 ペインにすると右ペインの文章が窮屈になる。幅 22rem（352px）は、現状の結果の表（手続き表の 5 列）を入れるには狭い。見本は 2 列に縮めてあり、実装では表の作り直しが要る。

**確かめていないこと。**

- 実機（屋外・片手・手袋・日差し）での操作。
- 実際の地図（MapLibre）での操作。見本は絵で、ピンチ・回転・ドラッグとシートの競合は未確認。
- 実データの結果の長さでの、シート・タブ・折りたたみの中のスクロール。
- DIPS の項目名・並びの実物との照合（群の名前は案）。
- 契約 B4 の精度 100m 超の確認（見本では 150m で 1 回出る）を、実機の取得精度で試すこと。
