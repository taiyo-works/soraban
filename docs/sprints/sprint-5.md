# Sprint 5: 判定履歴への申請支援条件・進捗の保存／復元 ＋ 診断証跡ハッシュ連携

> 親文書：`docs/spec.md`（§6.3 証跡・§9 状態・履歴）
> 前提：Sprint 1〜4 が完了していること。

## 実装する機能

- **機能A：申請支援条件・診断サマリ・手続き完了状態の履歴（`history.ts`）対応**
  - `SavedCheck` を後方互換を維持したまま拡張し、申請支援の入力（飛行方法フラグ・空域フラグ・飛行予定日・立入管理措置・目視外補助者・マニュアル方針・完了済み手続き ID 群）および診断結果サマリ（カテゴリー・特定飛行有無・必要手続き数・診断証跡 ID）を保持できるようにする。
  - 飛行方法やチェックリスト完了状態を変更した際にも、直近の履歴エントリへ即座にパッチ保存（`patchHistoryDiagnosis`）し、リロードや履歴からの復元で再現できるようにする。
- **機能B：履歴からの完全復元（レースコンディション解消）と履歴リスト表示の拡充**
  - 履歴アイテムをクリックした際、位置・機体運航条件（`FlightContext`）に加えて申請支援の入力・マニュアル選択・手続き完了チェックをすべて復元し、明示的引数渡しにより React state 反映前の古いクロージャ参照（レースコンディション）を起こさずに即時再判定・再診断を実行する。
  - 判定履歴リストの各行に、保存されているカテゴリー（`I` / `II-A` / `II-B` / `III(Lv4)`）、必要手続き件数（および完了数）、飛行予定日、診断証跡 ID をモノスペースのメタ情報として表示する。
- **機能C：診断証跡 ID（`computeDiagnosisEvidenceId`）の決定論的ハッシュ化**
  - `/api/diagnose` で採番される `evidenceId` に、位置・規制判定入力だけでなく診断入力（選択フラグ集合・飛行予定日・立入管理措置・第三者上空・目視外補助者）および導出されたカテゴリー・手続き ID 群を正規化して SHA-256 ハッシュに含める（`ev_<16hex>` 形式）。
  - ベースとなる地点判定の証跡 ID も `checkEvidenceId` として併せて返し、監査・損保引受時に地点判定と申請支援診断の双方を追跡可能にする。

## スプリント契約（完了条件）

以下の全条件を満たした場合のみ、このスプリントは完了とする。

- [ ] `apps/web/src/lib/history.ts` の `SavedCheck` が申請支援の入力（`diagnosisInput`）と診断サマリ（`diagnosisSummary`）を保持でき、既存の `soraban:history:v1` データ（旧形式エントリ）が壊れずに読み込める。
- [ ] `patchHistoryDiagnosis` により、同一地点（または同一 `evidenceId`）の履歴エントリに対して申請支援条件・診断結果・手続き完了チェック状態（`completedProcedureIds`）・マニュアル方針（`manualChoice`）を更新できる。
- [ ] 履歴アイテムをクリックして復元した際、保存されていた飛行方法・空域フラグ・飛行予定日・立入管理措置・目視外補助者・マニュアル方針・手続き完了チェックがすべて UI に復元される。
- [ ] 判定履歴リストの各行に、診断カテゴリーや手続き件数（完了数含む）・飛行予定日が表示される。
- [ ] `/api/diagnose` が診断条件（フラグ・予定日・立入管理措置・導出手続き等）を含めた SHA-256 ベースの `evidenceId`（`ev_<16hex>`）を返し、条件が変われば異なる `evidenceId` が採番される。
- [ ] `history.ts` および診断証跡ハッシュに関する単体テストが追加され、`pnpm test --run` と `pnpm -r typecheck` がすべて通過する。
