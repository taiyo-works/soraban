## C. 単位: 案件 → 飛行計画の通報 → 当日の飛行日誌（1 本の流れ）

「ある時点で飛ばす企画・仕事（案件）」→ **飛行計画の通報**（エリア・日時・機体・操縦者・点検の確認）→ **当日の飛行日誌**（離陸・着陸・飛行時間、点検）、を 1 本で完結させる。
- 案件は**最小の親**から始める（名前、予定の期間、メモ。顧客・保険・作業報告書は後続）。1 案件に 1 つ以上の飛行計画。既存の計画は案件なしのまま動く（案件は任意）。案件の導入は **Sprint 20**（通報の完結 P1 と一体）。タブは Sprint 17 の「計画｜通報｜当日｜日誌」を、案件の画面の「案件｜通報｜当日｜日誌」へ広げる（案: 17 の枠を再利用）。【未確認】案件を飛行計画の親にするマイグレーションの影響範囲（R3 の旧 22 の設計を前倒し）。
- 通報と日誌は互いに依存しない（C-R9、C-J9）。案件はそれらをまとめて見る入口。

## 0. 要点

1. **最優先の目標**: 飛ばしたい時に飛ばすための手続き（飛行計画の通報）を、**利用者が DIPS の画面や外部の民間サービスを開かずに、このアプリの中で完結できる**こと。ただし**飛行計画の通報の受付・記録の本体は国の DIPS にある**。このアプリは DIPS に置き換われない。実現できるのは、アプリが DIPS の API 経由で、**利用者本人の DIPS 認証と最終確認のもとで**送信し、受付番号・結果・更新・取消をアプリに取り込む形（§13）。DIPS API は**クライアント ID の発行・仕様が前提で、申請状況は不明（※要再確認）**。API が使えるまでは、手動（本人が DIPS に出し、受付番号だけ取り込む）で運用する。
2. **想定ユーザー**: 国家資格（技能証明）を持つ操縦者と、すでに飛行許可・承認を取得済みの企業・操縦者。許可・承認の**申請**の支援は**やらない**（境界 §B。既存の申請支援は外す／直す。専門家確認まで外部へ提供しない）。
3. **主機能は 4 つ + 地図・計画**: (a) 飛ばす前の**飛行区域の確認**、(b) DIPS の**飛行計画の通報**、(c) **飛行日誌**（離陸・着陸の時刻、飛行時間、様式1〜3、確定・訂正、PDF/CSV）、(d) **機体の点検**（教則に基づく「異常なし／あり」）。加えて (m) **計画を作る地図とレイヤー表示の全国対応**（北海道〜沖縄、離島を含む）。それぞれが単体で最初から最後まで完結する（§2）。
4. **判定（法令・条例の適合の確認）は後回し。やる場合もまず山陰だけ。** 山陰以外の地域では適合を判定せず、**「この地域の規制は確認していません」と正直に示す**（「問題なし」「不要」と読ませない）。地図とレイヤーの表示、計画の作成は全国で行える（判定の対象と区別する）。
5. **「完璧に」「法に抵触せず」を保証する表現・機能は作らない。** アプリが保証すること、利用者と国の制度が担うことの線引きを契約と画面の文言に入れる（§13.3）。行政書士法・DIPS の利用規約との関係は専門家確認が要る（※専門家確認）。
6. **外部サービスの依存**（§15）: 通報に必須で外部に依存するのは、国の DIPS（置き換え不可）、ホスティング・DB・認証（Vercel・Neon・Neon Auth。民間）。地図の背景・住所検索は国の公的サービス（国土地理院）で、代替の自前化はデータ量とライセンスの面で現実的でない（要確認）。
7. **段階（§16）**: 第一段階＝山陰で、案件 → 通報（手動記録）→ 日誌・飛行時間 → 教則に基づく点検が完結し、**地図の範囲選択を作り込む**／第二段階＝DIPS の公開 API（FPR 系）で DIPS の画面を行き来せずに送信（認可は DIPS 側）／第三段階＝全国の地図・UI の磨き込み／第四段階＝山陰以外の判定、販売前提（専門家確認の公開ゲート）。**UI/UX とビジュアルは最上位の品質基準**で、Sprint 16 を前・中・後に分けて置く（§D、§7）。
8. **画面の長さ**は引き続き必須。計画の詳細は実測で 375×812 に約 11 画面分（9,285px）、通報内容は約 15 画面分（12,257px）。通報をメインにし、判定を別画面に分ける（`sprint-17.md`）。
9. **教則の一次資料は確認できていない**（この環境はネットワークが使えない）。リポジトリが記録しているのは「第5版（令和8年7月7日公表、7月14日適用）」だけで、点検の章・項目は無い。創作せず「※要再確認」とし、確認の手順を契約に書く（§2.4、§3.3）。
10. **番号**は README のルールで 17〜 を新しく付ける（§6）。**本文の §2〜§5・§14 の古い Sprint 番号の言及は、§6 の最終表を正とする**（読み替え: 区域確認 18→35、通報の完結 19→20、点検 20→21、様式3 21→22、確定・出力 22→23、補正 23→24、受け入れ 24→26、送信画面 25→27、全国 26〜30→28〜32、山陰外の判定 31→35）。
11. **提供元・免責・規約・取扱説明書・専門家確認**は `legal-info-plan.md` に 1 つにまとめた。最低限（提供元の表記、免責の整合、禁止語の検査）は第一段階（Sprint 18）。**専門家確認が出るまで外部へ提供しない**（公開ゲート）。
12. **ブランドビジュアル**（挿絵・アイコン・ロゴ）は別枠（`brand-visual-plan.md`）。Sprint 16 の挿絵の線画化は暫定。**フューチャーテックの公式のオレンジの値は未確認**（ユーザーに確認）。

## 2. 「完結」の定義（契約の完了条件）

「完結」とは、**他の機能・外部のシステムの助けなしに、利用者が最初の入力から最後の記録まで進め、あとから監査できる**こと。現場・事務所で、375×812（スマホ）と 1280×800（PC）で操作できる。

## 5. 判定への依存を外す案（検討の結論）

- **利用者の操作の依存**: 無い【確認】。計画の保存でサーバーが判定を実行してスナップショットを作る（見なくてよい）。確認は判定が古くても警告だけ（`ConfirmPanel` の `stale`）。通報の記録は計画が確認依頼済み（`status = active`）なら可能。判定の閲覧を要求する画面は無い。**契約で固定する**（`sprint-17.md` J-1〜J-3）。
- **データの依存**: 通報の記録は、その時点のスナップショット ID・証跡 ID を監査として保存する（12b）。利用者に見せなくてよい内部の根拠として残す。変えない。
- **要否の導出**: 通報の要否は判定の結論から導く（`reportRequirement`）。分からないときは要として扱う。判定が無い・古いときも通報の準備は止まらない。
- **区域確認（C-A）**: 判定を使うが、画面の主役は確認の記録。判定の詳細は補助。
- 【未確認】判定エンジンの失敗時に計画の保存が止まるか。止まるなら 19 で「判定が出なくても保存でき、通報の要否は『要確認（要として扱います）』」にする。

## 13. DIPS を置き換えられないことの線引き（最優先の目標との関係）

### 13.1 制度上の制約（正直に書く）

- **飛行計画の通報の受付・記録の本体は、国の DIPS 2.0 にある。** このアプリが DIPS に置き換わることはできない。北極星 §0.1.10 は「そらばんは、DIPS 2.0 API の利用が可能になるまで DIPS に送信しない」とし、`sprint-13.md` §3 は「通報も、利用者本人が DIPS のログイン画面で認可し、自分の名義で出す」「画面に『代行』『代理申請』を出さない。パスワードを預からない」としている【確認】。
- 実現できるのは、**アプリが DIPS の API 経由で、利用者本人の DIPS 認証と最終確認のもとで送信し、受付番号・結果・更新をアプリに取り込む**形。DIPS 側の API は、飛行計画の取得、飛行禁止エリアの取得、飛行計画通報の受付（新規・更新）の 3 つ（ガイドライン 1.10 版。`docs/references/dips-fpr-guideline-findings.md`）【確認】。**取消の API は記載が無い**（`sprint-13.md`。※要再確認）。
- **API の利用はクライアント ID の発行が前提**（申請から通知まで最大 1 か月程度）。**現状は未発行で、申請状況は不明（※要再確認）**。固定 IP の要否は、北極星 §0.1.6 と findings で食い違う（※要再確認）。1 つのクライアント ID を複数事業者で使えるか、利用規約も不明（Sprint 13）。

### 13.2 段階

| 段階 | 利用者が開く DIPS の画面 | アプリがすること | 前提 |
|---|---|---|---|
| **P1（手動）** 第一段階 | DIPS で通報する（DIPS の画面を開く） | 項目を DIPS の入力順に整えコピーできる。本人が出した結果（受付番号・日時）を記録する。期限・漏れ・更新・取消の記録を管理する | なし（12b にある） |
| **P2（API）** 第二段階 | **認可（ログイン・同意）の画面のみ**。送信内容の確認と最終操作はアプリ内 | 本人の認可のもとで送信し、受付番号・結果を取り込む。更新も API。**取消は API の記載が無く、DIPS の画面で本人が行い、アプリに記録する（※要再確認）** | クライアント ID、接続元の条件、利用規約の確認、専門家確認 |

「DIPS の画面を一切開かない」は、**認可が DIPS 側にあるため保証できない**（OIDC の認可は DIPS のログイン画面で行う。同意画面の省略の可否、トークンの有効時間は不明※要再確認）。目標は「通報の作業のために DIPS の画面を行き来しなくて済む」と読む。

### 13.3 何をアプリが保証し、何を保証しないか

| 区分 | 内容 |
|---|---|
| **アプリが保証すること（機能として検査で固定できる）** | 入力内容を DIPS の項目へ整える（対応表の版と確認日つき）。**本人の最終確認の操作なしに送らない**。送信・記録・訂正・取消を版と監査で残し、改ざんを検知できる（版の履歴・ハッシュ連鎖）。通報が必要な計画で未記録のものと期限を知らせる（**分からないときは要として扱う**）。飛行時間を 1 分単位で記録・集計する。確認していない地域を「確認していません」と示す |
| **アプリが保証しないこと** | DIPS が通報を受理すること、通報の法的な有効性、飛行が法令・条例に適合すること、区域データの網羅と最新性、許可・承認の範囲照合が最終の判断であること、通報漏れが無いこと |
| **利用者が担うこと** | 内容の真正、DIPS での認可と最終確認、飛行前の現地確認、許可・承認の条件の遵守、記録の申告の正しさ |
| **国・DIPS が担うこと** | 通報の受付、許可・承認の審査と付与、空域の指定と公示 |

画面の文言（案。専門家確認の対象）:「そらばんは、あなたが確認した内容を、あなたの DIPS アカウントの認可のもとで DIPS に送ります。受付と記録の本体は国の DIPS です。通報の受理や、飛行が法令に適合することを、そらばんが保証するものではありません。」
**出さない語**: 「完璧」「確実」「法に抵触しません」「問題なし」「安心して飛べます」「通報不要」「通報は不要」「代行」「代理申請」。契約の検査に入れる（17・18・19・25）。

### 13.4 専門家確認が要るもの（創作しない）

行政書士法との関係（官公署に提出する書類の作成・提出の代理に当たらない設計か。本人名義・本人の操作・最終確認・パスワードを預からない、が設計の前提。判断は※専門家確認）。DIPS の利用規約・API の利用条件（SaaS が API を使えるか、複数事業者での共用）。画面の文言（13.3）。

### 14.3 全国で揃える範囲と、揃えられない範囲

- **地図と計画のために全国で揃える（目標）**: 背景地図（済）、DID、空港等周辺（公式の制限表面データが得られる場合）、飛行禁止法の対象施設、公園・史跡（管理者の許可・条例の参考として）、緊急用務空域（案内）。データ源・ライセンスが確認できたものだけ。
- **網羅の限界（契約に入れる）**: 条例・自治体の施設・施設管理者の取り決めは、全国で網羅できない。収録していない地域・規制は、地図の上と区域確認で「**この地域の規制は確認していません**」と示し、「問題なし」と読ませない（C-A7、C-M2）。**収録の台帳**（地域×規制×確認日）を画面で見られるようにする（確認できていない地域を利用者に正直に見せる）。
- **判定との関係**: 判定（適合の確認）は**山陰に限定**。全国のレイヤーは表示と計画のため。山陰外では判定せず、レイヤーを見ても「確認していません」と示す。

### 14.4 配信方式と現実性（Vercel・Neon）

現状: 同梱の静的データ 1.5MB をアプリに入れ、DB は Neon の PostgreSQL（PostGIS）。全国化でデータ量が桁で増えるため、**配信方式を 29 で決める**。候補: ①都道府県ごとの静的ファイルを必要なときだけ読む、②ベクトルタイル（単一ファイルの形式を静的配信）を事前に作る、③PostGIS に入れて範囲で問い合わせる。Vercel の関数・静的ファイルの上限、Neon の容量・接続の制約は**実際の値を要確認**（創作しない）。推奨は①か②の静的配信（サーバー負荷と費用が小さい）。決める前に、DID を 47 都道府県分取得して実測する（29 の最初の作業）。

## 16. 最終の優先順位と段階

**軸**: 日本の制度で不備なく飛ばせること（境界 §B: 代替するのは飛行計画の通報の項目の入力・送信・記録だけ）。**品質基準の最上位は UI/UX とビジュアル**（§D）。

| 段階 | 目標 | 内容（番号は §6） | 外部待ち・ユーザー作業 |
|---|---|---|---|
| **第一段階** | **山陰で、案件 → 通報（手動記録）→ 日誌・飛行時間 → 教則に基づく点検が完結。地図の範囲選択を作り込む。境界・提供元・免責・禁止語を整える。取扱説明書の最小版** | 17 → 18 → 16-1 → 19 → 20 → 21 → 16-2 → 22 → 23 → 24 → 16-3 → 25 → 26（受け入れ） | 教則の PDF（Q3）、提供元の事実（Q-B）、オレンジの値（Q-A）、専門家への質問票の送付（Q-C）、**DIPS クライアント ID の申請（FPR 系 3 つ。並行して始める）** |
| **第二段階** | **DIPS の公開 API（FPR 系）で、DIPS の画面を行き来せずに送信**（認可は DIPS 側。取消は画面案内） | 13 実装 1〜3、27 | クライアント ID の発行（最大 1 か月程度）、民間の独自アプリでの利用可否の確認（Q-L6）、専門家確認（Q-L1） |
| **第三段階** | **全国の地図・計画、UI の磨き込み、ブランドの刷新**（判定は山陰のまま） | 28〜34 | データ源・ライセンスの確認、公式のオレンジ・ロゴ（Q-A、U6） |
| **第四段階** | 山陰以外の判定（県ごと）、**販売前提**（公開ゲート LG-1〜LG-7） | 35、36 以降 | 専門家確認、販売先（Q1） |

順序の理由: (1) 通報・日誌・点検の完結が先に価値を出し、自社業務を紙から切り替えられる。(2) 地図の範囲選択は通報の中心で、第一段階に入れる（全国の地図のデータは後）。(3) 外部待ちが長い DIPS の申請・専門家の確認・教則の確認を、**ユーザー作業として今から並行**。(4) UI/UX は 16 の 3 分割で、機能と並べて進める（二度手間なし）。(5) 全国のデータ作業は長期になりうるので別の流れ。(6) 判定の拡大は網羅の限界が大きく、最後。
