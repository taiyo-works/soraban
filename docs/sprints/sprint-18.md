## 0. 要点

1. **サービスの境界**: 代替するのは、DIPS の**飛行計画の通報**に含まれる項目（飛行日時、飛行エリア、機体、操縦者、点検の確認、日誌に関する項目）の**入力・送信・記録だけ**。許可・承認の申請、機体登録の申請、その他一切の申請の代行・支援をしない。使う外部 API は FPR（飛行計画の通報）系だけ。FPA（許可・承認）と機体情報の API は使わない（DIPS 申請書の案も、機体情報一覧取得 ×、許可・承認情報取得 ×、許可・承認申請受付 ×、飛行計画情報取得 〇、飛行禁止エリア情報取得 〇、飛行計画通報受付 〇。`docs/references/dips-api-application-draft.md` §5【確認】）。
2. 現状には、境界の外に見える機能・文言がある（§2 の棚卸し）。**公開の `/` の申請支援（手続き診断、申請書類の PDF、DIPS プリフィル、飛行マニュアルの骨子、申請支援の保存）**、運航管理の**「許可・承認の申請済み」の記録と「許可・承認を申請する」の次にやること**、**申請期限のカレンダー**などが該当しうる。
3. このスプリントは、**棚卸し → 分類（外す／直す／残す）→ 実施 → 検査（禁止語・限定語）**を行い、あわせて**提供元の表記と免責の文言の整合**（`legal-info-plan.md` の最小）を入れる。外すものは、データを消さず（版の履歴を壊さず）、画面と導線から外す。
4. 分類は**安全側**（疑わしいものは外すか、専門家確認まで止める）。確認の結果で戻せるように、削除でなく**無効化（フラグ）**を基本にする。

## 1. 境界の定義（契約の冒頭）

| 区分 | 内容 |
|---|---|
| **やること（境界の内）** | 飛行計画の通報の項目の入力・整形（DIPS の入力順）、本人が DIPS で認可して出す（P1 手動記録、P2 API）、受付番号・結果・更新・取消の記録、期限と漏れの管理。それに関わる計画（日時・エリア・機体・操縦者・点検の確認）、当日の飛行日誌（離陸・着陸・飛行時間、様式1〜3）、機体の点検（教則）、地図の範囲選択 |
| **やらないこと（境界の外）** | 許可・承認の申請の作成・提出・代行・支援（書類のドラフト・プリフィル・申請の進行管理を含む）、機体登録の申請、その他の申請。DIPS 以外のサービスを経由した手続き |
| **使う API** | DIPS 2.0 の FPR 系: 飛行計画通報受付、飛行計画情報取得、飛行禁止エリア情報取得（ガイドライン 1.10 版。`dips-fpr-guideline-findings.md`）。**条件**: クライアント ID の発行（**API は未申請**。申請して ID と仕様書を得るまでは手動の運用 P1）、利用規約・民間の独自アプリでの利用可否（findings §7: 記載なし。判断不能）、**認定 USP の位置づけ**（`dips-fpr-screens.md` §2。専門家確認。第二段階のゲート）→ ※要再確認 |
| **使わない API** | FPA（許可・承認の取得・申請受付。realm `drs-req`）、機体情報一覧取得 |
| **取得済みの許可・承認の扱い** | 利用者が自分で取得した許可・承認の**情報を控えとして登録**し、通報の項目（許可・承認の情報）に使う。**申請ではない**。DIPS からの取り込み（FPA）は**しない**（手入力のまま） |
