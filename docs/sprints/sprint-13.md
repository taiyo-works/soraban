## 3. 飛行計画通報 API

### 目的

利用者が自分の DIPS アカウントで認可したうえで、飛行計画の取得、飛行禁止エリアの取得、飛行計画通報の受付（新規と更新）を、既存の通報ゲートウェイの奥に接続できる形にする。資格情報が無い間はモックだけで開発と試験を終える。

### 根拠（ガイドラインに書いてあること）

正は `docs/references/dips-fpr-guideline-findings.md`（ガイドライン 1.10 版、2026-08-26、全 75 頁を読んだ記録）。外部メモ `dips-api-notes-external.md` は原本と未照合の調査であり、食い違う点はガイドライン側を優先する。

- 認証は OpenID Connect の Authorization Code フロー。realm は `drs-fpl`。トークン要求に `client_secret` を含める。トークン交換はサーバー間通信。
- API のホストは、検証 `www.stg.uafpi.dips.mlit.go.jp`、本番 `www.uafpi.dips.mlit.go.jp`。認証系のホストは別（本番 `www.dips-reg.mlit.go.jp`、検証 `www.stg.uafp.dips.mlit.go.jp`。検証は `uafp` と `uafpi` で綴りが違う。原文のまま分ける）。
- 対象 API は次の 3 つ。いずれも `Authorization: Bearer`。
  - `POST /api/flight-plan/search`（飛行計画の取得）
  - `POST /api/flight-prohibited-area/search`（飛行禁止エリアの取得）
  - `POST /api/flight-plan/register`（飛行計画通報の受付。`flightPlanId` が無いときは新規、更新時は必須）
- 本番環境での性能負荷試験や、本番運用に影響する異常系試験はガイドラインが禁止している。検証と本番の URL をコードで取り違えない。
- クライアント ID は未発行。申請から通知まで最大 1 か月程度、とガイドラインにある。申請は国土交通省航空局への利用者作業であり、本スプリントの完了条件にしない。

### 範囲

- 既存の `packages/dips`（Sprint 12b。手動アダプターと模擬アダプター。DIPS へは送らない）の奥に、上の 3 API のポートを足す。画面と保存の形は、手動記録のときとモックのときで同じにする。
- 環境名（検証 / 本番）を設定で一つだけ選ぶ。ホストの定数は環境ごとに分け、テストはモックの応答だけを見る。テストから本番ホストへ HTTP を出さないことを、単体テストで固定する。
- 資格情報（client id、client secret、redirect URI）が無いときは、実アダプターを選べない。モックだけが動く。
- 新規と更新だけを扱う。更新は既存の飛行計画 ID を渡す。
- 秘密はブラウザに置かない。`client_secret` と refresh token はサーバー側だけ。

### 範囲外

- 取消・削除の API。ガイドラインの 3 API に無く、取消のエンドポイントは記載なし。ポータルの説明（`https://www.dips-reg.mlit.go.jp/`、2026-10-28 閲覧）は、ウェブ画面で開始日時までに変更・削除する、と書いている。API で消せるかは不明。既存の手動の取消記録は残す。
- 飛行許可・承認（FPA、realm `drs-req`）の接続。
- 本番および検証環境への負荷試験。検証環境への負荷の可否はガイドラインに記載がない。安全側として、どちらの実環境にも負荷をかけない。
- クライアント ID の申請そのもの、固定 IP の回線契約、本番の Neon と Vercel への秘密の投入。
- 行政書士の独占業務。許可・承認の申請をそらばんが代理しない。通報も、利用者本人が DIPS のログイン画面で認可し、自分の名義で出す。画面に「代行」「代理申請」を出さない。パスワードを預からない。

- 北極星 §0.1.6 は「DIPS は接続元 IP の登録が必要。通信は固定 IP の中継。クライアント秘密は中継に置く」としている。ガイドライン 1.10 版の 75 頁には、固定 IP・IP 制限・クライアント証明書の記載が無い（findings §3）。外部メモと findings はこの点で食い違う。本契約はどちらも消さない。実アダプターの前に、航空局へ要否を確認する。確認が済むまで、Vercel から本番 API を呼ばない。

## 4. 判定履歴のサーバー保存

### 目的

公開画面の判定履歴は、いま端末の中だけにある。監査に耐えるよう、判定の結果を追記専用でサーバーに残し、同じ利用者が別の端末でも一覧を読めるようにする。既存の診断証跡 ID を、その行の鍵にする。

### いまサーバーにあるもの（コードで確認した事実）

- `evidence_log`（マイグレーション `0002`、`0003`、`0009`）: 地点判定 1 回が 1 行。主キーは `evidence_id`（`ev_` と SHA-256 の先頭）。座標、規制 ID、規制ごとの状態、エンジン版、データセット、4 段の `verdict` を持つ。`/api/check` の応答のあと、`DATABASE_URL` があるときだけ書く。`EVIDENCE_LOG=off` なら書かない。IP は持たない。利用者 ID の列は無い。
- 申請支援の証跡 ID は、飛行計画の判定スナップショット（`judgement_snapshots.diagnosis_evidence_id`）に保存される。コメントは「`evidence_log` には書かれない」。スナップショットの `result` は `runDiagnosis` の応答そのもの。これは運航管理で計画を保存したときだけで、公開画面の判定だけでは行ができない。スナップショットは追記専用（更新・削除をトリガーが拒む）。`content_hash` は DB が決める。
- `record_versions`（`0006` 以降）: 運航管理の台帳（機体、計画、許可、事故など）の版。ハッシュ連鎖の追記。判定履歴そのものではない。
- 公開画面の履歴（`apps/web/src/lib/history.ts`）: `localStorage` の `soraban:history:v1`。最大 50 件（`MAX_ENTRIES`）。古いものから捨てる。保存するのは再現の手がかりと診断の要約であり、診断の全文ではない。コメントのとおり、サーバーの `evidence_log` とは別である。端末をまたがない。

### 認証と利用者

- 運航管理は `OPS_ENABLED=1` かつ `AUTH_PROVIDER` が `neon`（Neon Auth）または `test`（CI 用）のときだけ開く。実装は `apps/web/src/server/ops/auth/`。組織とメンバーは Sprint 10（`0004`〜）にある。
- 既定では `OPS_ENABLED` が無効で、`/ops` と `/api/auth` は 404。本番で Neon Auth が有効かどうかは、リポジトリの設定からは分からない。不明。
- 公開の `/` はログイン不要。この画面の履歴には、利用者 ID が無い。

### 範囲

- 新しい追記専用の表を 1 つ足す。行は消さない。更新も削除もしない（既存のスナップショットと同じ考え方）。
- 行は、診断の証跡 ID、地点判定の証跡 ID、エンジン版、判定時刻、結論、要約、結果の JSON、入力の正規化、`content_hash` を持つ。ハッシュの材料に診断の証跡 ID を含める。アプリが送ったハッシュは使わず、DB が決める。
- ログイン済みのメンバーには `member_id` を付ける。未ログインの公開判定は、利用者に紐づかない行として残すか、残さないかを実装の前に決める（未決）。端末の 50 件は、移行が終わるまで残す。
- ログイン済みの一覧 API は、そのメンバーの行だけを新しい順に返す。50 件で切らない。
- 他の組織の行は返さない。

### 範囲外

- 未ログインの履歴を、端末の識別子だけで横断同期すること（利用者を特定できない）。
- 既存の `evidence_log` の列の意味を変えること。地点判定の書き込みは残す。

## 6. GitHub Actions

### 目的

CI が GitHub 上で動いていることを、ワークフローと実行履歴で確認し、記録する。失敗した 12h のブランチは直さない。

### 確認した事実（2026-10-28）

- ワークフローは `.github/workflows/ci.yml`。`pull_request` と `main` への `push`。`docs/**` と `*.md` だけの変更では動かない。ジョブは verify（typecheck / lint / test / build）、e2e（Playwright）、db（PostGIS 18 のサービスコンテナ、`pnpm test:db` と運航管理の E2E）、smoke（外部サービス。失敗しても全体は止めない）。
- `main` の `6b82554`（PR #42 のマージ、2026-10-28T04:20:31Z）の実行 `40631775597` は成功。
- ブランチ `feat/12h-pr3b1-ops-v2` の実行 `40724764704`（2026-10-28T16:19:05Z、SHA `6f5874952b854be9cfba1382d90346deb22dc6f9`、PR #43）は失敗。verify と smoke は成功。失敗は db と e2e。
- db: `REQUIRE_DB_TESTS=1` で `TEST_DATABASE_URL` を外して失敗することを見るステップは、期待どおり失敗して通過している。そのあとの `pnpm test:db` は、テストファイル 9 件が passed のあと、未処理エラー 4 件で終了コード 1。エラーは PostgreSQL `57P01`（`terminating connection due to administrator command`）。`packages/db/src/test-db-helpers.ts` は使い捨て DB を `drop database ... with (force)` で消す。FORCE は接続中のバックエンドを切る。切られた接続のエラーがテストプロセスで未処理になった、とログから読める。どのファイルの drop が 4 本を切ったかは、ログにファイル名が残っておらず不明。この失敗の時点で、あとの E2E-DB のステップには進んでいない。
- e2e: `e2e/sprint12h-pr2.spec.ts` 427 行付近。「地図をクリックして地点を選ぶと、結論が画面に入る」。`pos.top >= 0` が失敗。受信値は、Pixel 5（393×727）で約 -5.9 と -7.3（再試行も失敗）、iPhone SE 第 3 世代（375×667）で約 -10.4（再試行は成功）。結論の上端が画面の上にはみ出している。

## 7. 使い心地

### オーナーの意図（原文のまま）

- 硬すぎず柔らかすぎず、仕事でありながら親しみやすさがあり、みんなが使っていて心地がいい感じ
- 操作に迷わない
- 必要な情報をいつでも読み出せる
- ごちゃごちゃしすぎない
- アイコンの位置、画面構成、色合いに改善余地があればどんどん改善する
- 昨今のアプリのベンチマークとして、世の中のドローン・飛行管理系アプリのユーザビリティを調査し、良い点を取り入れる

良い点は、一般的な操作の原則として取り入れる。他社の文言、配置、ロゴ、画像、アイコン、名称、特徴的な見た目は写さない。調査の表は `docs/design/sprint-13-ux-benchmark.md`。

### 既存の方針との関係

合わせるもの:

- 余白を広く、情報を詰め込まない（北極星 §4.3「余白は機能」、デザインシステム v2 の帯）。
- 操作の色は 1 色。判定の色は結果だけに使う（v2 草案 §3。現行の正は v2 で、アクセントは橙 `#F89B48`）。
- 装飾のための動きや、動画背景を足さない（v1 の決定 8、v2 は動き 2 種類まで。CLAUDE.md の designer は AI スロップを排除する）。
- PC とスマホは同じ仕様の 1 本（デザインシステム v1 の原則 1、v2 も継続）。
