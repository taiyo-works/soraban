## 4. 順序の判断：② と ③ のどちらを先に出すか

**推奨：② を先、③ を直後。メニューの変更は ③ に入れる。**

理由（事実と推測を分ける）：

1. **実機で確認できるのが ② だけ**【確認：`sprint-12h.md` §11、P3-17】。Preview では `/ops` にログインできない見込み（Neon Auth が未設定。【未確認】）。のりさんが片手・屋外で見る確認は、② ならスマホで URL を開くだけでできる。
2. **v2 のトークンと部品を、1 回で入れて確かめられる**。③ はその部品を使う側で、先に ② で試した形を使う方が手戻りが少ない【推測】。
3. **③ は `/ops` が本番で 404（`OPS_ENABLED` 無効）のため、公開への影響がない**【確認：`sprint-12h.md` §8.3】。順番を後にしても、公開の利用者には損がない。
4. **標準フローは並行実行を禁止している**（`CLAUDE.md`）。大きい ③ を先にすると、② の実機確認が先延ばしになる【推測】。

**背骨が運用の流れになったことの影響**：北極星では背骨は「計画→点検→日誌」なので、運用の画面（③）の重みが増した。それでも ② を先にする理由は上のとおり。**反対の見方も成り立つ**：段階 0（社内の点検業務）を早く始めたいなら ③ が先。ただし段階 0 には本番で `/ops` を開ける設定（`OPS_ENABLED`、ログインの設定）が要り、これは見た目とは別の作業で、現状は未確認【未確認】。だから ③ を先にしても、段階 0 がすぐ始まるとは言えない。

**メニューの変更を ③ に入れる理由**：

- 下タブから「判定」を外す（のりさん決定）と、スマホのログイン済みの利用者は、ホーム上部の「現在地で判定」「場所を調べる」のピルからしか判定に行けない。**ピルが出るのはホーム（`/ops`）で、それは ③ の画面**。メニューだけ先に変えると、判定への入口がなくなる期間ができる【推測。構成は `design-system-v2-draft.md` §7】。
- 下タブに「点検」を足すには、`ops-nav-model.ts` の項目・現在地の判定・戻りリンクの表・テストを一緒に変える（§9）。③ の「運航管理の置き換え」と同じ範囲。
- ② は、ログイン済みの `/` で今の 5 項目（ホーム／判定／計画／日誌／登録）を**色だけ** v2 にして出す。

**前提作業（のりさんの承認が要る、docs だけ）**：`origin/design/warm-compare` の docs を main に入れる。これで generator が見本・トークン・検査を main から読める。docs だけの変更は CI を動かさない（`ci.yml` の `paths-ignore: docs/**, **/*.md`）【確認】。入れない場合は、generator が `git show origin/design/warm-compare:<パス>` で読む（動くが、ブランチが消えると失う）。**推奨：入れる**（実行は私＝オーケストレーターが、承認後に行う）。

## 5. 根拠の表示を ② に入れるか

**推奨：② に「最小の根拠欄」だけ入れる。それ以外は別 PR。**

北極星の約束は「どの画面でも、結論の根拠（法令・条例・判例、版、確認日、確認の状態）がたどれる」こと（§0.1.11）。ただし今のデータには、約束の全部を出すための項目がない（§3）。無理に出すと、画面が持っていない事実を作ることになる。

### 5.1 ② に入れるもの（既存データに載っているものだけ）

規制ごとのカード（`regulation-card.tsx`）で、すでに出ている次の項目を、「根拠」という 1 つのまとまりに整えて見せる。**値も出どころも増やさない**。

| 見せるもの | 出どころ（今あるもの） | 見出しの語（案） |
|---|---|---|
| 法令・条例の名称と条・項 | 規制の題名（`title`）。題名に条・項が書かれているものだけ。構造化はしない | 題名のまま |
| 区分（国・県・市）と法的な重さ | `source`、`legalTier` | 既存の語 |
| 使用データ（名前・基準年・確認日） | `datasets[]`（`regulation-datasets`） | 「使用データ」「確認日」 |
| データの版 | 台帳の `version`。`getDataset(id)` で引く（`apps/web` 側だけで足りる見込み。**エクスポートされているかは generator が確認**【未確認】）。引けなければ出さない | 「版」 |
| 反映済みの改正 | `amendments[]`（名称・施行日・リンク） | 「反映済みの改正」 |
| 出典のリンク | `regulation.url` | 「出典」 |
| 条文を確認した日 | `confidence.verifiedAt` | 「条文確認」（既存） |
| 確からしさ（高・中・低） | `summarizeConfidence`。**「確認の状態」と呼ばない**（区域の位置と条文の読み取りの精度を表す別のもの） | 「確からしさ」（既存） |

守ること：

- `data-testid`（`regulation-datasets` ほか）と文言は変えない。見た目と並べ方だけ変える。
- 「確認済み」「要確認」「未確認」の語を**出さない**（付与の規則も、確認者の記録もまだないため。Q-24 で grep）。
- 判例・裁判例の語や欄を**出さない**。空の「参考」欄も置かない（北極星の決定 4：まず公開裁判例の件数と内容を調べてから、載せるかを決める）。
- 判定不能のカードの言い回し（「データ未整備」）は変えない（E2E が固定。§3）。

### 5.2 別 PR にするもの（理由）

| もの | 別にする理由 |
|---|---|
| 確認の状態（3 段階）と付与の規則（例：確認日が 90 日超なら要確認。提案書 §3.5） | 台帳の項目と規則を新しく決める必要があり、`packages/regulations` を変える。② の「判定の部品は変えない」（K3）と衝突する。誰が何を確認済みと言えるかは、法務の確認を含む（北極星の決定 7） |
| 条・項の構造化、引用文言、本文のハッシュ | 同上。条文ごとの台帳をつくる作業 |
| 判例の「参考」欄 | まず件数と内容の調査（決定 4）。結論には使わない |
| 「収録なし」への言い換え（「判定不能（データ未整備）」から） | 文言が packages と E2E に固定されている。言い換えると意味が少し変わる（判定不能＝データなし、と同じとは限らない）ため、台帳の整理と一緒に決める |
| 計画・日誌に当時の版を保存する | DB と履歴の変更。③ より後 |

この別 PR は、仮に「根拠の台帳」と呼ぶ。② のあと、③ と並べて順序を相談する。

### 6.5 現在地での判定と 100m の確認

12h §1・P2-12〜P2-14 を引き継ぐ。要点：

1. 開いただけでは位置を要求しない。ボタンを押すまで通信しない（100m 超の確認の前も）。
2. 押す → 位置を 1 回取得 → 成功したら続けて判定。精度 100m 以内は確認なし。100m 超は「精度 約 N m です。この位置で判定しますか」を 1 回。
3. 送るのは緯度・経度（小数 6 桁）だけ。精度・時刻・方法は要求本文に入れない。追跡・自動の再取得をしない。
4. 取得に失敗したら判定せず、従来の失敗表示（地点と前の結果は変えない）。
5. 結果に「現在地（精度 約 N m）」を添える。精度は整数の m の表示だけで、判定には送らない。
6. `CURRENT_LOCATION_PRIVACY_NOTE` を新しい挙動の文にする。**この定数は計画の作成画面でも使う**（§3）ので、文が `/ops` でも通るか確認する。

### 6.7 ホームのピルから来る入口

ホーム（③ で作る）の「現在地で判定」「場所を調べる」は、どちらも `/` に行く。② では `/` が次の 2 つの入口を受ける。

| URL | 開いたときの状態 |
|---|---|
| `/?start=here` | ページは通常どおり開く。「現在地で判定」ボタンにフォーカスを移す。**位置の要求はしない**（押すのは利用者） |
| `/?start=search` | 住所の入力欄にフォーカスを移す |

- 既定の理由：「開いただけでは位置を要求しない」（§6.5 の 1）を守るため。ピルを押した後にもう 1 回、ボタンを押してもらう（1 回余分）。
- もし「ピルを押したら、すぐ現在地を取りに行く」にしたいなら、§6.5 の 1 を変えることになる。その場合は、のりさんの決定と、`sprint9.spec` の期待の見直しが要る。今は**既定のまま**にして、③ のホームのピルを実機で見たときに判断する。
- この入口は、パラメータがなければ今と同じ表示。`/` の `<title>`・noindex・OG は変えない。

## 7. 暗い表示と Web フォント

### 7.1 暗い表示

**推奨：② の前に、v2 の暗を別に定義する（文書とコントラスト検査だけ。アプリは変えない）。② ではその暗に対応して出す。**

- 事実：今の `/` は OS の暗い設定に対応している【確認：`globals.css` 66・388 行、`sprint11b.spec` の暗の検査】。v2 のトークンは暗が未定義【確認：`soraban-tokens-v2.css` の冒頭コメント、`design-system-v2-draft.md` §1・§8 の 1】。v1 の暗は `soraban-tokens.css` 133 行以降にある。

- 定義する範囲：v2 §8 の 1「面が 3 色交互のままか、暗では 2 色か」の決定、各トークンの暗の値、検査（通常・現場の 2 通りに暗の 2 通りを足す。件数は決まってから）、橙の面の上の墨の文字、判定 5 段の暗での値。担当：designer（planner が仕様を渡す）。成果物：`docs/design/tokens-v2/` の更新。**のりさんが見本の撮影で確認してから** ② の実装に入る。
- 地図タイル（国土地理院の淡色）は暗でも明るい。まぶしさの確認は実機（§11 の 7）。【未確認】
- 代案（推奨しない）：② は明だけで出し、暗は後日。理由は上のとおり後退になるため。

### 7.2 Web フォント（Noto Sans JP、Plus Jakarta Sans）

事実：今は `next/font/google` で Fraunces・IBM Plex Sans JP・IBM Plex Mono を読み込み、`subsets: ["latin"]`、`display: "swap"`（`layout.tsx`）。Next の資料では、`subsets` に書いたものだけが先読み（preload）され、既定の `display` は `swap`、Google のフォントは CLS を減らす自動のフォールバック（`adjustFontFallback`、既定で有効）が付く【確認：font.md の `subsets`・`display`・`preload`・`adjustFontFallback`】。

方針（案）：

| 項目 | 方針 | 理由 |
|---|---|---|
| 読み込み方 | `next/font/google`。依存は足さない（K4） | 今と同じ仕組み。ビルド時に取得して自前配信になる |
| Plus Jakarta Sans | `subsets: ["latin"]`。数字・英字だけに使う。太さは必要な 2 つ（本文 500、強調 700）から始める | 小さい。latin だけを先読みして、数字がずれにくい |
| Noto Sans JP | 太さは 400・700 の 2 つから始め、500 が必要な箇所があるかを見て足す。**日本語の分割ファイルは先読みしない** | 日本語は分割ファイルが多く、先読みすると転送量が増え、LCP が遅れる【推測】 |
| `display` | まず `swap`。CLS が出たら、Noto Sans JP だけ `optional`（読み込みが間に合わなければ、その表示では端末の字体のまま）を試す | `optional` は文字のずれが原理的に出ないが、初回は字体が違って見える。その場合の見え方をのりさんに見せてから決める |
| 字体の指定 | Noto Sans JP の次に端末の日本語ゴシックを並べる（今の v1 の指定と同じ考え方） | 読み込み前後の見た目の差を小さくする |
| 測る | main と同じ方法で、375px の `/` のフォント転送量・LCP・CLS を測り、PR に書く（Q-17） | 合格条件は「悪化させない」 |

確認が要ること【未確認】：Noto Sans JP の分割ファイルの数と大きさ、`next/font` が日本語の分割をどう配るか、実際に 375px で取得されるファイル数。**generator が `next build` の結果と通信の記録で測って PR に書く**。今の IBM Plex Sans JP も同じ仕組みなので、main との比較で足りる。

## 13. のりさんに決めてもらうこと（6 つ。それぞれ推奨つき）

1. **順序とメニューの置き場**：② を先、③ を直後にし、下タブ 5 つ・ホーム上のピル・PC 6 項目は ③ に入れてよいか。**推奨：はい**。理由：実機で確認できるのは ② だけ。ピルが出るホームは ③ の画面で、メニューだけ先に変えると判定への入口がなくなる（§4）。反対の見方：段階 0 の社内運用を急ぐなら ③ 先だが、そのためには本番で `/ops` を開ける設定が別に要る（未確認）。
2. **根拠の表示の範囲**：② は「今ある出典・確認日・改正・確からしさ」を整えて見せるだけにし、確認の状態・条・項の構造化・判例の欄・「収録なし」の統一は別の PR にしてよいか。**推奨：はい**。理由：今のデータにその項目がなく、足すと判定の部品側（`packages/regulations`）を変える。誤って「確認済み」と見せるリスクも避けられる（§5）。
3. **暗い表示**：② の前に、v2 の暗を別に定義してから出してよいか。**推奨：はい**。理由：今の `/` は暗に対応していて、暗を落とすと後退になる。定義は文書と検査だけで、アプリは変わらない（§7.1）。代案：② は明だけで出す（非推奨）。
4. **レイアウト**：新しい見本の「縦に積む（PC は 2 カラム）」を採用し、12h の「地図が土台のシート」と「PC の 3 ペイン」を取り下げてよいか。**推奨：はい**。理由：新しい決定が優先で、実装が小さく、地図の操作とシートのドラッグの競合がない。失うもの：スマホで地図が常に画面の土台にあること（§2.2）。
5. **挿絵**：トップの挿絵は v2 の独自 SVG にして、今の Firefly の PNG（`hero-drone.png`、約 220KB。外形が DJI の機種に似ていると承知のうえで採用した経緯）を `/` から外してよいか（ファイルの削除は ④）。**推奨：はい**。理由：見本の絵と合う、画像の転送がなくなる、機種に似た外形の問題が小さくなる。
6. **現場モードの下タブ**（未決。最終回答待ち）：**推奨（既定）：出さない現行のまま、「ホームへ戻る」だけ**。見本（`field.html`）の 5 タブは採用しない。② には影響せず、③・④ の契約で扱う。理由：現場は誤タップを減らす設計（12g-1b A11）で、見本が現行実装と食い違う。

**契約の既定として入れたが、のりさんの目に入れておくこと**：①ピルから `/` に来たとき、もう 1 回ボタンを押してもらう（位置を勝手に取らないため。§6.7）。②層の一覧の「準備中」の使い方は、12h §12 の 4 の推奨のまま（未回答）。③この契約の数値（JS +6KB など）は案で、main の測定値が出てから了承を取る。
