## 2. 12h ④・PR #47・明るい統一の組み合わせ（推奨と理由）

### 2.1 事実【確認】

- PR #47（③b2b）は `main` 848b946 から分岐。21 ファイル、+710／−283。現場に `.ops-v2` を当て、現場の 2 画面だけ `<html data-mode="field">` を付ける（`FieldModeMark`）。事故・通報・判定の履歴・現場を `.opx-*` に移し、`ops-v2-conventions.test.ts` に b2b の 16 ファイルの「旧トークン・直書き 0」を足す。E2E-DB `sprint12h-pr3b2b-db.spec.ts` 6 件。既存の E2E の期待値は変えていない（`docs/evaluations/12h-pr3b2b-test-changes.md`）。
- 作業ブランチ（S14・S15）と #47 が両方触るのは **`field-client.tsx`**（作業ブランチ側 +691／−19、#47 側 81 行の変更）と `plans/[id]/report/page.tsx`（作業ブランチ側 2 行）だけ。ほかの 19 ファイルは作業ブランチで変わっていない。
- #47 は S14・S15 が足した現場の部品（書類・手続き、現場状況、状態の帯、先読み）と `offline-shells.tsx`・`pwa-register.tsx` を知らない。#47 の T-2（`B2B_FILES` に `field-client.tsx` を含む「旧トークン 0」）は、S14・S15 の上に載せると **S14・S15 が足した旧い名前で落ちる**【推測：grep の 32 行の多くは S14・S15 の追加】。
- 12h ④（`sprint-12h.md` §7、P4-1〜P4-18）は未着手。中身の半分（旧トークンの削除、旧見本の削除、現場の寸法、実機の日差しと色覚、アイコン）は、明るい統一とそのまま重なる。残り（起動画面、メニューのふわっと、等高線）は v2 草案の「動きは 2 種類だけ」「挿絵はトップだけ」で既に置き換わっている。

### 2.2 推奨

| 順 | やること | 担当の流れ |
|---|---|---|
| 1 | **Sprint 14・15 を main へ**（作業ブランチの PR。両方とも評価合格） | オーケストレーター（git 操作） |
| 2 | **PR #47 を 1 の上に載せ直す**。`field-client.tsx` の衝突を解き、#47 の T-2 が通るよう、**S14・S15 が `field-client.tsx` に足した部品も `.opx-*` に移す**（#47 の契約 `sprint-12h-pr3b2.md` の作法のまま。新しい見た目の判断はしない）。評価して マージ | generator → evaluator（designer は不要。見た目の新しい判断が無いため） |

**理由**

1. **#47 を捨てない。** 現場に v2 の枠と `data-mode="field"` を付ける構造の仕事は、明るい統一の前提そのもの（トークンを替えたとき現場まで効くのは、現場が `--sb-*` を読んでからだけ）。#47 は既に評価できる形にある。16 に吸収すると 16-2 が #47 の 21 ファイル分ふくらみ、評価の単位が大きくなる。
2. **#47 を S14・S15 より先に main へ入れない。** 先に入れると、評価合格済みの S14・S15（現場の 691 行）の側で衝突を解くことになり、合格した側を作り直す。小さい #47 を載せ直す方が危険が小さい。
3. **12h ④ を単独で出さない。** ④ を今の値（ベージュ帯・暗は OS）で仕上げてから 16 で値を替えると、現場の撮影・実機の確認（P4-6）を 2 回やることになる。実機の日差しの確認は 1 回にまとめたい（S14 F-1・S15 G-3 も同じ機会と書いてある）。
4. **16 を #47 より先にしない。** 16-1 のゲート（見本と Preview を実機で見る）で、現場の実画面が v2 になっていないと、いちばん日差しの下で使う画面を見ずに配色を決めることになる。

**代替**（ユーザーが #47 を急がない場合）: #47 を閉じ、その差分を 16-2 の最初のコミットとして取り込む。評価は 16-2 でまとめて行う。16-2 の規模が約 2 倍になるので推奨しない。
