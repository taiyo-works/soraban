## 2. 分け方：PR は 2 本（推奨）

| PR | 内容 | 本番への影響 | CI |
|---|---|---|---|
| **A**（12g-1b-A） | 試作ブランチの内容（紙面のトークン・部品・見本）＋ **`/ops` の骨組み**：名称、左メニュー、下 5 タブ、利用者メニュー、ホーム、登録、日誌への事故の移動、戻りリンクの統一 | **なし**（`/ops`・`/ops/design` は本番で 404。`/` は未ログインの DOM を変えない） | 1 回 |
| **B**（12g-1b-B） | **判定画面 `/`**：PC の 3 ペイン、概要の帯、現在地の即判定、ログイン済みの `/` に新しいメニュー | **あり**（公開ページ） | 1 回 |

**この分け方の理由**

- CI の消費：PR 1 本あたり verify＋e2e＋db の 3 ジョブ（各 20〜30 分上限）。3 本に細分すると約 1.5 倍になる。2 本なら、本番に影響する変更（B）だけを単独にでき、A は影響がないので大きくまとめてよい。
- リスク：B を A と分けるのは、公開ページの変更を単独で戻せるようにするため（マイグレーションが無いので、PR の revert 1 回で戻る）。Vercel のプレビュー（GitHub Actions を消費しない）で、のりさんが PC とスマホの実機を見てからマージする。
- A に試作ブランチを含める理由：紙面への切り替えは、実画面の `/ops`（本番で見えない）に初めて適用されるため。PR を分けると、同じ差分が 2 回 CI を通る。
- 試作（`/ops/design?view=menu`）と `e2e/sprint12g-ux2.spec.ts` は、A では残し（のりさんの確認用）、B で削除する。名称・ハンバーガー無しなどの検査は、A の実画面の E2E に移す（検査の対象は減らさない）。

**push の回数を減らす進め方（全 PR 共通）**

1. generator → designer → evaluator のループは、**手元で回し切る**。evaluator の不合格の修正もここで済ませる。
2. 手元で §10 の検査をすべて通してから **PR を作る**。それまではブランチに push だけしても CI は動かない（実際に push するのは、バックアップが要るときだけ）。
3. PR を作った後の修正は、まとめて 1 回の push にする。
4. この環境では E2E-DB が動かせないため、**db ジョブが CI で初めて動く**。§6.2 の「影響を受けるテスト」を、push 前に grep で全部直しておく。それでも落ちたときのために、push は最大 2 回までを見込む。

## 5. 「近づく期限」（ホーム）

| 項目 | 出どころ（既存の列） | 備考 |
|---|---|---|
| 技能証明の有効期限 | `pilots.license_expires_on`（`store.listPilots`） | 状態の語は既存の `licenseRenewalStatus`（更新の受付期間・期限を過ぎた・期限切れ）に合わせる |
| 許可・承認の有効な最終日 | `permit_registrations.valid_to` と失効日から `effectiveLastDate`（`permit-logic.ts`） | 失効・取消済みは出さない |
| 機体の期限（登録・保険・点検整備） | **記録する場所が無い** | 見本どおり「機体の期限は、記録する場所がまだないため出ません。」の 1 行だけ。ダミーの行を出さない |

- 範囲：期限が **60 日以内**（過ぎたものを先頭に）、最大 5 件。12c の「技能証明を更新する」（次にやること）の 60 日と揃える。名前は実在の操縦者・許可のものだけ。

## 9. のりさんに決めてほしいこと（推奨つき）

1. **PR は 2 本（A＝`/ops`、B＝`/`）でよいか。** 推奨：2 本。CI の消費を抑え、本番に影響する B だけを単独で戻せる。3 本以上にする案（A をさらに分ける）は CI が増えるため採らない。
2. **「現在地で判定」の即判定を、精度が低い（100m 超）ときにも適用するか。** 推奨：**精度が低いときだけ、確認を 1 回残す**（従来の「この地点で判定」）。正しくない場所の結果を、確認なしで出さないため。通常（100m 以内）は押したらすぐ判定。決定済みの方針に対する例外のため、のりさんの判断を仰ぐ。あわせて、位置情報の文言を変えること（B5）の承認。
3. **コマンドパレット・ショートカット・手動のテーマ切り替えを、12g の 1b から外し、段階 2 以降に回してよいか。** 推奨：外す（今回の決定事項に無く、PR が大きくなる）。テーマは OS の設定に自動で従う（`color-scheme`）。
4. **URL を据え置き（`/ops/more` の表示名だけ「登録」）でよいか。** 推奨：据え置き。転送・テストの書き換え・ブックマークの切れを避ける。
5. **近づく期限の範囲：60 日以内・全操縦者と有効な許可・承認・最大 5 件でよいか。** 推奨：この範囲。機体の期限は 12f 以降（記録する場所の追加が先）。

## 10. 検証の方針

push（PR の作成）の前に、手元で次をすべて通す。

1. `pnpm typecheck`、`pnpm lint`、`pnpm test`（単体）、`pnpm build`。
2. `pnpm test:e2e`（DB を使わない E2E。CI と同じく `pnpm build` 後に `next start`。環境変数は `ci.yml` の e2e ジョブと同じ）。
3. `pnpm test:e2e:ops`（E2E-DB）は、**PostgreSQL 18＋PostGIS と `soraban_app` ロールがある環境でのみ**。ない環境では実行できないため、§6.2 の表のテストを grep で先に直し、「手元で未実行」と PR に明記する。
4. evaluator（Playwright MCP）の目視：375・768・1280px × 明・暗。A はホーム・登録・日誌・メニュー、B は `/`（PC は 1280×800 と 1440×900）。
5. `git diff origin/main` で C11（`packages/regulations/**`、`packages/db/**` のマイグレーション、`ENGINE_VERSION`、証跡 ID、`/api/**` の入出力）に差分がないこと。例外は §5 の `deadlines` の追加（応答に項目が増えるだけ）。`package.json` に差分がないこと。

CI は PR に対して 1 回で通すことを目標にする。落ちた場合は、原因をまとめて直し、1 回の push にする。
