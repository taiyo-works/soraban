## 目的と位置付け

12a〜12c で「計画と判定の根拠」「通報の記録」「現場の事実」ができた。しかし判定の「手続き済み（条件付き）」は、判定画面や計画で **DIPS の許可・承認を「持っている」とチェックするだけ**で付く。許可の番号・有効期間・範囲（場所・飛行の方法・機体・操縦者）は照合しておらず、画面は「範囲と有効期間は照合していません。許可書で確認してください」と書くにとどまる（spec §13.9.5）。期限切れの許可や、別の機体・別の場所の許可でも、チェックさえあれば「手続き済み」になる。

12d は、**自社が持つ許可・承認を番号つきで登録し（追記専用）、計画の判定に、範囲と有効期間が合うものだけを適用する**。

1. 運航管理者が、許可・承認（包括許可・個別許可。空港等周辺の個別許可を含む）を、許可番号・許可書発行日・有効期間・種類・範囲（場所、機体、操縦者、高度・重量・補助者・立入管理措置の条件）つきで登録する。訂正・失効・取消は版として残る。
2. 計画の「許可・承認の番号」の欄に入れた番号が、登録に結びつく。**結びついた登録のうち、計画の日時・場所・飛行の方法・機体・操縦者が範囲に収まるものだけ**が判定に使われる。範囲外・期限切れ・失効・取消・未登録・確認できないものは、要手続きのまま。
3. 判定スナップショットに、**どの許可の登録（番号・版・版のハッシュ）に基づいたか**が残り、日誌からあとで辿れる。

### 安全の原則（不可侵）

- **許可は「手続き不要」を生まない。** 登録を使っても、判定の最上位は「手続き済み（条件付き）」まで。元の判定が該当・該当の可能性・判定不能の規制は、手続き不要にならない（エンジンが保つ。変えない）。
- **確認できないものは要手続きのまま。** 範囲が文章だけで機械的に照合できない、計画の半径・高度・機体の重量が未入力で収まりを確かめられない、番号が登録にない、などはすべて「適用しない」（安全側）。
- **空港の敷地内と緊急用務空域は、許可の登録があっても飛行不可のまま。** 空港等の周辺の個別許可は、登録と照合を行い画面に出すが、**判定の段は変えない**（要手続きのまま。理由は「判定の既存の挙動への影響」#5）。
- **登録は利用者の申告である。** そらばんは許可書そのものを確認できない。画面は常に「登録は利用者の入力です。許可書で確認してください」と示す（12b の通報の記録と同じ作法）。
- 「通報不要」の語は出さない。条番号は `model-aircraft.ts` の定数経由のみ。法令の一次資料が未照合の事項は「※要確認」を残す。

| 照合 | 計画の日時・場所・飛行の方法・機体・操縦者・高度・重量・補助者・立入管理措置が、登録の範囲に収まるかを調べること |
| 適用 | 照合で収まった登録の種類を、判定の入力に足すこと。**登録があるだけでは適用しない** |

※要確認：包括許可・個別許可の実際の様式、書かれる条件、除外される空域・飛行の方法は、国土交通省の許可・承認の手続のページ・審査要領（`permit-notes.ts` の一次資料）と**未照合**。本書の登録項目は、DIPS の許可・承認情報（FPR No.74〜87）と判定エンジンの扱いから起こした案で、実際の許可書で確かめる（U15）。文言には「※要確認」を付ける。

### C. 照合の規則（`permit-logic.ts`。純粋関数。DB・時計・ネットワークに触れない。単体テストで全組合せ）

**入力**：計画（予定開始の JST 分、所要時間、座標、半径（null 可）、最大高度（null 可）、判定の入力のフラグ（利用者が選んだものと、最大高度 150m 以上で足した `airspace_150m`）、立入管理措置（null 可）、補助者の有無（null 可）、機体の ID と最大離陸重量（g。null 可）、操縦者の ID、許可番号の文字）と、組織の登録のヘッド行（版番号と版のハッシュを含む）。

**番号の分割と正規化**：許可番号の文字を `,`・`，`・`、`・`;`・`；`・改行で分け、各項を前後の空白を除き、`normalizePermitNumber`（Unicode NFKC → 空白をすべて除く → 英字を大文字に）で鍵にする。空の項は捨て、鍵は重複を除く。登録の `permit_number_key` と鍵が一致するものが、結びついた登録。

**飛行の窓**：開始 = 予定開始、最終分 = 予定開始 + (所要時間 − 1) 分。開始日 = 開始の JST の日付、最終日 = 最終分の JST の日付。

**関係する種類**：`did`（地点が DID かは判定が決めるため、常に関係する）と、判定の入力のフラグに対応する種類（`method_night`→`night`、`method_bvlos`→`bvlos`、`method_30m`→`30m`、`method_event`→`event`、`method_dangerous`→`dangerous`、`method_drop`→`drop`、`airspace_150m`→`150m`。`DIPS_PERMIT_BY_FLAG` の対応を使う）。`airport` は種類として関係づけず、空港等周辺の参考表示だけ（判断 7）。

**結びついた登録 1 件の判定**（次の**すべて**を満たすとき「範囲に収まる」。満たさない規則はすべて理由コードで返し、途中で止めない）：

| # | 規則 | 満たさないときの理由コード |
|---|---|---|
| R1 | 取消（`voided`）でない。取消なら、番号は未登録として扱う（`voided`） | `voided` |
| R2 | 失効していても、`revoked_on` の前日までは有効。有効な最終日 = `min(valid_to, revoked_on の前日)`（失効なしなら `valid_to`）。開始日 ≥ `valid_from` かつ最終日 ≤ 有効な最終日 | `not_started`（開始前）・`expired`（期間の終わりが飛行の最終日より前。失効を含む理由は `revoked`） |
| R3 | 場所：`nationwide` は収まる。`circles` は、計画の円（中心と半径）が**いずれか 1 つの円**に完全に含まれる：（計画の中心と円の中心の距離 [m、整数に切り上げ] + 計画の半径）≤ 円の半径。計画の半径が未入力なら含まれるかを確かめられない。`text` は照合しない | `place_out_of_scope`・`place_extent_unknown`（計画の半径が未入力）・`place_not_checkable`（文章のみ） |
| R4 | 機体：`any` は収まる。`listed` は計画の機体の ID が含まれる | `aircraft_out_of_scope` |
| R5 | 操縦者：同様 | `pilot_out_of_scope` |
| R6 | 高度の条件があるとき：計画の最大高度が入力されていて、条件以下。未入力は確かめられない | `altitude_over_limit`・`altitude_unknown` |
| R7 | 重量の条件があるとき：計画の機体の最大離陸重量が分かっていて、条件以下（g に直して比べる）。分からなければ確かめられない | `weight_over_limit`・`weight_unknown` |
| R8 | 補助者が条件で、登録の種類に `bvlos` を含み、計画が `method_bvlos` を選んでいるとき：計画の補助者の有無が「あり」 | `observer_required` |
| R9 | 立入管理措置が条件のとき：計画の立入管理措置が「あり」（未選択・なしは満たさない） | `access_control_required` |

**結果（計画ごと）**：

- 番号ごとの状態：`applied`（範囲に収まり、関係する種類を 1 つ以上含む）／`reference`（範囲に収まり、`airport` だけ。判定には使わない）／`not_relevant`（範囲に収まるが、関係する種類を含まない。例：夜間の許可だけの登録で、夜間でない計画で、`did` も含まない）／`not_applied`（上の規則を 1 つ以上満たさない。理由コードの一覧つき）／`unregistered`（登録にない、または取消）。
- `grantedValues`：`applied` の登録の関係する種類のうち DIPS の 8 種を、`mlit:<種類>` の値にしたもの（並べ替え、重複なし）。**8 種以外の値は決して入れない**（同意・通報・公園・文化庁は手入力のまま）。
- `basis`：`applied` と `reference` の登録を、**版の識別つきで**並べたもの（設計 D）。決まった順（有効な最終日の遅い順、番号の昇順）。
- 候補：番号が計画の欄にない登録のうち、同じ規則で範囲に収まり関係する種類を含むもの（`applied` と同じ判定）。提案の表示に使い、判定には使わない。
- 出力は決定的（同じ入力から同じ順序・同じ文字列）。表示の文言（理由コードごとの文・状態の語）は定数 1 か所に置き、画面・API が共有する。

**登録の有効性の表示**（一覧用。照合とは別。今日の日付で求める）：`upcoming`（開始前）・`valid`・`expiring`（満了まで 30 日以内。表示だけで、次にやることには出さない）・`expired`・`revoked`・`voided`。

### D. 判定への適用とスナップショットの根拠

- `buildJudgementInput(plan, aircraft, permitMatch)`：`pilotPermits` = 計画の手入力の値のうち **DIPS の値（`mlit`・`mlit:*`）を除いたもの** ＋ `permitMatch.grantedValues`（重複除去・並べ替え）。`permitMatch.basis` が空でないときだけ `permitBasis` を入力に足す。それ以外のキーは 12c までと同じ。`toDiagnosisRunInput` は `permitBasis` を読まない（判定には `pilotPermits` だけが渡る）。
- `permitBasis` の要素：`registrationId`、`versionNo`、`versionHash`（その版の `record_versions.content_hash`）、`permitNumber`、`coverage`、`kinds`（この計画で関係した種類）、`applied`（DIPS の種類を適用したなら true、`airport` の参考なら false）、`validFrom`、`validTo`（有効な最終日）、`window`（照合した飛行の開始日・最終日）。判定の結果・証跡 ID には入らない。
- **保存時の新しいスナップショットの要否**：12a の `planJudgementChanged` に加え、「現在のスナップショットの入力と、照合を含む新しい入力が違う」ときに新しいスナップショットを作る（同じトランザクション）。許可の番号の集合・所要時間・操縦者・登録の変更で照合の結果が変わる場合を含む。再判定（`/rejudge`）も現在の登録で照合する。
- **鮮度**：`snapshotFreshness` は、現在の登録で照合し直した入力とスナップショットの入力を比べる。`pilotPermits` または `permitBasis` だけが違うときの理由は `permits_changed`、それ以外は従来どおり。登録の訂正・失効・取消・新規、計画の許可番号・所要時間・操縦者の変更で「判定が古い」になり、既存の「判定をやり直す」の次にやることが出る。照合に使う登録は、計画の番号に結びついたものだけを**一括で**取得する（一覧の鮮度の計算で、クエリ数が計画の件数に比例しない）。照合に外部通信は要らない。
- 過去のスナップショットは不変。登録をあとから訂正しても、当時の版（`registrationId`・`versionNo`）は `record_versions` に残り、スナップショットの `permitBasis` から当時の内容に辿れる。

### E. 計画の許可番号の結びつきと、12b の手続きの記録との関係

| 項目 | 12d の扱い |
|---|---|
| 計画の「許可・承認の番号」の欄 | 従来の自由記述（0〜200 文字）のまま。**意味が変わる**：入れた番号が登録に結びつき、判定の入力になる（設計 D）。番号は区切り（`,`・`、`・`;`・改行）で複数入れられる。登録にない番号は保存できる（12a〜12c の記録との互換。「登録にありません。判定には使いません」と警告） |
| 計画の画面 | 番号ごとに状態（適用／参考（空港等周辺）／関係なし／適用しない（理由）／未登録）と、登録の有効期間・版を出す。範囲に収まる登録済みの許可の候補を「番号を入れる」ボタンつきで提案する（欄に追記するだけ。保存は利用者が行う） |
| 12b の「許可・承認の申請」が済み（`plan_procedure_records.dips_permit`） | **別のもの**。申請したことの申告で、判定を変えない（12b のまま）。許可が下りたら、運航管理者が登録し、計画の欄に番号を入れる → 判定が「手続き済み（条件付き）」になり、判定の手続きの一覧から当該の許可の手続きが消えるため、「許可・承認を申請する」の次にやることも消える（導出） |
| 次にやること（新規 1 件） | **「許可・承認の結果を登録する」**：計画に有効な `dips_permit` の記録（申請済み）があり、現在の判定に DIPS の許可・承認の手続きが残り、計画の番号に `applied` の登録が 1 件もないとき。tier は 12b の `apply_permit` と同じ重さ、`startsInMinutes` は計画の開始までの時間。押すと「許可・承認の登録」の新規入力へ。`canAct`：運航管理者のみ（それ以外は「運航管理者に依頼」。12b と同じ作法）。文言は `NEXT_ACTION_LABEL` に足す |
| 通報内容（12b）の許可・承認の番号 | 変更しない（計画の欄の文字のまま）。許可書発行日・許可期間（FPR No.76〜78）は、結びついた登録があれば `prepare` の項目に出す（契約 16。なければ従来どおり「DIPS で入力」）。対応表の版（`mapRevision`）を上げる |
| 現場モード（12c）の携行品 | 番号の表示に、番号ごとの状態（適用／適用しない・未登録）を添える（読み取りだけ。既存の `data-testid` は変えない） |

- [ ] 15. （単体・E2E-DB）12b との関係：有効な `dips_permit` の記録（申請済み）があり、判定に DIPS の許可・承認の手続きが残り、`applied` の登録がない計画に、次にやること「許可・承認の結果を登録する」が出て（運航管理者のみ `canAct`。それ以外は「運航管理者に依頼」）、登録の新規入力へ移る。登録を作り番号を計画に入れて判定が手続き済み（条件付き）になると、この項目と「許可・承認を申請する」が消える（記録は履歴に残る）。12b の `planNextActions` の既存の期待は無変更で通る。申請済みの記録は判定を変えない（12b のまま）。
- [ ] 16. （単体・E2E-DB）（残れば）通報内容と現場モード：通報内容（12b の `prepare`）の許可・承認情報に、結びついた登録があれば許可書発行日・許可期間（自・至）が項目として出る（なければ従来どおり「DIPS で入力」。`mapRevision` を上げ、12b の単体の期待のうち版に依るものだけを更新する。形式が未確認の項目は `unconfirmed` として「※要確認」）。現場モードの携行品の行に、番号ごとの状態（適用／適用しない・未登録）が出る（既存の `data-testid` は不変）。

### F. 文言・範囲・CI

- [ ] 17. （単体・grep・CI）文言と範囲：新しい画面・文言・API の応答に、禁止語（「通報不要」「通報は不要」「通報の必要はありません」「通報しなくて」）と特許・出願の表示がない。「飛べる」「許可済みで飛行可能」など、飛べると読める語を使わない。法令の条番号を新しく直書きしていない（条番号の表記は `model-aircraft.ts` の定数経由だけ）。包括許可の様式・除外事項に触れる文言には「※要確認」がある。DIPS・FPA への送信・外部通信を新しく足していない（登録は自分のサーバーの API だけを呼ぶ）。画面は色だけで状態を区別せず、375px で横スクロールがなく、明暗両方で読める。
- [ ] 18. （CI）`pnpm typecheck`・`lint`・`test`・`test:db`・`test:e2e:ops`・`build` が通る。

## 分量の判断と削る順

機能は 4 件（許可の登録と版の履歴、照合、判定への適用とスナップショットの根拠、画面）で、契約 18 項目は §13.6 の目安（10〜20）に収まる。契約 1・5・6・10 の検証が重く、2 週間の上限付近と見る。遅れたときに削る順：

1. 通報内容への許可書発行日・許可期間の追加と、現場モードの携行品への状態の表示（契約 16。登録・照合・根拠は残す）。
2. 計画の画面の候補の提案（契約 13 の候補の部分。番号の欄と照合の表示は残す）。
3. 次にやること「許可・承認の結果を登録する」（契約 15 のその部分。申請済みの記録との関係の導出は残す）。
4. 登録一覧の絞り込み（`validity`・`q`）と「この登録を根拠にしている計画」の一覧（契約 12。件数の表示だけにしてもよい）。

**削らないもの**：追記専用の登録（版・訂正・失効・取消）、照合の規則と安全側（確認できない・範囲外・期限切れ・未登録・失効は適用しない）、手入力の DIPS の許可を判定に使わないこと、スナップショットの根拠（`permitBasis` と DB の検査）、鮮度（`permits_changed`）、空港の敷地内・緊急用務空域・空港等周辺の判定を変えないこと、エンジン・`ENGINE_VERSION`・証跡 ID を変えないことと回帰の確認、禁止語の不在。

## リスク

| リスク | 備え |
|---|---|
| 登録の誤りで誤って「手続き済み」になる（利用者の申告であり、許可書そのものを確認できない） | 登録は運航管理者のみ。「機体・操縦者を限定しない」「文章のみ」は照合できない旨を出し、文章のみは適用しない。適用しても「手続き済み（条件付き）」までで、手続き不要にならない。許可書の条件を守る旨と「許可書で確認してください」を常に出す。訂正・失効・取消は理由つきの版で、根拠にした版がスナップショットに残る（あとから何に基づいたか辿れる） |
| 手入力の DIPS の許可を廃止して、利用者が戸惑う | 計画のフォームに「許可・承認は登録から照合します」と案内し、候補の提案で番号の入力を助ける。書き忘れは要手続きのまま（安全側）。公開の判定画面は従来どおり |
| 登録の訂正で、過去の飛行の根拠が書き換わったように見える | 版の履歴は追記専用。スナップショットは当時の版（`versionNo`・`versionHash`）を指す。DB のトリガーが存在しない版を指すことを拒む。画面に当時の版へのリンク |
| 登録を変えると多くの計画が「判定が古い」になる | 影響する計画の数を訂正の画面に出す。再判定は計画ごとの操作（自動で書き換えない）。社内 10 名以内の規模で許容 |
| 包括許可の実際の様式・除外事項と、登録の項目が合わない | 項目は DIPS の許可・承認情報と判定エンジンの扱いから起こした案で、「※要確認」を付ける。照合できない条件は文章（`conditions_text`）で持ち、適用した許可に常に添える。実際の許可書での確認はユーザー作業 U15。合わなければデータ（項目）の追加で足す |
| 空港等周辺の個別許可が判定に効かず、利用者が不便に感じる | 画面に理由を明記し（登録・照合は行い、判定の段は変えない）、現場試用で必要性を確かめて別のスプリントで扱う（未決事項 1）。誤って「手続き済み」にするより安全側 |
| 判定の既存の挙動を意図せず変える | エンジンを変えない縛り（契約 10）、同値の確認、3 つの基準値、`git diff` の確認、許可番号なしの入力の一致。変える点は 6 つに限定し、表で明示した |
| 登録済みの許可が日付で切れる飛行の見落とし | 照合は飛行の窓（開始日と最終日）で行い、期限切れの許可で手続き済みにしない。期限の一覧・次にやることは 12f |
| 12 全体の規模が大きい | 上の削る順。12d は 12e・12f と独立で、遅れても他に影響しない |

## 未決事項

**推奨で決めたもの**（覆す場合は着手前に知らせる）：エンジンを変えず `ENGINE_VERSION` を上げない（判断 1）、計画の DIPS の手入力を廃止し登録からだけ入れる（判断 2・変更点 #1）、番号の欄で適用する登録を選ぶ（判断 3）、飛行の窓で照合する（判断 4）、場所は全国・円・文章のみ（判断 9）、登録は運航管理者のみ（判断 8）。

1. **空港等周辺の個別許可を判定の段（要手続き → 手続き済み（条件付き））に反映するか。** 推奨：12d では反映しない（登録・照合・表示・根拠の記録まで。判断 7）。反映するには、エンジンの変更（空港等周辺の項目に満たす例外を足す）と `ENGINE_VERSION` の更新（0.5.0。証跡 ID と 3 つの基準値が変わり、既存のスナップショットが「判定が古い」になる）が要り、空港ごとの範囲・高さ・調整を扱えるデータも要る。現場試用で自社の飛行が空港等周辺に当たると分かったら、別のスプリントで planner が計画する。

**ユーザーに伺うこと**：なし（上の 1 は推奨で決めた。覆す場合のみ知らせてほしい）。
