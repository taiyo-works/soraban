## 目的と位置付け

企画書の「実務で使える」5 条件の②「電波なしの現場でスマホだけで点検・飛行記録」を実現する。いまは離着陸・確認・事故の簡易記録だけが `localStorage` の送信待ちに乗る。**画面そのものは圏外で開けず**（Service Worker もマニフェストも無い）、日常点検と飛行記録（日誌）はオンライン前提である。

15 が終わると、操縦者は次のことができる。

1. スマホのホーム画面に追加して、アプリとして開ける（PWA）。
2. 事務所や自宅の通信がある場所で「今日」を開くと、**当日の計画と必要な登録内容が端末に先読み**される。
3. 現場で圏外になっても、先読み済みの当日の現場画面を**開き直しても**開ける。
4. 圏外のまま、飛行前の確認（14 の書類・手続き・空域・現場状況を含む）、離陸・着陸、日常点検（前後）、日誌（飛行記録）の保存まで進められる。
5. 電波が戻ると、**順番を守り、二重にならずに**送られ、結果（送れた／拒否された理由）が行ごとに分かる。
6. 画面に、送れていない件数と最後に保存した時刻が常に出る。

## 設計の判断（planner の判断。generator は本書に従う）

1. **14 のあとにする理由**: 14 で現場の事実を追記専用イベントとして足す。イベントは識別子と時刻をクライアントが付けるので、送信待ちにそのまま乗る。オンライン前提で作ってから圏外に作り替える手戻りを避ける。
2. **圏外の対象範囲（最小）**: 圏外で必要なのは、①当日の現場画面を開く、②現場の事実（確認・離着陸・飛行後点検・現場状況）を残す、③日常点検を入力して残す、④日誌（飛行記録）を保存する、⑤事故・ヒヤリハットの簡易記録（既存）。**計画の作成・編集、通報の記録、許可・機体・操縦者の登録、一覧の検索は圏外の対象にしない**（オンラインで行う）。圏外の画面からそれらへ進むと、圏外であることと戻ってから行うことを示す。
3. **先読み（当日バンドル）**: 利用者がオンラインで「今日」を開いたとき、当日（JST）と、必要なら翌日分の飛行計画のうち、**その利用者が現場で扱うもの**だけの最小データを端末に保存する。含めるもの: 計画の要約（日時、場所名、機体、操縦者、特定飛行の形態）、14 の書類・手続きの判定に要る**登録内容の要約**（許可の番号・期間・範囲の要約、通報の状態、機体の登録記号）、日常点検の項目（9 項目）、直近の点検の結果、選択肢の定数。含めないもの: 技能証明書の番号、座標の全文、他の人の計画、自由記述、判定スナップショットの全文。**書類・手続きの自動判定は圏外では端末の先読みデータで再計算する**ため、判定の純粋関数（14 B）をブラウザでも動く形に保つ（サーバーの DB に依存しない）。先読みの時刻を画面に出し、古い（登録が変わった可能性がある）ときは「最終更新: ○○」と注記する。
4. **保存先**: 先読みバンドルは IndexedDB（容量が `localStorage` の上限に収まらない可能性があるため）。送信待ちの行は **既存の形式・キー・許可リストを維持**し（12c と互換）、日常点検と飛行記録の送信待ちを**種別として足す**。保存先の最終の選択（`localStorage` のまま／IndexedDB へ移行）は generator が PR に理由を書く。どちらでも、既存の送信待ちの行が読めなくなってはならない（移行テスト）。
5. **Service Worker の方針**: 画面と静的ファイルのキャッシュは**許可リスト方式**（現場画面・点検・日誌の入力・ホームの「今日」と、それに必要な JS/CSS/フォント）。**`/api/**` の応答、認証系（`/api/auth`・`/ops/sign-in`）、他の利用者のデータを含み得るものはキャッシュしない**（先読みはアプリのコードが IndexedDB に利用者ごとのキーで保存する）。新しい版の配布時は、現場の入力中の画面を勝手に再読み込みしない（更新は次に開くとき、または利用者の操作）。デプロイ間の食い違い（古い画面から新しい API を呼ぶ）で壊れないよう、API の形の互換を保つか、版の不一致を検出して再読み込みを促す。
6. **再送の方式**: 背景同期の API には**依存しない**（対応していない環境がある。※要再確認）。送信は、画面が前面にあるとき、通信が戻ったとき（`online` イベント）、画面を開いたとき、「いま送る」ボタンで行う。同じ計画の送信は同時に 1 つだけ（既存）。
7. **順序と依存**: 日常点検の送信待ちが、現場の確認の行（`inspection_id` で点検を指す）より先に送られる。端末側の仮の識別子から、サーバーの識別子への読み替えを送信側が行う。飛行記録は、離陸の行（`takeoffEventId`）との結び付けの順序を守る（12c の `journal_linked`）。
8. **拒否の扱い**: 4xx（業務上の拒否）は黙って捨てず、行ごとに理由を残し、「あとから入力」または破棄を選べる（既存）。**72 時間を超えた行（`too_old`）は、この契約でも延長しない**（延長は別の決定。離島・山間の複数日運用は§未確認）。ただし画面で「あと○時間で送れなくなります」を出す。
9. **セッション切れ**: 圏外から戻ったとき認証が切れていた（401）場合、送信待ちを消さずに再ログインを促し、ログイン後に続きを送る。ログアウトは未送信があると警告する（既存）。先読みバンドルは、ログアウト時に消す（未送信の送信待ちは警告のうえ残す選択を与える）。共用端末では、他の利用者のキーのデータを消す（既存の作法を IndexedDB にも適用）。
10. **インストール**: マニフェスト（名称、アイコン、`display`、開始 URL は `/ops`、`theme_color`）。`OPS_ENABLED` が無効の環境では、`/ops` が 404 のまま、Service Worker も登録しない（公開の `/` の LCP と既存の検査に影響させない）。**公開の判定画面 `/` には Service Worker を適用しない**。
11. **表示**: 圏外の状態（接続なし）、送信待ちの件数、最後に保存した時刻、先読みの最終更新を、現場画面の上部の固定の帯に出す（12h ④ P4-4 の「送れていない件数と最後に保存した時刻」を満たす）。圏外であることは**色だけでなく文字**で示す。

## 追加（2026-10-30、Sprint 14 の評価から引き継ぎ。ユーザー決定）

- **飛行後点検を計画に結び付ける**（Sprint 14 評価の R-1）。現在は `daily_inspections` に計画との列が無く、機体と時刻の範囲だけで飛行後点検を対応付けるため、同じ機体を同じ日に 2 つの計画で飛ばすと、別の計画の飛行後点検を「済み」と数えうる（安全側でない）。点検の記録に計画（と飛行）との結び付きを足し、対応付けを計画内に絞る。既存の点検行（結び付きなし）の扱いは、満たした扱いにしない方向で契約に書く。追加のマイグレーションは既存の最大番号の次から。完了条件: 同じ機体・同じ日の 2 計画で、一方の飛行後点検が他方を満たさないことを DB テストと E2E-DB で固定する。

- **通報の表示の食い違いを画面で補う**（Sprint 14 の評価 U-2。オーケストレーターの判断、2026-10-30）。DIPS で離陸前に通報し、そらばんへの記録だけが離陸後になった場合、現場画面に既存の「✓ DIPS で通報済み」と、書類の通報の「？ 要確認（通報の記録が離陸より後です）」が並ぶ。書類の通報の根拠に**通報日時と記録の時刻の両方**を出し、通報の記録が無い・まだの計画では、現場画面の飛行前に「通報は離陸の前にそらばんへ記録してください」の旨を出す。判定（要確認）と離陸の未了は変えない。完了条件: 単体（根拠の文言に両方の時刻）と E2E（記録が離陸後の通報で、根拠に記録の時刻が出る）。

- **飛行前点検も計画に結び付ける**（Sprint 15 の評価の差し戻し時のオーケストレーターの判断、2026-10-31）。R-1 と同じ理由（同じ機体・同じ日の 2 計画で、一方の飛行前点検が他方の「済」になり得るのは安全側でない）で、飛行後点検と同じ結び付きの仕組みを使い、結び付きのない点検は飛行前点検を満たさない。現場画面から点検へ移る導線は planId を渡す。結び付けは現場の記録と同じ権限（運航管理者、または計画の操縦者本人）でだけ行える（他人の計画を指定した点検は 403）。点検の一覧から計画を経ずに入れた点検がどの計画も満たさないことは、安全側として受け入れる。
