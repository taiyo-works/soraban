## 1. 目的と位置付け

ユーザーの要望（2026-10-20）：「飛行計画の通報から点検、日誌まで完璧に統合したサービスにしたい」。判定（地点の可否）→ 飛行計画 → 通報 → 飛行前の点検 → 離着陸 → 飛行日誌 → 事後（期限・事故）を一つの流れとし、トップ画面から迷わず使えるようにする。目的は、業務で確実に飛ばすことと、DIPS 2.0 への申請・通報をスムーズにすること。

North Star §0.1.1 のとおり、価値の芯は「判定の結果が通報と日誌に流れ込み、飛行ごとに判断の根拠（どの法令と条例を、どの版と確認日で判定したか）が記録に残ること」である。現状は部品（判定、申請支援、機体・操縦者、日常点検、飛行記録）が別々に並んでおり、飛行記録の `flight_plan_id`・`snapshot_id` は NULL のままの予約列である。本スプリント群は、それらを「飛行」という一つの単位でつなぐ。

### 設計の原則

1. **「飛行」を中心の単位にする。** 判定、計画、通報、点検、離着陸、日誌、事後のすべてが、一つの飛行（飛行計画）にぶら下がる。利用者は部品を探さず、「次にやること」から入る。
2. **根拠を鎖にする。** 日誌 → 飛行計画 → 判定スナップショット → 証跡 ID → データセットの版と確認日。どの段階からも根拠へ辿れる。
3. **事実は消さず、追記する。** 判定スナップショットは不変。通報の記録は追記だけ（取消も記録）。日誌と計画は版の履歴（既存の `record_versions`）で、訂正は版、取消は取消の版。
4. **そらばんは DIPS に送信しない（当面）。** 通報は「DIPS の入力順に整えて項目ごとにコピーする」「利用者が DIPS で通報した結果を手で記録する」「要否・期限・漏れを知らせる」までを行う。申請・通報は DIPS 2.0 などの公式の手続きで行う旨を、画面に明記する。API 連携は後の段階とし、通報ゲートウェイ（ポートとアダプター）の形で、いつ API を取得しても差し替えられるように整える（§10・§11）。
5. **誤って「不要」「済み」と出さない。** 通報の要否、手続きの済み、判定の新しさは、分からないときは厳しい側（要・未済・古い）に倒す（North Star §0.1.9）。

## 2. 製品の流れ

### 2.1 用語

| 用語 | 意味 |
|---|---|
| 飛行 | 一つの飛行計画と、それに紐づく判定・確認・通報・点検・離着陸・日誌。画面では「飛行」と呼ぶ。 |
| 判定スナップショット | 計画時に、サーバーが判定エンジンを実行して保存した、入力と結果の一式。作成後は変更しない。 |
| 通報の記録 | 利用者が DIPS 2.0 で通報した結果（通報日時・番号）の記録。そらばんが送信したものではない。 |
| 次にやること | 動詞で始まる 1 行の一覧。押すと、その作業をする画面へ直接移る。 |

### 2.2 段階と状態遷移

```
判定 ──→ 計画 ──→ 確認 ──→ 通報 ──→ 飛行前 ──→ 離着陸 ──→ 日誌 ──→ 事後
 (地点)   (飛行)  (運航管理者) (DIPS)  (点検・確認) (現場)    (記録)   (期限・事故)
   ↑        │        │         │
   └────────┴────────┴─────────┘  計画を変えると、判定は「やり直し」、確認は「再確認」、通報は「変更通報の要否を確認」に戻る
 どの段階も、離陸の前なら「中止」へ進める（中止は版として残る）
```

状態は、保存する事実から求める。保存して持つ状態は計画の `draft`（下書き）・`active`（有効）と、取消の版としての中止（12a で確定。`status` の列は `draft`／`active` のみ）だけで、「通報済み」「確認済み」などの進み具合は、各記録の有無と整合（スナップショットの ID・計画の版）から画面のたびに求める（進み具合の列を持つと、記録とずれるため）。

| 段階 | 入る条件 | 記録するもの | 不変にするもの | 戻るとき | 次にやること（例） |
|---|---|---|---|---|---|
| 1 判定 | 地点・機体の条件・飛行の方法を入れる（既存。ログイン不要） | 判定の結果、証跡 ID（既存の `evidence_log`） | 証跡 ID の計算（既存） | — | 「手続きを済ませる（期限つき）」（既存の段取り） |
| 2 計画 | 「この判定で飛行計画を作る」で、機体・操縦者・飛行予定日時・場所・飛行の方法・目的を入れて保存。**サーバーが入力から判定を実行し、スナップショットを作る**（画面から送られた判定結果は使わない） | 計画の項目、判定スナップショット、通報の要否（導出） | スナップショット | 計画を変えたら新しい版。判定に関わる項目を変えたら、スナップショットは古い扱いとなり「判定をやり直す」 | 「確認を依頼する」「判定をやり直す」 |
| 3 確認 | 運航管理者が、スナップショットと計画の版を見て確認または差し戻す | 確認者・日時・対象のスナップショットと計画の版・差し戻しの理由 | 確認の記録（追記のみ） | 計画の版が変わると、確認は「前の版への確認」と表示され、再確認が要る | 「計画を確認する」（運航管理者）、「差し戻しを直す」 |
| 4 通報 | 通報が要る飛行（導出）で、通報内容を DIPS の入力順に表示し、利用者が DIPS で通報して結果を記録する | 通報の記録（通報日時・番号・通報した計画の版の指紋・経路は手動）。変更・取消も記録 | 通報の記録（追記のみ） | 通報後に通報事項が変わると「変更通報の要否を確認」。中止すると「通報を取り消す」 | 「飛行計画を DIPS で通報する」「通報の結果を記録する」「通報を変更する」 |
| 5 飛行前 | 飛行の当日。日常点検（既存の様式2、飛行前）と飛行前確認（緊急用務空域の確認、通報済みの再確認、許可書等の携行） | 日常点検記録（既存）、飛行前確認の記録（確認項目・時刻・情報源） | 版の履歴（既存） | 点検で異常があれば、飛行を止めて不具合に回す | 「日常点検をする」「緊急用務空域を確認する」 |
| 6 離着陸 | 現場モードで、離陸・着陸の時刻を記録（片手）。未了の項目があれば警告するが、事実の記録は止めない | 離陸・着陸の時刻、未了事項の写し | 版の履歴 | 押し間違いは「取り消す」（版として残る） | 「着陸を記録する」 |
| 7 日誌 | 着陸後、離着陸時刻・計画から自動で入った飛行記録（様式1）を確認して保存。計画・スナップショットに紐づく（既存の予約列） | 飛行記録（既存）、安全に影響のあった事項、不具合 | 版の履歴と、取消＋再記録（既存） | 時間帯の外・通報なしは食い違いとして知らせる | 「飛行日誌を記入する」「日誌の食い違いを直す」 |
| 8 事後 | 期限（技能証明、機体登録、許可・承認、点検整備）と、事故・ヒヤリハット | 期限は既存データから導出。事故・ヒヤリハットは記録（12e） | 版の履歴 | — | 「技能証明を更新する」「事故を記録する」 |

### 2.3 通報の扱い（そらばんから送信できない期間）

そらばんから DIPS への送信はできない（DIPS 2.0 API の利用申請は準備中で、接続には固定 IP の中継が要る。North Star §0.1.6）。この期間の「通報」は次の四つで構成する。

**(1) 要否の導出**（12a で表示、12b で漏れの検出に使う）

- 通報は特定飛行を行うときの義務である（出典：drone-ops `docs/research-regulations.md` §2.1、飛行計画の通報要領 https://www.mlit.go.jp/common/001878897.pdf 。**2026-10-20 時点で通報要領の本文を作業環境から取得して照合していない。※要確認**）。判定スナップショットから導く。

| 条件（スナップショット） | 通報の表示 |
|---|---|
| 100g 未満（模型航空機）。航空法の無人航空機の規制は対象外（spec §13.9.9） | 「DIPS の飛行計画の通報は対象外（模型航空機）」。第134条の3 の許可・通報は別の手続きとして、判定の手続きに並べる（既存） |
| 100g 以上で、特定飛行に当たる項目（DID、空港等周辺、150m 以上、緊急用務空域の選択、夜間、目視外、30m 未満、催し場所、危険物、物件投下）が一つでも「要手続き」「手続き済み（条件付き）」「判定不能」 | **要**。当たった項目を根拠として並べる（例：「夜間飛行に当たるため」） |
| 100g 以上で、全項目が「手続き不要」、かつ入力が揃っている | 「義務ではないが、通報を推奨」 |
| 重量が未入力、または判定が成立していない | 「要確認（要として扱う）」 |

- **「通報不要」への上書きは設けない。** 例外（国・地方公共団体などの捜索・救助の飛行は通報不要）は、利用者が目的として選んだときだけ「通報不要の例外に当たる可能性（要確認）」と出し、通報の要を消さない。
- 通報システムの障害で飛行開始までに通報できない場合は飛行開始後の通報ができる、という例外は、注記として出す（義務の根拠は通報要領。※要確認）。
- 小型無人機等飛行禁止法の公安委員会への通報（飛行の 48 時間前まで）は、DIPS の通報とは別の手続きである。判定の手続きに既にあり、計画の「手続きの済み」で追う（12b）。

**(2) 期限と漏れの知らせ**

| 手続き | 期限（出典・状態） | 次にやること |
|---|---|---|
| DIPS の飛行計画の通報 | 「あらかじめ」（事前）。通報要領は時間に十分なゆとりを持った事前の通報を求めるとされ、何時間前という数値の期限は確認できていない（drone-ops の調査、2026-10-20。※要確認）。**法定の期限として日付を作らない。** 社内の目安として「飛行開始の 24 時間前まで」を組織の設定（既定 24 時間）で持ち、「目安」と明記する | 目安の時刻を過ぎて未記録なら警告。**飛行開始時刻を過ぎて未記録なら、最上位の警告**（「通報せずに特定飛行を行うと罰則がある」旨を出典つきで。drone-ops は 30 万円以下の罰金、航空法第157条の10第1項第10号としているが、そらばんでは条文を一次資料で確かめるまで「※要確認」を付ける） |
| 通報後の変更・取消 | 変更は変更事項を通報、中止が分かったら速やかに取り消す（drone-ops の調査）。DIPS は「通報した飛行開始日時までに変更、削除を行う」と案内 | 通報後に日時・経路・機体・操縦者などが変わったら「通報を変更する」。中止なら「通報を取り消す」 |
| 許可・承認の申請 | 10 開庁日以上前（既存 §13.9.6） | 「許可・承認を申請する」 |
| 公安委員会への通報（飛行禁止法） | 48 時間前まで（既存 §13.9.6） | 「警察へ通報する」 |

- **2026-03-31 に改正された飛行計画の通報要領（国空無機第351405号）の具体的な改正内容は、drone-ops の調査でも「不明」（附則のみ確認）である。** 12b の着手前に、要領の本文で通報事項と入力の要領を確かめる（ユーザー作業か、作業環境から取得できた場合は planner が照合する。§6）。確かめるまで、通報事項の一覧は「通報要領（令和8年3月31日最終改正）に基づく。改正内容は※要確認」とする。

**(3) 通報内容の DIPS 入力順の表示とコピー**

- 通報要領 4(3) の通報事項（日時・経路、登録記号と種類、操縦者の氏名、技能証明書番号、許可・承認の番号、目的・高度・速度、飛行禁止空域と飛行の方法、出発地、目的地、所要時間、立入管理措置、保険、その他）を、**DIPS 2.0 の通報画面の入力順**に並べ、項目ごとに「コピー」ボタンを付ける。入力順は、DIPS 2.0 の操作マニュアル（飛行計画通報編 https://www.ossportal.dips.mlit.go.jp/guide/fiss/DIPS-Manual_FPR_ALL_Ja.pdf ）と通報画面で確かめて決める（**2026-10-20 時点で未照合。※要確認。ユーザー作業 U4**）。
- 値の整形：時刻は JST・分単位、所要時間は 5 分単位・最大 24 時間（超える分は別の計画）、名称は 30 文字以内（FPR API の値域。drone-ops の調査。※要確認）。目的は DIPS の選択肢の言葉に合わせる。
- 地図上の経路は DIPS の画面で描く必要があり、コピーできない。座標の一覧（円なら中心と半径）を表示し、「DIPS の地図で描く」と案内する。これは正直に画面に書く。
- 項目の変換は、版つきの対応表（データ）と 1 か所のモジュールに閉じ込める。将来の API 送信の変換と同じ表を使う。通報の準備・送信・記録は、1 つの抽象（通報ゲートウェイ）の裏に置き、今は手動アダプター、開発用に模擬アダプター、将来 API アダプターに差し替えられる形にする（§10）。

**(4) 結果の手動記録と二重の確認**

- 利用者が DIPS で通報したあと、「通報の結果を記録する」で、通報日時（JST・分）と DIPS 側の番号を入れる。**記録するまで「通報済み」にならない。** そらばんが送信したのではなく、利用者の申告であることを、記録に「手動」と残す。
- 記録のとき、二つのチェックを必須にする：「DIPS 2.0 の画面で通報を完了した」「通報した内容は、この計画の最新の版と一致している」。
- 飛行当日の現場モードの「飛行前」で、「DIPS で通報済み（記録：日時・番号）」を再掲し、確認を求める。未記録なら離陸前に警告（記録は止めない）。
- 通報時の計画の指紋（日時・所要時間・経路・高度・速度・機体・操縦者・飛行の方法。drone-ops の review 2d に学ぶ）を保存し、計画が変わって指紋が変わったら「変更通報の要否を確認」と出す。
- DIPS 側の番号が画面に表示されるかは未確認。表示されない場合の記録（番号を必須にできるか）は、12b の着手前に DIPS の画面で確かめる（ユーザー作業 U4、未決 5）。
- 利用者への伝え方（画面の固定文言の案）：「そらばんは DIPS に送信しません。この内容を DIPS 2.0 で通報し、通報した日時と番号をここに記録してください。記録するまで『通報済み』にはなりません。申請・通報は DIPS 2.0 などの公式の手続きで行ってください。」

### 2.4 画面と導線

**トップ画面と下メニュー**

- `/` は、これまでどおり地点判定と申請支援の入口（ログイン不要）として残す。DIPS の申請書に書く接続システムの URL であり、外部の担当者も見るため、運航管理の導線で置き換えない。
- 運航管理を使える状態（`OPS_ENABLED` 有効かつログイン済み）のとき、スマホの下メニューを共通の枠として全画面に出す（案）：

| 項目 | 行き先（案） | 内容 |
|---|---|---|
| 今日 | `/ops`（12c で「今日」に作り替え） | 今日の飛行カード、次にやること |
| 判定 | `/` | 地点判定・申請支援（既存）。結果に「この判定で飛行計画を作る」 |
| 計画 | `/ops/plans` | 飛行の一覧（これから・過去）、新しい飛行計画 |
| 日誌 | `/ops/flights`、`/ops/inspections` | 飛行記録・日常点検（既存）。12c で一つの「日誌」にまとめる |
| その他 | `/ops/more` | 機体、操縦者、利用者、よく使う地点、期限一覧（12f）、事故・ヒヤリハット（12e）、設定 |

- drone-ops は下メニューを 4 つ（今日／計画／日誌／その他）にしている。そらばんは判定の入口を残すため 5 つにする（ユーザー案）。5 つで 375px に収まるかは 12c で確かめる。収まらなければ「判定」を「今日」の中の大きなボタンにする。
- 運航管理にログインしている人が `/` を開いたとき、見出しの下に「今日」の帯（今日の飛行と、次にやること上位 3 件）を出す（12c）。`/` の自動の転送はしない（未決 2）。
- 12a の時点では、`OPS_ENABLED` が有効なとき `/` の見出し付近に「運航管理」への小さなリンクを出す（今は入口が無い）。無効の本番では出ない。

**「今日」と次にやること（12c）**

- 今日（なければ次）の飛行を大きなカード 1 枚で出す：時間、名称、機体、操縦者、判定の段階、通報の状況、確認の状況。その下に「次にやること」を、動詞で始まる 1 行の一覧で出す。件数だけのタイルは作らない。
- 並び順（案）：飛行開始までの時間が短いものを先に。同じなら、法的な重さ（通報・許可の漏れ ＞ 点検・確認 ＞ 日誌 ＞ 期限）。次にやることは各記録の有無から導出する（保存しない）。

| 次にやること（動詞で始まる） | 条件（導出） | 押すと |
|---|---|---|
| 飛行計画を DIPS で通報する | 通報が要で、有効な通報の記録がない | 通報内容のコピー欄 |
| 通報の結果を記録する | （手元に結果があるときのため）通報内容を開いた後で未記録 | 記録フォーム |
| 通報を変更する／取り消す | 指紋が変わった／中止した | 変更点の表示 |
| 許可・承認を申請する／警察へ通報する | 判定の手続きで期限が近い・過ぎた | 判定の段取り |
| 計画を確認する／差し戻しを直す | 確認が未了・差し戻し | 確認画面 |
| 判定をやり直す | 計画が変わった、または判定の根拠のデータ・エンジンの版が変わった | 再判定 |
| 緊急用務空域を確認する | 飛行当日で、確認の記録がない | 飛行前確認 |
| 日常点検をする | 飛行当日で、飛行前の点検がない | 点検フォーム |
| 日誌を記入する | 着陸済み、または計画の時刻を過ぎて日誌がない | 計画の内容が入った日誌フォーム |
| 日誌の食い違いを直す | 時間帯の外で離陸、または特定飛行で通報の記録がない | 該当の記録 |
| 技能証明を更新する ほか | 期限が近い（既存データから。12f で一覧に） | 操縦者・機体の編集 |

**現場モード（12c）**

- 1 つの飛行に集中する画面。①飛行前（日常点検、緊急用務空域の確認、通報済みの再確認、携行品）→ ②離陸・着陸 → ③日誌（時刻・計画から自動入力）。押す大きなボタンは 1 つ（片手、72px 以上の離着陸ボタン）。確認ダイアログの代わりに「取り消す」。飛行中は経過時間を表示し、画面の消灯を防ぐ（Screen Wake Lock API。対応端末と HTTPS のときだけ）。
- **圏外対応は現実的な範囲に絞る。** Sprint 11 の決定（下書きの保持と、`clientRequestId` による再送まで）を土台に、12c では、離着陸の時刻を端末に一時保存して通信が戻ったら送る範囲までとする。現場モードの画面と今日から 3 日間の計画の要点を端末に保存して完全に圏外で動かす構成（Service Worker と IndexedDB）は、山陰の現場の通信状況と Next.js 16 での動作が未確認のため、12c の後半の任意項目とし、現場試用の結果で判断する（Sprint 11 未決 4 と同じ扱い）。個人データを端末に残す範囲と、ログアウトでの消去を、そのとき決める。
- 離陸の記録は、未了の項目（点検、通報、確認）があっても止めない。事実の記録を止めると、飛んだのに記録が無い状態になる。未了の項目は警告し、飛行記録に「離陸時の未了事項」として写しを残す。

### 2.5 そらばんの強みを各段階に貫く

| 段階 | 貫き方 |
|---|---|
| 計画 | スナップショットに、証跡 ID、`ENGINE_VERSION`、使用データセットとその確認日、手続きの `revision` を入れる。計画の画面で「どの法令・条例を、どの版と確認日で判定したか」を開ける |
| 確認 | 運航管理者は、判定の結果だけでなく、出典と確認日が古い項目（90 日超など）を見て確認する |
| 通報 | 通報内容の「飛行禁止空域と飛行の方法」の項目に、判定の根拠をそのまま使う。通報の記録に、対象のスナップショットの ID を持たせる |
| 日誌 | 飛行記録から、計画 → スナップショット → 証跡 ID → データセットの版・確認日へ 3 タップ以内で辿れる。飛行 1 件の証跡出力（Sprint 15）で、これを一式にして出せる |
| 再判定 | 判定の根拠が更新されても、古いスナップショットは書き換えない。再判定は新しいスナップショットとして残し、計画の「現在の判定」を新しい方に向ける。履歴で並べて見られる |

### 2.6 データの置き方（案。マイグレーションの確定は各スプリントで）

### 3.2 この順序にした理由

- **12a を最初にする理由**：スナップショットと計画がないと、通報・点検・日誌を結びつける相手がない。日誌から根拠へ辿れる（North Star §0.1.1 の価値の芯）のは、12a の時点で実現する。
- **12b を 12a の次にする理由**：通報は、飛行ごとの義務（特定飛行）のうち、漏れたときの影響が大きく（罰則の可能性。※要確認）、DIPS 申請・通報をスムーズにするというユーザーの目的の中心である。送信できない期間でも価値がある（コピーと漏れの検出）。
- **12c を 12b の後にする理由**：「今日」と現場モードは、通報・確認・計画の状態を束ねる画面であり、先に状態が決まっている必要がある。
- **13（点検整備）と 15（証跡出力）を既存のまま残し、12d・14 を 4 月以降に回す理由**：点検整備記録は飛行日誌の三つの記録の一つで、証跡出力は日誌の提出・保管に要る。年度末の三点（North Star §0.1.4）のうち「自社の飛行記録をすべて運航管理で作成」と「条例データの鮮度」は、12d（許可の範囲の照合）がなくても満たせる。12d を後にする間は、Sprint 11d の入力（種類ごとに「持っている／いない」、範囲は照合しない旨の注記）と、計画の許可番号の手入力で運用する。未決 1 で、12d を 13 の前に置く案（13 を 4 月に回す）も示す。
- **旧 Sprint 14（判定データの DB 化と管理画面）を Phase 2 に回す影響**：「確認日が 90 日を超えたデータの一覧」は、Sprint 7 の出典・確認日の台帳（静的データ）から Sprint 16 の集計で出す前提とする（台帳から機械的に出せるかは、Sprint 16 の計画で確認する。未決 1 の確認事項）。

## 4. Sprint 12a（確定した契約は `docs/sprints/sprint-12a.md`）

2026-10-21 に、下書き（17 項目）を現在のコードに照らして確定させた（契約 22 項目）。下書きから変わった主な点：

- 証跡 ID は判定時刻を含むため、「画面の証跡 ID と一致する」は成立しない。「保存した入力と結果から再計算すると一致する」にした。

- 判定に関わる項目を変えた保存は、同じトランザクションで新しいスナップショットを自動で作る（「判定が古い」は、機体の重量・エンジンの版・データの確認日・手続きデータの版が変わったときに出す）。
- スナップショットは追記専用（`soraban_app` に更新・削除の権限を与えない）に加え、DB が内容のハッシュを決め、オーナーでも更新・削除できないトリガーを置く。計画・飛行記録との関係は複合外部キーで DB が守る。

- 「通報不要の例外」の文言は、「通報不要」の言葉を使わない形に改めた。
- 計画の複製、差し戻しの理由の分類は範囲外にした。

### 7.2 未決事項（2026-10-21 に、ユーザーが「進めて」で承認。13 件すべて推奨どおりで確定）

> 5 は推奨に条件がある：番号が通報後の画面に表示されることを U4 で確かめ、表示されるなら必須、表示されないなら通報日時と控えを求める（12b の着手前に確定）。13 は推奨どおり「Phase 2 の開始時に、API の仕様と合わせて決める」。ユーザーの判断が必要な項目は残っていない。以下は決定前の記録で、推奨が確定した内容である。

1. **12d（許可・承認の登録）を 4 月に回し、13・15 を年度末までに残す順序でよいか。** 推奨：この順序。13・15 は日誌の記録と提出に要り、年度末の三点にも関わる。12d を回す間は、11d の「持っている／いない」の入力＋範囲未照合の注記と、計画の許可番号の手入力で運用する。代替：12d を 13 の前に置き、13 と 15 の一部を 4 月に回す（見落としゼロの点では 12d が先だが、点検整備の記録が年度末に間に合わない）。あわせて、旧 Sprint 14（判定データの DB 化）を Phase 2 に回し、確認日の鮮度の集計を静的な台帳から出すことでよいか（台帳から出せるかは Sprint 16 の前に planner が確認する）。
2. **ログイン済みの人が `/` を開いたとき、「今日」へ自動で転送するか。** 推奨：転送しない。`/` は判定の入口で、DIPS の申請書に書く URL でもある。代わりに見出しの下に「今日」の帯を出す（12c）。試用で迷う人が多ければ転送を検討する。
3. **運航管理者が自分の計画を確認すること（自己確認）を許すか。** 推奨：許す。小規模では同一人物が兼ねるため。記録と画面に「自己確認」と出す。別の運航管理者がいる場合の確認を必須にする設定は、後続の候補。
4. **通報の「目安」の時刻（飛行開始の 24 時間前）を既定にするか。** 推奨：既定 24 時間、組織の設定で変えられる。法定ではなく社内の目安と画面に明記する。通報要領の改正内容の確認（U3）で数値が分かれば、その値に合わせる。
5. **DIPS 側の番号を、通報の記録で必須にするか。** 推奨：番号が通報後の画面に表示されることを U4 で確かめ、表示されるなら必須。表示されない場合は、通報日時と、DIPS の画面の控え（画像の保管は後続）を求める。
6. **計画の飛行範囲を、点（と半径）に限るか、多角形まで持つか。** 推奨：12a は点と半径。多角形の作図は、現場試用で必要性を確かめてから別のスプリントで（DIPS の通報で経路を描くのは利用者であり、座標の表示で足りる間は後でよい）。
7. **離陸の記録を、未了事項（点検・通報・確認）があっても止めないことでよいか。** 推奨：止めない。警告し、日誌に未了事項の写しを残す。事実の記録を止めると、飛んだのに記録が無い状態になるため。
8. **下メニューの 5 項目（今日／判定／計画／日誌／その他）でよいか。** 推奨：5 項目で作り、375px で収まらなければ「判定」を「今日」の大きなボタンにする（12c で確かめる）。
9. **飛行 1 件の証跡出力（Sprint 15）に、通報の記録（手動）を含めるときの表示。** 推奨：「利用者の申告による記録」と区別して出す。API 連携後は「DIPS から取得した記録」と区別する。
10. **事故・ヒヤリハット（12e）の報告の数値期限。** drone-ops の調査では「速やか」以外の数値は確認できず「不明」。推奨：「速やかに DIPS 2.0 で報告」とだけ出し、数値の期限を作らない。U5 で条文を確かめる。
11. **通報ゲートウェイの置き場所（案：`packages/dips`）と、アダプターの切り替えの単位。** 推奨：パッケージを分け、切り替えは環境変数（既定 `manual`）で全体に一つ。組織ごとの切り替え（一部の組織だけ API）は、必要になってから足す（データには `channel` を持つため後から可能）。
12. **API の送信の確認画面で、利用者に何を見せるか。** 推奨：項目ごとの値と、通報の指紋、「実際の国への通報になります」の注意。確認なしの送信は設けない。
13. **中継の置き場所と運用（国内 VPS の選定、監視、鍵の管理）と、アプリ ↔ 中継の認証方式。** 推奨：Phase 2 の開始時に、API の仕様と合わせて決める（§10.9）。12b では設計の枠（要求の形、監査の突き合わせの ID）だけ確定する。

## 8. North Star への差し込み案（実際の反映はユーザー承認後）

**反映済み（2026-10-21）：`docs/00_NORTH_STAR.md` §0.1.10 として追加し、版を 1.6、最終更新を 2026-10-21 にした。** 反映した文はユーザーの言葉を冒頭に添えたもので、下の案とほぼ同じ。

> ### 0.1.10 統合した運航管理サービス（2026-10-20 案。実際の文は North Star 本体を正とする）
>
> そらばんは、判定から事後までを「飛行」という一つの単位でつなぐ、統合した運航管理サービスとして作る。流れは、判定 → 飛行計画 → 運航管理者の確認 → 通報（準備と記録）→ 飛行前の点検 → 離着陸 → 飛行日誌 → 事後（期限・事故・ヒヤリハット）である。トップの「今日」から、次にやることを順にたどれば、手続きの漏れなく飛べる状態を目指す。
>
> - 価値の芯は、各段階に判断の根拠（どの法令・条例を、どの版と確認日で判定したか）を貫くこと。計画の判定は不変のスナップショットとして保存し、通報の記録・点検・日誌から辿れる。
> - 申請・通報・報告は DIPS 2.0 などの公式の手続きで行う。そらばんは、DIPS 2.0 API の利用が可能になるまで DIPS に送信しない。当面は、通報内容を DIPS の入力順に整えて項目ごとにコピーできるようにし、利用者が DIPS で通報した結果を手で記録し、通報の要否と漏れを「次にやること」で知らせる。画面には、そらばんが送信していないこと、記録は利用者の申告であることを明記する。
> - 通報の送信は 1 つの抽象（通報ゲートウェイ）の裏に置き、手動・模擬・DIPS 2.0 API のアダプターに、画面とデータモデルを変えずに差し替えられる形にする。DIPS 宛ての通信だけを固定 IP の中継経由にし、クライアント秘密は中継に置く（§0.1.6）。
> - 通報の要否は、分からないときは要として扱う。「通報不要」とは出さない（§0.1.9 の見落としゼロの方針を通報にも適用する）。
> - drone-ops（ユーザー自身の作品）の画面の流れ（「今日」、現場モード、通報内容のコピーと手動記録）を参考にする。判定の厳密さ、出典、版の履歴、複数利用者の認可は、そらばんの方式を保つ。
>
> 詳細は `docs/spec.md` §13.10 と `docs/sprints/sprint-12.md`。

**§0.1.7 の確認項目との関係**：本方針の各機能は「判定から通報、点検、記録までの手間か誤りを減らすか」（1）に当たる。山陰の自社の点検で使い（2）、出典と確認日を持たせられ（3）、維持の手順を残せる（4）ため、保留の対象ではない。

| DIPS の許可・承認は飛行開始の 10 開庁日以上前 | 既存 spec §13.9.6 | 既存の確認（spec） |

## 10. 通報ゲートウェイ（API に差し替えられる形）

ユーザー指示（2026-10-20）：「通報は送れなくてもいいので、いつ API を取得してもいいようにカタチも整えたい」。通報（と、必要なら申請）の送信を、1 つの抽象の裏に置く。画面とデータモデルは、アダプターが手動でも模擬でも API でも同じにする。

**API の正式な仕様は入手前である。** 項目の対応表と状態の遷移は拡張できる作りにし、分からない部分は「未確定・要確認」として §10.9 に集め、推測で固定しない。drone-ops の調査（FPR API ガイドライン 1.10 版の記述）は参考にとどめ、API 利用の開始時に正式な仕様で照合する。

### 10.1 ポートとアダプター

```ts
// 案（型の名前・メソッドは 12b の契約で確定する）
interface NotificationGateway {
  readonly adapter: "manual" | "mock" | "api";
  capabilities(): { mode: "user_reported" | "direct"; canStatus: boolean; canCancel: boolean; canChange: boolean };
  prepare(plan: PlanForReport, snapshot: JudgementSnapshot, kind: "new" | "change" | "cancel"): PreparedReport;
  submit(prepared: PreparedReport, ctx: { idempotencyKey: string; actor: ActorRef; manualResult?: ManualResult }): Promise<SubmitResult>;
  status(report: ReportRef): Promise<StatusResult | Unsupported>;
  cancel(report: ReportRef, ctx: { idempotencyKey: string; actor: ActorRef; reason: string; manualResult?: ManualResult }): Promise<CancelResult>;
}
```

| メソッド | 役割 |
|---|---|
| `prepare` | 計画とスナップショットから、通報内容（DIPS の入力項目に対応づけた項目の一覧、整形済みの値、コピー用の文字列、警告）と、通報の指紋・項目の対応表の版を作る。副作用なし。**どのアダプターでも同じ結果**（対応表を使う）。画面の「入力順の表示とコピー」は、この結果をそのまま描く |
| `submit` | 通報を確定する。`direct`（API・模擬）は外部へ送る。`user_reported`（手動）は、利用者が DIPS で通報した結果（`manualResult`：通報日時・番号・二つの確認）を受け取って記録する。どちらも結果は同じ形（`SubmitResult`：状態、番号、通報日時、エラー） |
| `status` | 通報の状況を外部に問い合わせる。手動は `Unsupported`（DIPS 側の状態は取得できない）を返し、画面は「利用者の申告」と表示する |
| `cancel` | 通報の取消。手動は、利用者が DIPS で取り消した結果を記録する。`canCancel` が偽なら「DIPS の画面で操作してください」に倒す（ケイパビリティ） |

- 画面は `capabilities().mode` だけで分岐する：`user_reported` なら「コピー → 記録」、`direct` なら「送信内容の確認画面 → 送信」。送る前の確認画面は必須（実際の国への通報になるため）。分岐以外の画面・データ・状態の遷移は共通。
- **切り替えは設定で行う。** 環境変数（例：`DIPS_REPORT_ADAPTER=manual|mock|api`）と接続の設定（中継の URL など。値はリポジトリに置かず、名前だけ `.env.example` に書く）。既定は `manual`。組織ごとの切り替えの要否は未決 13。
- **模擬アダプターは本番で使えない。** 本番のビルドで `mock` が選ばれていたら起動を拒否する（drone-ops の `deploy-check` にならう）。
- ゲートウェイの実装は 1 つのパッケージ（案：`packages/dips`）に置く。判定エンジン（`@soraban/regulations`）には依存させない（スナップショットの型だけを受け取る）。

### 10.2 通報内容の項目の対応表（データとして持つ）

項目の対応表は、コードに直書きせず、版つきのデータファイル（`procedures.json` と同じ流儀：`revision`・確認日つき）で持つ。画面の入力順の表示と、将来の API の入力項目の両方が同じ表を使う。

| 列 | 内容 |
|---|---|
| `key` | そらばんの項目の名前（例：`flight_start`、`pilot_name`、`permit_numbers`） |
| `order` | DIPS の通報画面での入力順（**未照合。U4**） |
| `dipsLabel` | DIPS の画面の項目名 |
| `requirement` | 通報要領 4(3) の通報事項の記号（a〜n。※要確認） |
| `format` | 値の整形規則（JST・分単位、5 分単位、30 文字以内など） |
| `copyable` | コピーできるか（地図の経路は偽。座標を表示する） |
| `apiField` | API の項目名。**API の仕様の入手前は空（未確定）**。drone-ops の調査にある名前は「参考（未確認）」として別の列に置き、確定値にしない |
| `confirmedAt`／`confirmedBy`／`source` | 確認日・確認者・出典。確認していない行は `status: "unconfirmed"` とし、画面で「※要確認」を出す |

- 対応表の版（`mapRevision`）を、通報の記録に残す。後で表が直っても、過去の通報が当時どの表で整えられたかが分かる。
- 項目の追加・変更はデータの更新で済み、型・画面は変えない（未知の項目は一覧に足されるだけ）。

### 10.3 状態と遷移（拡張できる形）

通報の記録（1 回の通報行為）の状態。ユーザー指定の六つに、「結果不明」を足す（理由は §10.5）。

| 状態 | 意味 | 送信元 |
|---|---|---|
| `prepared`（準備中） | 通報内容を整えた。まだ何も行っていない | すべて |
| `copied`（コピー済み） | 利用者が項目をコピーした（DIPS での通報は未確認）。任意の中間状態で、飛ばしてもよい | 手動 |
| `reported_manual`（DIPS で通報済み・手動記録） | 利用者が DIPS で通報し、結果を記録した（利用者の申告） | 手動 |
| `submitted_api`（送信済み・API） | API で送信し、受け付けられた | API・模擬 |
| `failed`（失敗） | 送信前の失敗、または DIPS が拒否した（確定している失敗）。再送できる | API・模擬 |
| `unknown`（結果不明） | 送信後に応答が得られない（時間切れなど）。**二重通報を避けるため、自動で再送しない**。状況の確認（`status` か、DIPS の画面）の後に確定する | API・模擬 |
| `cancelled`（取消） | 通報を取り消した（取消の記録も別の行として残る） | すべて |

遷移（案）：`prepared → copied → reported_manual`、`prepared → reported_manual`、`prepared → submitted_api | failed | unknown`、`failed → submitted_api | failed`（再送）、`unknown → submitted_api | failed | reported_manual`（確認後）、`reported_manual | submitted_api → cancelled`。

- 遷移表は 1 か所（1 つのモジュール）に置き、画面・アダプター・テストが同じ表を使う。表にない遷移は拒否する。
- **拡張の仕方**：DIPS が返す受付の状況（例：受付中、受理、重複の調整中など。**未確定**）は、状態には入れず、まず `external_status`（生の値と取得日時、`external_ref jsonb` の中）に保存する。状態の追加が必要になったときだけ、追記のマイグレーション（CHECK の置換）と遷移表の更新で足す。未知の外部状況は「状況：不明（生の値）」と表示する。
- 変更・取消は、元の通報を指す別の通報行（種別：`change`／`cancel`）として足す。有効な通報は「取消でない、最新の新規または変更」。

### 10.4 通報の記録（データモデル）

| 項目 | 内容 |
|---|---|
| 識別 | `id`、組織 ID、計画 ID、種別（新規／変更／取消）、元の通報の ID（変更・取消のとき） |
| 根拠 | 判定スナップショットの ID と**証跡 ID**、計画の版と指紋、項目の対応表の版（`mapRevision`）、`ENGINE_VERSION` |
| 内容 | 整えた通報内容の写し（項目ごとのキーと値。`jsonb`。送った・コピーさせた内容がそのまま残る） |
| 状態 | §10.3 の状態 |
| 結果 | 発行番号（DIPS 側の番号）、通報日時（JST・分。手動は利用者の入力、API は DIPS の受付時刻か送信時刻。どちらかは未確定）、送信日時（サーバーが送った時刻。手動は記録した時刻） |
| 送信元 | `channel`：`manual`（利用者の申告）／`api`／`mock`。画面に「手動（利用者の申告）」「API」「模擬（開発用）」と必ず出す |
| 冪等性 | 冪等性キー（§10.5）。一意制約あり |
| 外部 | `external_ref jsonb`（DIPS 側の ID、`external_status`、生の応答の要約。空でよい） |
| 版の履歴 | `record_versions`（entity_type = `flight_report`）の方式。状態の変更・訂正は版として追記し、物理削除しない（取消も版） |

- 通報の内容と結果の列は、版の `data` に入れ、ヘッド表を DB が作る（Sprint 10・11 と同じ流儀）。
- 手動記録の訂正（番号の打ち間違いなど）は、理由つきの新しい版。訂正前の値は履歴に残る。

### 10.5 冪等性・取消・再送

| 論点 | 定義 |
|---|---|
| 二重通報の防止 | 冪等性キーは「組織 ID ＋ 計画 ID ＋ 種別 ＋ 通報時の計画の指紋」から作る決定的な値（画面の再読み込み・二度押しでも同じキーになる）。同じキーの有効な通報があれば、新しい通報行を作らず、既存の結果を返す。変更通報は新しい指紋なので、別のキーになる |
| 手動と API の二重 | 手動記録（`reported_manual`）が有効な計画に、API で新規送信することは禁止する。DIPS 上で同じ計画が二重になるため。DIPS の画面で作った計画を API から参照・変更できるかは**未確定** |
| 取消 | 取消は別の通報行。`canCancel` が偽（手動など）なら、DIPS の画面で取り消した結果を記録する。計画を中止したら、有効な通報があるかぎり「通報を取り消す」が次にやることに出る |
| 再送 | `failed`（確定した失敗）だけ、利用者の操作で再送できる。同じ冪等性キーを使う。DIPS 側が冪等性キーを受け付けるかは**未確定**のため、そらばん側で「再送の前に、同じキーの `submitted_api` が無いこと」を確かめる |
| 結果不明 | 時間切れなどで結果が分からないときは `unknown` とし、自動で再送しない。`status` で確認できればその結果で確定、確認できなければ、利用者に DIPS の画面で確かめてもらい、結果を記録する（`reported_manual` か `failed`） |
| 自動の再試行 | 送信前に必ず失敗したと分かる場合（中継への接続の失敗など）と、読み取りの呼び出し（`status`）だけ、回数と間隔を決めて自動で再試行する。送信が相手に届いた可能性がある場合は再試行しない |

### 10.6 接続の構成（North Star §0.1.6 に沿う）

```
 利用者のブラウザ
       │ HTTPS
       ▼
 ┌─────────────────────────────┐        ┌───────────────┐
 │ Vercel（Next.js、sin1）        │        │ Neon（記録・監査）│
 │  通報ゲートウェイ（ポート）      │───────▶│ flight_reports │
 │   ├ 手動アダプター（既定）       │        │ attempts 等    │
 │   ├ 模擬アダプター ─────────┐   │        └───────────────┘
 │   └ API アダプター ───┐     │   │
 └───────────────────────│─────│───┘
                         │     │ 開発・E2E のみ
        署名つきの要求（方式は未確定）  ▼
                         │   模擬サーバー（e2e/mock-dips-relay-server.mjs）
                         ▼
 ┌─────────────────────────────┐   固定 IP（検証：本社回線、本番：国内 VPS を想定）
 │ 中継（固定 IP）                │   ・クライアント ID／秘密はここだけ
 │  ・DIPS 宛ての通信だけを担う      │   ・利用者ごとのトークンを保管
 │  ・OIDC のトークン交換・更新      │   ・要求の監査ログ
 └──────────────┬──────────────┘
                ▼
        DIPS 2.0（OIDC 認可コードフロー、FPR API）
```

- DIPS 宛ての通信だけを固定 IP の中継経由にする。アプリ本体は Vercel のまま。**クライアント秘密は Vercel に置かない。** Vercel が持つのは、中継を呼ぶための資格情報だけ。
- アプリ → 中継の認証と通信の保護の方式（署名つきの短命のトークン、相互 TLS など）、中継の実装（小さな HTTP サービス）と置き場所は**未確定**。中継は、許可された操作（prepare 済みの内容の送信、状況の確認、取消）だけを受け、組織・利用者・冪等性キーを必須にする。
- **認可（OIDC 認可コードフロー）**：drone-ops の調査では、DIPS の画面にログインする方式で、アプリは DIPS のパスワードを扱わない。クライアント ID・秘密は法人単位で申請し、各操縦者は自分の DIPS アカウントでログインして、そらばんの利用者と対応づける。トークン（アクセス・リフレッシュ）は中継が暗号化して保管し、利用者の ID をキーにする（そらばんの DB には置かない）。`redirect_uri` の条件、トークンの有効期間・更新の仕組み、検証環境の利用可否は**未確定**。連携の開始は、利用者が「DIPS と連携する」を押し、DIPS のログイン画面へ移り、戻ったら中継が連携済みを記録する流れ（案）。トークン切れ（401）は「DIPS と再度連携してください」に倒し、送信は `failed`（確定した失敗）として記録する。
- 送信できない状態（連携していない、中継に届かない、機能フラグが無効）では、手動アダプターに自動で落とさない。画面で「API が使えません。手動の記録に切り替えますか」と利用者に選ばせる（二重通報を避けるため、勝手に切り替えない）。

### 10.7 監査の記録

`flight_report_attempts`（追記のみ。`soraban_app` は INSERT と SELECT だけ）に、ゲートウェイの呼び出し 1 回ごとに 1 行を残す。「誰が、いつ、何を送ったか」を後から示せる。

| 列 | 内容 |
|---|---|
| 誰が | 利用者（member）の ID と、その時点の表示名・役割の写し |
| いつ | 呼び出しの時刻（UTC。表示は JST） |
| 何を | 操作（`prepare`／`copy`／`submit`／`status`／`cancel`／`manual_record`）、通報の ID、冪等性キー、送った内容のハッシュと要約、項目の対応表の版、スナップショットの証跡 ID |
| どこへ | アダプター（`manual`／`mock`／`api`）、中継の要求 ID（中継の監査ログと突き合わせる） |
| 結果 | 成功／失敗／結果不明、HTTP の状態、エラーの種類、DIPS 側の番号（あれば） |

- 秘密（トークン、クライアント秘密）、個人情報の全文は監査に入れない。内容はハッシュと要約にとどめる（通報内容の全文は通報の記録に残る）。
- 手動のコピー・記録も同じ表に残す（誰が、いつコピー・記録したか）。

### 10.8 模擬アダプターと模擬サーバー

- 模擬アダプターは、`mock` の送信先として、模擬サーバー（`e2e/mock-dips-relay-server.mjs`。既存の `mock-gsi-server.mjs`・`mock-neon-auth-server.mjs` の流儀）を呼ぶ。本物の API アダプターと同じ経路（HTTP、署名つきの要求）を通すため、API アダプターの結合の確認にも使える。
- 模擬サーバーは、成功、確定した失敗（拒否）、401（トークン切れ）、500、時間切れ（結果不明）、同じ冪等性キーの再送を再現できる。drone-ops の「モックでの模擬通報」（障害の再現、重複の再現）を参考にする。**重複の判定などの模擬の振る舞いは、DIPS の実際の仕様ではなく、そらばん独自の仮定**であることを、模擬サーバーと画面（「模擬（開発用）」）に明記する。
- 模擬は、開発・CI・E2E でだけ使える（§10.1 の本番の拒否）。

## 11. API を取得したときの移行手順

「ユーザー作業」はユーザー（のりさん）が行う。「開発作業」は planner・generator・designer・evaluator が行う。エージェントは、本番の Neon・Vercel の環境変数・DIPS の資格情報に触れない。

| 順 | 区分 | 作業 | 完了の確認 |
|---|---|---|---|
| 1 | ユーザー | DIPS 2.0 API の利用申請書の【要記入】を埋めて送付（検証環境。HANDOFF §5）。接続システム URL は soraban.futuretec.jp | 申請の受理の通知 |
| 2 | ユーザー | 固定 IP の確認（会社の回線が固定か。検証環境は本社回線の想定）と、DIPS への接続元 IP の登録 | 登録の完了通知 |

### 12.3 契約テストの置き方（手動・模擬・将来の API で同じ）

**同じ画面・同じデータ・同じテストが、アダプターを替えても通ることを契約にする。**

1. **ゲートウェイの契約テスト（単体・結合）**：1 つのテスト群 `notificationGatewayContract(makeAdapter)` を、アダプターを引数に取る形で書く。確かめる不変条件：
   - `prepare` の結果が、同じ入力・同じ対応表の版なら、アダプターによらず同じ。
   - `submit` が同じ冪等性キーで 2 回呼ばれても、有効な通報は 1 件で、2 回目は既存の結果を返す。
   - `submit` の結果が、遷移表の許す状態で、証跡 ID・指紋・対応表の版・送信元を持つ。
   - 取消が別の行になり、有効な通報が無くなる。`canCancel` が偽なら、手動の記録に倒す。
   - 結果不明では自動で再送しない。確定した失敗は再送できる。
   - 監査の行が、操作ごとに 1 件できる。秘密を含まない。
   - 手動アダプターは、テスト用の補助（`manualResult` を与える）を通して同じ群に参加する。API アダプターは、検証環境か記録した応答（フィクスチャ）で同じ群を通す。**利用できるようになるまで `skip` とし、skip の理由と件数を CI に表示する**（通っていないことを隠さない）。
2. **E2E**：同じ Playwright のシナリオ（計画を作る → 通報内容を開く → 通報する／記録する → 番号と状態を確かめる → 変更 → 取消）を、`DIPS_REPORT_ADAPTER=manual` と `mock` の両方で流す。手動では「コピー → 記録」、模擬では「確認 → 送信」と、操作だけが違い、**画面の結果（状態、番号、証跡 ID、送信元の表示）と DB の行は同じ形で検証する**。将来、`api`（検証環境）を同じシナリオに加える。
3. **模擬サーバー**：`e2e/mock-dips-relay-server.mjs`。障害の再現は環境変数かテスト用の要求で切り替える。CI は外部に接続しない。
4. **契約の更新の規則**：API の仕様を入手して差分が見つかったら、模擬サーバーとテストを直し、契約テストの不変条件は原則変えない（変える場合は、§11 の手順 5 で planner が理由を文書に残す）。

### 12.4 12b の分量の判断

機能は 5 件（ゲートウェイと手動・模擬、通報の記録と監査、要否・期限・漏れ、契約テスト、済みの簡易記録）、契約 14 項目で、2 週間の目安の上限付近である。収まらない場合は §3.3 の削る順に従い、通報の変更の指紋比較を取消と新規の記録だけにする。ゲートウェイの契約テストと、手動・模擬の E2E の共通化は削らない（API 取得後の移行が軽くなる要になるため）。
