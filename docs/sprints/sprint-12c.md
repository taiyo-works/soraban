## 目的と位置付け

12a で「計画と判定の根拠」、12b で「通報の記録と期限」ができた。12c は、それらを**飛行の当日に一本の流れとして使える画面**にする。机では「今日」を開いて次にやることを上から順に片付け、現場では 1 つの飛行に集中して、**飛行前（点検・緊急用務空域・通報済みの再確認・携行品）→ 離着陸 → 日誌**を片手でつなげる。日誌は、計画の内容と実際の離着陸の時刻で自動入力され、計画の時間帯の外で飛んだことや、特定飛行なのに事前の通報の記録がないことは「知らせる」（保存は止めない）。

12c が終わると、利用者は次のことができる（North Star §0.1.10 の「トップの『今日』から次にやることを順にたどれば、手続きの漏れなく飛べる」）。

1. `/ops` を開くと、今日（なければ次）の飛行が大きなカード 1 枚で出て、その下に動詞で始まる「次にやること」が急ぐ順に並び、押すとその作業の画面へ直接移る。
2. スマホの下メニュー（今日／判定／計画／日誌／その他）で、全画面を移れる。
3. 現場モードで、片手・屋外・手袋の可能性を前提に、飛行前の確認、離陸・着陸の記録、日誌の保存までを行える。押し間違いは確認ダイアログでなく「取り消す」で戻す。
4. 通信が切れても離着陸の記録は端末に残り、戻ったら二重にならずに送られる。

## 12c の設計の判断（planner の判断。generator は sprint-12.md の記述でなく本書に従う）

| # | 判断 | 理由 |
|---|---|---|
| 1 | 離陸・着陸・飛行前の確認は、**追記専用の新しい表 `flight_field_events`** に 1 回のタップ = 1 行で残す。`record_versions`（版の履歴）は使わない。sprint-12.md §2.6 の `preflight_checks`（版の履歴）の案を、この 1 表に統合する | 離陸・着陸・確認は「その時刻にあった事実」で、訂正して版を重ねるものではない。誤りは「取り消す」（取消の行）で戻す。冪等性（`client_event_id` の一意）と端末の保存（設計 F）を単純にできる。`record_versions` のトリガー関数の置き換え（0008・0011・0013 と同じ作業）を避けられる |

### A. データモデル（マイグレーション 0014。追記のみ。generator が分けてよい）

**`flight_field_events`（現場の事実の行。追記専用）**

| 列 | 内容 |
|---|---|
| `id`、`org_id`、`plan_id` | `(plan_id, org_id)` は `flight_plans(id, org_id)` への複合外部キー |
| `kind` | `check`（飛行前の確認）／`takeoff`／`landing`／`undo`（取り消す）／`journal_linked`（日誌との結び付き）。CHECK |
| `item`、`result`、`source` | `check` のとき必須。`item` ∈ `inspection`（日常点検）・`emergency_airspace`・`report_recheck`（通報済みの再確認）・`carry`（携行品）。`result` は `emergency_airspace` が `not_designated`／`designated`、他は `done`。`source` は緊急用務空域の確認元（0〜100 文字。`emergency_airspace` は必須） |

| `occurred_at` | 事実の時刻（`timestamptz`、**1 分単位**）。端末の時計を元にするが、サーバーが範囲を検査する（設計 E） |
| `snapshot_id`、`plan_version` | 記録した時点の計画の現在のスナップショットと版（サーバーが入れる。リクエストの同名の値は読まない） |
| `gaps jsonb` | `takeoff` だけ。離陸の時点の**未了事項の写し**（サーバーが導出して入れる。設計 D） |
| `note` | 0〜300 文字（任意） |
| `queued` | 端末に保存してから送ったか（送信待ちの経由か）。表示に使う |
| `client_event_id` | 端末が付ける識別子（uuid）。`(org_id, client_event_id)` は一意 |
| `recorded_by_member_id` と表示名・役割の写し | 誰が押したか |
| `recorded_at`、`content_hash` | DB が決める。リクエストの値は読まない |

- 更新・削除・TRUNCATE を拒むトリガー（SB409 `immutable`。12a・12b の追記専用の表と同じ流儀）。`soraban_app` は SELECT・INSERT のみ。CHECK で `kind` ごとの必須の列を DB も守る。
- 状態の整合（離陸中に離陸はできない、着陸は開いた離陸が必要、など）は**アプリの遷移の関数が 1 か所で決める**（設計 B）。DB は列の整合と組織・計画の検査だけを持つ。ただし二重の離陸を並行リクエストですり抜けられないよう、サービス層は計画の行をロックして検査する。
- `packages/db/src/types.ts` に行の型と列の一覧を足し、`OPS_TABLES`・`TABLE_COLUMNS` に入れる。`MIGRATION_VERSIONS` を更新する。CI の db ジョブの `has_table_privilege` の確認に `flight_field_events`（INSERT=t・UPDATE=f・DELETE=f・TRUNCATE=f）を足す。

### B. 現場の状態（純粋関数。保存せず、行から毎回導出する。単体テストで全組合せ）

`apps/web/src/server/ops/field-logic.ts`（案）。入力は計画ごとの `flight_field_events`（取り消された行を除く）と、現時点の関連記録。

- **確認項目の状態**：項目ごとに「済（時刻・結果・情報源）／未」。同じ項目の最新の取消されていない `check` が有効。`inspection` は確認の行を持たず、**実際の日常点検の記録**（計画の機体・飛行日・飛行前）から導出し、行が無くても「済」になる（点検をした事実を二重に押させない）。異常ありの点検は「異常あり」と出す。
- **飛行（離陸 → 着陸）の組**：取り消されていない `takeoff` ごとに、対応する取り消されていない `landing` があれば「着陸済み」、無ければ「飛行中」。1 つの計画に複数回の離着陸がありうる（バッテリー交換など）。飛行中の離陸が開いている間は、次の離陸は 409（`already_in_flight`）。
- **日誌の状態**：着陸済みの飛行ごとに、取り消されていない（`voided_at` がない）飛行記録を指す `journal_linked` があれば「日誌済み」、無ければ「日誌待ち」。結び付いた飛行記録が後で取消されたら「日誌待ち」に戻る（導出なので自動）。
- **取り消す（`undo`）の規則**：`check`・`takeoff`・`landing` を取り消せる。`takeoff` は、取り消されていない `landing` があれば取り消せない（先に着陸を取り消す。409 `landing_exists`）。`landing` は、日誌済みなら取り消せない（409 `journal_exists`。誤りは飛行記録の取消＋再記録）。`journal_linked` と `undo` は取り消せない。
- **計画の状態による扱い**：中止した計画への新しい `check`・`takeoff` は 409 `plan_cancelled`。ただし**すでに開いている離陸の `landing` と、`undo` は、中止した計画でも記録できる**（飛んだ事実は止めない）。下書き・確認待ち・差し戻しの計画の離陸も止めない（未了事項として警告し、写しを残す）。

### C. 「今日」と次にやること（`/ops`。純粋関数 + 画面）

**今日の飛行の選び方**（純粋関数 `todayModel`）：

1. 「今日」は `nowOf(ctx)` の JST の日付。対象は、中止していない計画のうち予定開始が今日のもの。
2. 大きなカードに出す 1 件：飛行中の離陸がある計画 ＞ 今日の計画のうち、予定の終了が現在より後で最も早いもの ＞ 今日の計画がなければ、これから最も近い計画 ＞ なければ空の状態。
3. 残りの今日の計画は、カードの下に 1 行ずつ（時間・名称・状況の札）で出す。
4. 空の状態は「何がないか」と次にできること（「飛行計画を作る」「地点を判定する」）を一緒に出す。件数だけのタイルは作らない。
5. カードの内容：時間、名称、機体、操縦者、判定の段階（4 段のラベル）、通報の状況、確認の状況（既存の導出と文言をそのまま使う）。主ボタンは 1 つ：当日の計画は「現場モードを開く」、それ以外は「計画を開く」。
6. 操縦者役割の利用者には、自分が操縦者の飛行を先に出す（全員の計画は見られる。12a の規則）。

**次にやること**：今日から 7 日以内に始まる計画（と、飛行中・日誌待ちの計画）について、`planNextActions`（12b）の結果に、下の新しい項目を足し、`compareNextActions` で並べる（複数の計画をまたぐ）。上位 8 件を出し、「計画の一覧へ」を添える。**保存された状態は読まず、記録の有無から毎回導出する**。動詞で始まる 1 行、押すとその作業へ直接。`canAct` が偽のものは、リンクにせず「運航管理者に依頼」などと示す（12b と同じ）。

| 技能証明を更新する | 操縦者の技能証明の有効期限が 60 日以内（過ぎていれば tier 3）。**既存の列だけから導出。期限一覧は 12f** | 5（期限切れは 3） | 操縦者の編集 |

- 「日誌の食い違いを確認する」は、確認済みの記録を作らず、**直近 3 日間だけ**出る（時間で消える）。記録として残す確認は範囲外。
- 並び：`tier`、同じなら飛行開始までの時間が短い順（12b の `compareNextActions`）。既存の 12b の項目の tier・条件・文言は変えない。
- 点検の判定は、既存の `countInspectionsOn` と同じ規則（機体・飛行日）で、取消した点検を数えない。

**`/` の「今日」の帯**（削る順の③）：運航管理が有効でログイン済みの利用者が `/` を開いたとき、見出しの下の動的な部分（`OpsHomeEntry`）に、今日の飛行 1 行と次にやること上位 3 件を出す。**`/` は自動で転送しない**（sprint-12.md §7.2 の 2）。静的シェルは変えない。無効・未ログインでは何も描かず、追加の通信もない（12a の契約 18 のまま）。

### D. 未了事項（離陸の写し）と食い違い（純粋関数）

**離陸の未了事項（`takeoffGaps`）**：離陸の記録時にサーバーが導出して `gaps` に残す。項目は次のとおり。状態は短い語（例：`none`＝記録なし、`abnormal`、`designated`、`stale`、`changed`）で持ち、表示の文言は定数にする。

| 項目 | 未了と数える条件 |
|---|---|
| 日常点検 | 飛行前の点検が今日付けで無い。または異常あり |
| 緊急用務空域 | 確認の行が無い。または結果が「指定されている」 |
| 通報 | 要・要確認の計画で、有効な通報が無い。または指紋が変わっている（変更通報の要否を確認）。または通報の記録が離陸より後。**推奨・対象外（模型航空機）は数えない** |
| 確認（運航管理者） | 確認済みでない（下書き・確認待ち・差し戻し・前の版への確認） |
| 判定 | 判定が古い |
| 携行品 | 確認の行が無い |

- 未了事項があっても**離陸の記録は成功する**（201）。応答に未了事項を返し、現場モードの画面に警告として出し、離陸の行に写しを残す。画面の警告は「止める」文言にしない（「記録しました。次の項目が未了です」）。

**食い違い（`journalMismatches`）**：飛行記録 1 件と、結び付いた計画から導出する。計画なしの記録は食い違いなし（従来どおり「判定の根拠が紐づいていません」は 12a のまま）。

| コード | 条件 | 表示（例） |
|---|---|---|
| `outside_plan_window` | 離陸が計画の予定開始より前、または着陸が予定終了（開始 + 所要時間）より後 | 「計画の時間帯の外で飛行しています（離陸が 12 分早い／着陸が 8 分遅い）」。早い・遅いの分数を出す |
| `report_missing` | 計画の要否が要・要確認で、離陸の時点で有効な通報の記録が無い（通報の記録の `reported_at` が離陸より後のものは「有効」と数えない） | 「特定飛行ですが、離陸の時点で DIPS の通報の記録がありません」 |
| `report_after_takeoff` | 要・要確認で、有効な通報の `reported_at` が離陸より後 | 「通報の記録が離陸より後です。事前の通報として数えません」 |

- 機体・操縦者の違いは従来の `differs_from_plan` に任せる。**食い違いは `FlightDto.mismatches`（コードと表示と分数）で返し、一覧・詳細に出す。保存は止めない**（`POST`・`PATCH` の応答の `warnings` にも同じコードを足す）。
- 罰則や法令の条番号は画面に新しく書かない。「通報せずに特定飛行を行うと罰則の対象になりえます」の文言は 12b の定数（`※要確認`つき）を再利用する場合に限る。「通報不要」「通報は不要」「通報の必要はありません」「通報しなくて」は、どの出力にも含めない（12a 契約 15 の禁止語）。
- 一覧で食い違いを出すために、飛行記録ごとに計画・通報を引くと件数に比例してクエリが増える。**一括で引く**（飛行記録の ID の集合で計画と有効な通報をまとめて取得する）。

### E. API（すべて `opsHandler`。`OPS_ENABLED` 無効なら 404）

| メソッド・経路 | 内容 |
|---|---|
| `GET /api/ops/today` | `serverNow`、今日のカード、残りの今日の計画、次にやること（上位）。`result` 全体は読まず、一覧の要約の値だけを使う |
| `GET /api/ops/plans/[id]/field` | 現場モードの状態：計画の要約、確認項目の状態、飛行の組（離陸・着陸・日誌の状態）、離陸した場合の未了事項の予告、通報の状況（記録の日時・番号・「手動（利用者の申告）」）、点検の状態、`serverNow` |
| `POST /api/ops/plans/[id]/field-events` | 1 行を追記する。`kind`、`clientEventId`、`occurredAt`（JST 分）、`item`・`result`・`source`（確認）、`targetEventId`（着陸・取り消す）、`queued`、`note`。201。**同じ `clientEventId` で内容が同じなら新しい行を作らず既存を 200 で返す。内容が違えば 409 `request_conflict`**。離陸は未了事項があっても 201 で、応答に `gaps` を返す |
| `POST /api/ops/flights`（既存に追加） | `takeoffEventId`（任意）。あれば、同じ組織・計画の、着陸済みで日誌待ちの離陸であることを確かめ、飛行記録の作成と `journal_linked` の追記を**同じトランザクションで**行う。飛行記録の離着陸の時刻は、利用者が画面で直した値を保存する（イベントの時刻は事実として行に残る） |
| `GET /api/ops/flights`・`/flights/[id]`（既存に追加） | `mismatches`、結び付いた離陸の未了事項の写し（`takeoffGaps`）を返す |

- **時刻の検査（サーバー）**：`occurredAt` は JST 分の形。サーバーの現在（`nowOf(ctx)`）より 5 分を超えて未来は 400 `future_time`。`queued` でない（その場で送る）ときは現在から ±5 分を超えて離れていれば 400 `clock_skew`（「端末の時刻がずれています。時刻の設定（自動）を確かめてください」）。`queued` のときは過去 72 時間まで受ける（それより古いのは 400 `too_old`。画面は「あとから入力」へ案内）。
- 確認の `source` と `result` は、`emergency_airspace` のとき必須（400 `invalid_input` と項目ごとの理由コード）。`token`・秘密・個人情報（技能証明書番号・氏名）は行に入れない。
- 誤りの形は既存と同じ（400・403・404・409 `plan_cancelled`・`already_in_flight`・`no_open_flight`・`landing_exists`・`journal_exists`・`already_journaled`・`request_conflict`）。`route.ts` は薄く、処理は `server/ops/field.ts`・`today.ts` に置く。他の組織の計画・行は 404。

### F. 端末の保存（送信待ち。アウトボックス）— 圏外対応の範囲

- 現場モードの記録（確認・離陸・着陸・取り消す）は、送る前に**端末の `localStorage` に 1 行ずつ保存**し（`clientEventId` と `occurredAt` を付ける）、順番に送る。成功（201・200）した行を消す。通信できない・5xx・時間切れの行は残して再試行する（接続が戻ったとき、画面を開いたとき、画面を開いている間の 15 秒ごと）。**順序を守る**（古い行が送れないうちは後の行を送らない）。
- 4xx（業務上の拒否：`clock_skew`・`too_old`・`plan_cancelled`・`landing_exists` など）の行は**黙って捨てない**。「送れませんでした」と理由を行ごとに出し、利用者が「あとから入力」へ進むか、破棄を選べる。後ろの行は止めない（理由の行だけ飛ばす）。
- 画面に「未送信 N 件」を常に出す（0 件のときは「送信済み」）。離着陸のボタンは、送信待ちでも**押した時点で押下の結果を画面に反映**する（経過時間の表示など）。
- キーは利用者ごと（`drafts.ts` の流儀。`soraban:ops-draft:field-<計画の ID>:<利用者の ID>` など）。ログアウト時の消去は、**未送信が残っているときは警告し、黙って消さない**（「未送信 N 件があります。送ってからログアウトしますか」）。他の利用者の保存は `clearOtherUsersDrafts` が消す。端末に残す内容は、計画の ID・種別・時刻・識別子・確認の項目だけ（氏名・技能証明書番号・座標は入れない）。
- 日誌（飛行記録の保存）は、従来の「下書き + `clientRequestId` での再送」のまま（Sprint 11）。12c では、日誌の入力画面の初期値に使う現場の値（離着陸の時刻）を、送信待ちの行から取れるようにする（サーバーに届く前でも入力を始められる）。

### H. 現場モード（`/ops/plans/[id]/field`）

**前提：片手、屋外、手袋の可能性。** 「操作は親指だけ」「日差しで画面が見づらい」「指が大きい」を想定する。

- 上部：計画名・予定時間・機体・操縦者（1〜2 行）と「今日へ戻る」。ほかの計画への切り替えは、同日の計画があるときだけ上部の横並びボタン。**下メニューは出さない**（判断 7）。
- 段階の表示：①飛行前 → ②離着陸 → ③日誌 の 3 段を上に並べ、いまの段階を文字と形で示す（色だけにしない）。どの段階も押せる（順序を強制しない。強制すると事実の記録を止める）。
- **①飛行前**：次の 4 項目を、1 項目 1 行・全幅のタップ領域で並べる。各行に「済（時刻）／未」を文字で出す。
  1. **日常点検**：今日付けの飛行前の点検があれば「済」（点検した時刻・異常の有無）。異常ありは「異常あり」を目立たせ、「飛行を止めて不具合を確認」と案内する（止めはしない）。無ければ「日常点検をする」ボタン（日常点検の入力へ。保存後に戻る）。
  2. **緊急用務空域の確認**：「確認した」を押す前に、情報源（選ぶ）と結果（指定されていない／指定されている）を選ぶ。**「指定されている」を選べば、飛行できない旨の最上位の警告**を出す。記録は残る。
  3. **通報済みの再確認**：12b の通報の状況を再掲する（「DIPS で通報済み（利用者の申告・手動記録）：日時・番号」または「通報の記録がありません」または「計画が通報時から変わっています」）。有効な通報があれば「通報内容を再確認した」で確認の行が残る。要・要確認で記録がなければ警告と「通報内容を開く」。**推奨・対象外の計画は「この飛行は通報の記録を必須としません（推奨）」の趣旨を文言の定数で出す**（「通報不要」とは書かない）。
  4. **携行品**：計画の許可・承認の番号（あれば）を表示し、「必要な書類・携行品を確認した」で確認の行が残る。法令の条番号は書かない。
- **②離着陸**：押す大きなボタンは**常に 1 つ**。状態に応じて「離陸」→（飛行中は）「着陸」に変わる。
  - 離陸を押すと、**確認ダイアログは出さず**に記録する。直後に「離陸 14:03 を記録しました。取り消す」の帯を出し、未了事項があれば「次の項目が未了です：…」を併記する（記録は成功している）。
  - 飛行中は経過時間を大きく出す。押した直後の二度押しは 1.5 秒無視する（サーバーも `clientEventId` で二重にしない）。
  - 着陸を押すと同様に記録し、「日誌を記入する」へ進める。着陸の時点で計画の時間帯の外なら「計画の時間帯の外です」と知らせる（記録は止めない）。
  - 離着陸を何回でも繰り返せる（次の離陸のボタンが戻る）。
  - 「時刻を入れて記録する（あとから入力）」は、日誌の入力（時刻が空）へ移る別の入口として小さく置く。
- **③日誌**：着陸済みで日誌待ちの飛行があれば、日誌の入力（計画の機体・操縦者・目的・場所・特定飛行の形態、離着陸の時刻、飛行前の点検が入った状態）を開く。利用者が「安全に影響のあった事項」だけ確かめて保存できる。保存後に食い違いがあれば知らせる。
- **見た目の基準（契約 15）**：
  - タップ領域：離陸・着陸ボタンは高さ 80px 以上・幅いっぱい（画面下半分の親指の届く位置）。ほかの押す部品は高さ 56px 以上。隣り合うタップ領域の間は 12px 以上あける。
  - 文字：本文 18px 以上、状態の語（済・未・異常あり・飛行中）は 20px 以上で太く、経過時間は 48px 以上の等幅数字。
  - コントラスト：本文と主要ボタンの文字は背景との比 7:1 以上、そのほか（補助の文字・枠）も 4.5:1 以上。**明るい配色と暗い配色（`prefers-color-scheme`）の両方で満たす。** 日差しの下を既定に考え、淡い灰の文字・細い線に頼らない。
  - 状態は**文字 + 形（記号）**で示し、色だけで区別しない。押した結果は文字で返す。
  - `touch-action: manipulation`（ダブルタップ拡大を止める）、ホバーだけに頼る操作を作らない。
  - 飛行中は画面の消灯を防ぐ（Screen Wake Lock API。対応端末かつ HTTPS のときだけ。対応しない端末では静かに何もせず、控えめな注記を出す）。画面が隠れたら解放し、戻ったら取り直す。

### J. テスト環境の時計と端末

- E2E-DB のサーバーの時計は `OPS_TEST_NOW`（JST 2027-01-05 12:00）。**ブラウザの時計も Playwright の `page.clock` で同じ時刻に合わせる**（端末の時刻を元にする `occurredAt` がサーバーの検査と合うように）。時計のずれの検査（`clock_skew`）は、時計をずらして別に確かめる。
- 圏外は `context.setOffline(true)` で再現する。ブラウザの Wake Lock は、単体テストで `navigator.wakeLock` を差し替えて確かめる（E2E の実機検証は範囲外）。
- 色の比は、Playwright で計算した色（`getComputedStyle`）から WCAG の式で計算する補助関数を `e2e/` に置き、明るい配色と暗い配色（`colorScheme` の切り替え）で主要な要素を検査する。

### 圏外対応（Service Worker）を範囲外にした理由と、将来の縛り

| 論点 | 判断・理由 |
|---|---|
| なぜ入れないか | ①認証が要る画面（操縦者の氏名・技能証明書番号・飛行場所を含む）を端末にキャッシュすると、共用端末・紛失・ログアウト後の残りの扱いが新しい設計課題になる。②Next.js 16（`cacheComponents`）と Service Worker の相互作用は未確認で、古い画面が出続けて通報・判定の「新しさ」を損なうリスクがある（North Star §0.1.9：古い判定を信じない）。③山陰の現場の通信状況は未確認（Sprint 11 未決 4）。現場試用の結果で必要性を判断する。④離着陸・確認の**事実の記録**は端末の送信待ち（設計 F）で守られ、日誌は従来の下書きと再送で守られる。圏外で失われるのは「画面の読み込み」だけで、記録ではない |
| 将来入れる場合の縛り（契約にするなら） | ①書き込みは今の送信待ちの経路だけを使い、`clientEventId` で二重を防ぐ（Service Worker から別経路で書かない）。②キャッシュするのは静的な資産と、今日から 3 日間の計画の要点（個人名・技能証明書番号を含まない）に限る。③ログアウトで、キャッシュと送信待ちの未送信を確認のうえ消去する。④判定の新しさ（スナップショットの鮮度）は圏外でも表示の古さを示す（「最終更新 …」）。⑤追記専用の記録（離着陸・確認・通報）を端末で書き換えない |

### B. 日誌への引き継ぎと食い違い

- [ ] 4. （DB・API・単体）`POST /api/ops/flights` に `takeoffEventId` を付けると、飛行記録の作成と `journal_linked` の追記が同じトランザクションでできる（片方が失敗すれば両方残らない）。着陸していない離陸・取り消された離陸・他の計画の離陸・すでに日誌済みの離陸は拒否される（400／409 `already_journaled`）。同じ `clientRequestId` の再送は 1 件のまま。利用者が時刻を直して保存すると、飛行記録は直した値で、離着陸の行は元の時刻のまま残る。飛行記録を取消すと、その飛行は「日誌待ち」に戻る。**計画の予定時刻が飛行記録の離着陸の時刻に入る経路がない**（`planId` だけで開いた入力、`takeoffEventId` がない保存では、時刻は空・入力どおりであることをテストで確かめる）。

### E. 現場モード

## 分量の判断と削る順

機能は 5 件（今日と次にやること、下メニュー、現場の事実の記録、現場モードの画面と見た目、日誌の引き継ぎと食い違い）に、端末の保存と画面の消灯が付く。契約 18 項目は §13.6 の目安（10〜20）に収まるが、1 項目あたりの検証は重い（契約 1・3・5・11・13）ため、2 週間の上限付近と見る。圏外対応（Service Worker）は最初から範囲外にしてあり、sprint-12.md §3.3 の削る順①をすでに適用している。遅れたときに削る順：

1. 〔Service Worker による圏外対応〕 — **適用済み（範囲外）。**
2. 画面の消灯の防止（契約 14。離着陸の記録・経過時間は残す）。
3. `/` の「今日」の帯（契約 16 の帯の部分。入口の維持と自動で転送しないことは残す）。
4. `/ops/journal` の最近 14 日の合算の一覧（契約 9。入口の 2 つのボタンと切り替え、下メニューの現在地は残す）。
5. 「技能証明を更新する」と「日誌の食い違いを確認する」の次にやること（契約 6 の該当項目。食い違いの札と警告は残す）。

**削らないもの**：「今日」（カードと次にやること）、下メニュー、現場モード（飛行前 → 離着陸 → 日誌）、離陸の記録を止めないこと、取り消す、追記専用の `flight_field_events`、計画の予定時刻を離着陸に入れないこと、端末の保存（送信待ち）の順序・二重防止・黙って捨てないこと、片手・屋外の寸法とコントラスト、「通報不要」を出さないこと。

## リスク

| リスク | 備え |
|---|---|
| 離陸の記録を止めない方針で、未了のまま飛ぶ癖がつく | 未了事項を離陸の直後に目立たせ、離陸の行に写しを残し、飛行記録の詳細に表示する。後の証跡出力（Sprint 15）で見られる。止めるのは事実の記録を失わせるため採らない（sprint-12.md §7.2 の 7） |
| 端末の時計のずれで、事実の時刻が狂う | サーバーが範囲を検査し（`clock_skew`・`future_time`・`too_old`）、その場の送信が大きくずれると拒否して時刻の設定を案内する。運用の決めごと（スマホの時刻は自動設定。HANDOFF §5）。送信待ちの行は 72 時間まで |
| 送信待ちの行が二重・順序違いで送られ、状態が壊れる | `clientEventId` の一意と同一内容の再送は既存を返す。送信は順序を守る。状態の遷移はサーバーの 1 か所の関数で決め、計画の行をロックして並行を防ぐ |
| 端末に個人データが残る | 送信待ちには計画の ID・種別・時刻・識別子・確認の項目だけを入れ、氏名・技能証明書番号・座標を入れない。利用者ごとのキー、ログアウトの警告、他の利用者の保存の消去 |
| 屋外で見えない・押せない | 寸法と配色の基準を契約にし、明暗両方で計算して検査する。実機の屋外確認はユーザー作業（下）。見た目の最終判断は現場試用で |
| 「今日」の次にやることの計算が重い（計画の数 × 通報・記録の取得） | 対象を 7 日以内の計画と飛行中・日誌待ちに限る（社内 10 名以内）。一覧の要約と同じ「必要な値だけを取る」作法を使う。件数が増えたら範囲を絞る |
| 食い違いの導出で一覧のクエリが飛行記録の件数に比例する | 一括の取得を契約 5 で縛る |
| `/ops` を作り替えて既存の E2E の期待が崩れる | 変えるのは `/ops` の内容だけ。経路・`data-testid`・機能は他の画面で保つ。更新するのは `/ops` の期待値だけ（契約 17） |
| 下メニューが `/` の静的シェルを壊す | 動的な部分（Suspense の内側）で出す（12a 設計 J と同じ）。ビルドの出力で確かめる（契約 8） |
| 緊急用務空域の情報源の名称を誤る | 新しく名称・URL を作らず、`@soraban/regulations` の参照先の定数だけを選択肢にする。確認先の正式な運用はユーザーに確かめる（下の U13） |
| 完全な圏外で画面が開けない | 範囲外にしたことを画面（現場モードの注記）と文書に明記。現場試用で必要なら別の枠で、「圏外対応を入れる場合の縛り」に沿って足す |
| 12 全体の規模が大きく 02-19 に収まらない | 上の削る順 |
