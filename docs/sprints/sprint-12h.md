### 2.3 PR にする前にすべきこと（統合）

1. 5 本を別々に PR にしない。同じ差分が 5 回 CI を通るため。`design/plan-system`（この計画の文書を足して）を **PR ① 1 本**にする。
2. PR ① の前に、手元で `pnpm typecheck`・`pnpm lint`・`pnpm test`・`pnpm build`・`pnpm test:e2e` を通す（この計画の作成では未実行）。
3. PR A の evaluator 合格レポートを取る（12g-1b の A14）。
4. 統合した 5 ブランチは、マージ後にのりさんの指示で削除する。

### 2.4 PR の分け方

| PR | 内容（design-system §12 の段階） | 公開 `/` への影響 | 戻し方 |
|---|---|---|---|
| **①** 統合 | 文書、トークン CSS、見本、PR A（`/ops` の骨組み）＋段階 B（`--sb-*` の取り込み。見た目は変えない） | なし | revert 1 回（マイグレーションなし） |
| **②** 判定画面 | 段階 C の前半（フォント、`.ds` の色の付け替え）、D のうち `/` が使う部品、G（公開ページ）。シート UI、PC 3 ペイン、層の一覧、現在地の即判定 | **あり**（単独。実機確認が済むまでマージしない） | revert 1 回 |
| **③** 運航管理 | 段階 C の後半（左メニュー・下タブ・ハンバーガー）、D の残りの部品と各画面の置き換え | なし（`/ops` は本番で 404） | revert 1 回 |
| **④** 現場モード・動き・後始末 | 段階 E、F、H と旧トークンの削除 | 旧トークンの削除のみ（見た目は②で済み） | revert 1 回 |

**順序の理由**：①は見た目を変えず、CI で DB のテストを初めて通すための土台。②は本番に出る唯一の変更なので、③の大きな差分と混ぜない。③は `/ops` が本番で見えず、②で作った部品をそのまま使える。④は動きが入るため最後に置き、旧トークンの削除は②③が終わってからでないとできない。

**GitHub Actions を抑える進め方**

| 事実 | 内容 |
|---|---|
| 動く条件 | `pull_request` と main への push。ブランチへの push だけでは動かない。`docs/**` と `*.md` だけの変更は動かない（`ci.yml` を確認） |
| 1 回の重さ | verify・e2e・db の 3 ジョブ（のりさんの目安で各 15〜25 分）＋ smoke（最長 5 分、止めない）。pnpm と Playwright のブラウザはキャッシュが効く。OS の依存パッケージは毎回入れる |
| 見積り | 1 PR 1 push なら 4 PR で 3 ジョブ × 4 = 12 ジョブ（約 180〜300 分）。各 PR 2 push までを見込むと最大 24 ジョブ（約 360〜600 分）。同じ PR への続けての push は古い実行が止まる |
| 進め方 | ①②③④とも、generator → designer → evaluator を手元で回し切り、K2 の検査を通してから PR を作る。ドラフト PR でも CI は動くので、早めに作らない。PR 作成後の修正はまとめて 1 回 |
| 実機確認 | Vercel の Preview はブランチを push すると作られる見込み（Actions は使わない）。②は **PR を作る前に**ブランチの Preview で実機確認できる。ただし carta-lab への転送後の Git 連携と、Preview の保護設定は**未確認**（§11） |

   - 単体：`regulation-map.tsx` 以外で `once("load"` を呼ばない（grep のテスト）。
4. **層の一覧と判定の対応を固定**：一覧の各行 ↔ 地図の層 ID ↔ 判定の規則の表を単体テストで固定する。層を足す・消すと落ちる。「準備中」の行は、層 ID も規則も持たない。
5. **精度の表示**：現在地の精度は取得値を整数の m で表示するだけ。判定には送らない。

## 12. のりさんに決めてほしいこと（最大 5 つ。推奨つき）

1. **範囲と PR の分け方**：4 本（①統合 ②判定画面 ③運航管理 ④現場モード・動き）でよいか。12g の段階 2〜3b にある機能の追加（並べ替え、保存済みビュー、CSV、右の詳細パネル、地点の地図ワークスペース、コマンドパレット）は、12h に含めず、12f（期限一覧）のあとで計画し直す形でよいか。**推奨：4 本、機能の追加は含めない**（含めると ③ が 12g の段階 2〜3b、見積り約 4 週間分に近づく）。
2. **スマホの下タブの右端**：design-system の決定 9 は「丸いハンバーガー」、決定 10 は「主要な導線を隠さない。名称は『登録』」で、PR A の実装は文字つきの「登録」タブ。丸いハンバーガーに「登録」の文字を常に添えてよいか。**推奨：丸の下に「登録」の文字を添える**（名称を画面に残す）。
3. **視差（パララックス）**：design-system §8 は視差を禁止にしている。依頼の文に「パララックス」があったので確認する。**推奨：入れない**（④の動きは、起動画面の拡大と色の膜、せり上がり 1 回、メニューのふわっとだけ）。
4. **「準備中」の使い方**：判定に使っている層（空港周辺・対象施設・公園・文化財・密集施設）は、公開資料からの概算なので「概算」と書き、「準備中」は DIPS の群にあるのに収録していない層だけに使う、でよいか。緊急用務空域（動的な情報）を「準備中」にするかも。**推奨：3 区分（公式データ・概算・準備中）。緊急用務空域は「地図に出さない」の 1 行**（使っている層を使っていないように見せない）。
5. **スマホで、運営者・利用の範囲・対象地域を判定票の中に置く**：1 行の要約には「参考情報」だけ、残りは判定票を開いた先頭の「このサービスについて」。PC は概要の帯に常時出す。**推奨：この置き方**（確定事項の「免責の全文は判定票を開いたとき」に合わせた。運営者の常時表示が必要かは未確認）。
