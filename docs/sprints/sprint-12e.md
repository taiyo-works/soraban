## 目的と位置付け

飛行の事後（sprint-12.md §2.2 の段階 8）のうち、**事故とヒヤリハットを、事実として確実に残す**スプリント。現場で何かが起きたとき、まず人の安全を確保してもらい、そのあと（または現場では最小の操作で）起きたことを記録し、飛行計画・日誌・機体・操縦者と結びつけ、国への報告の要否を確かめる手がかりと、報告した結果の記録を残す。

12e が終わると、利用者は次のことができる。

1. 事故・ヒヤリハットの入力画面を開くと、**最初に「人の安全を確保してください」という案内**が出る。入力はそのあとでよい。
2. 現場モードから、**2 回のタップほどで簡易に記録**できる（区分・けがの有無・時刻。詳細はあとで補う）。通信が切れても端末に残り、戻ったら二重にならずに送られる。
3. 事務所で、起きたこと（事実の項目、経過、とった対応、考えられる要因、再発防止）を詳しく記録し、あとから訂正できる（訂正は版として残る）。
4. 入力した事実から、**「報告の対象になる可能性があるか」の目安**が出る。目安は確認の手がかりであり、報告の要否を決めない。
5. 国への報告を DIPS 2.0 等で行ったら、その結果（日時・番号）を**利用者の申告として記録**できる。要否を国土交通省などに確かめたことも記録できる。
6. 飛行計画・日誌の画面から、その飛行に関する事故・ヒヤリハットへ移れ、日誌の「安全に影響のあった事項」から記録を始められる。

### 安全の原則（不可侵）

- **記録は事実の記録であり、法的な報告の完了も、責任の判断も意味しない。** この旨を、事故・ヒヤリハットのすべての画面に固定の注意書きとして出す（設計 A の N1）。
- **報告の義務の有無を、アプリは断定しない。** 「報告不要」「報告対象外」「報告の必要はありません」と出さない。同時に「報告が必要です」「報告義務があります」とも出さない（どちらも一次資料が未照合。U5・U17）。目安は「報告の対象になる可能性があります／入力の範囲では選ばれた事象がありません。どちらも要否は公式の案内で確認」の 2 段だけで、分からないときは可能性の側（厳しい側）に倒す。
- **報告の様式・期限・報告先を、数値や名称でアプリが断定しない。** 「○日以内」「○時間以内」「○営業日」の期限の表現、罰則の額、様式の項目名、報告先の窓口名を、画面・API・データに作らない。一次資料を確認する作業は U17・U18。確認できるまで「※要確認」を付け、確認できたら**データの更新だけで反映できる形**にする（設計 C の目安の規則表）。
- **そらばんは国へ報告を送信しない。** 報告は DIPS 2.0 などの公式の手続きで行う。記録は利用者の申告で、そらばんが報告の完了を確認したものではない（12b の通報の記録と同じ作法）。
- **救護・安全の確保が先。** 入力を求める前に案内を出し、入力が済まなくても人命に関わる行動を妨げない。
- **個人を特定する情報を記録しない。** けがをした人・第三者の氏名、連絡先、病状の詳細、写真は扱わない（設計 B）。
- 「通報不要」の語は、どの画面・文言にも出さない。条番号・URL は `packages/regulations/src/model-aircraft.ts` にだけ置く方針のまま、**12e は条番号も URL も新しく書かない**（設計 A）。判定エンジン・`ENGINE_VERSION`・証跡 ID は変えない。

## 12e の設計の判断（planner の判断。generator は sprint-12.md の記述でなく本書に従う）

| # | 判断 | 理由 |
|---|---|---|
| 1 | 事故・ヒヤリハットの記録は `record_versions`（`entity_type = incident_record`）に追記し、ヘッド表 `incident_records` を DB が作る。訂正・取消は版（理由必須）。物理削除なし | あとから事実を足す・直す記録のため。12a・12b・12d と同じ作法（ハッシュ連鎖、`verify_record_chain`、`soraban_app` はヘッド表を直接書けない） |
| 2 | **国への報告の記録は別の追記専用表 `incident_report_records`** に残す（報告した／要否を確かめた／取り下げ）。`record_versions` は使わない | 「いつ、誰が、何を申告したか」は事実で、訂正して版を重ねるものではない（12b の `plan_procedure_records`、12c の `flight_field_events` と同じ判断）。誤りは取り下げの行で戻す |
| 3 | **sprint-12.md の目安の出し方を改める。** 当初案の「事故／重大インシデント／報告対象外／要確認」の 4 段をやめ、**「報告の対象になる可能性がある」「入力の範囲では選ばれた事象がない」の 2 段**にする。「報告対象外」は出さない。事故・重大インシデントの法令上の区分も、アプリは出さない | 「報告対象外」と出すのは報告の義務がないと断定することで、一次資料が未照合（U5・U17）の間は誤りになりうる（12a が「通報不要」を禁止語にしたのと同じ理由。North Star §0.1.9「分からないときは厳しい側」）。区分は利用者が自分の言葉で選ぶ（判断 4） |
| 4 | **「事故／ヒヤリハット／まだ分からない」は、利用者が選ぶ区分**であって、法令上の事故・重大インシデントの判定ではない。画面に「法令上の区分ではありません」と書く | アプリが法令上の区分を決めると、判断の誤りが利用者の報告漏れになる。区分は一覧の整理のためだけに使う |
| 5 | 目安の事象の項目（けが・他人の物の損壊・機体の損傷・制御不能・他の航空機との接近・発煙発火）と、どれが目安に効くかは**版つきのデータ**（`INCIDENT_GUIDANCE_REVISION`・状態 `unconfirmed`）に持つ。**現時点ではどの項目も「あり」または「わからない」なら可能性ありに倒す**（安全側の広めの設定）。一次資料を確認できたら（U17）、データの更新だけで絞り込める | 項目の絞り込みは法令の理解に依るため、確認前は広く拾う。画面に「事象の区分は国土交通省の案内と未照合（※要確認）」と目安の版を出す |
| 6 | 目安は**記録の保存のたびにサーバーが事実から計算して版の中に残す**（画面の値は読まない）。後で規則の版が変わっても、過去の版には当時の目安と規則の版が残る | 「当時は何を根拠に何を表示したか」を辿れるようにする（根拠の鎖の考え方） |
| 7 | **個人を特定する情報は列にも自由記述の想定にも置かない。** けがをした人の人数（0〜999）と有無だけを持ち、氏名・連絡先・病状の詳細は持たない。写真・画像は扱わない。操縦者は `pilot_id` だけを持ち、氏名は表示のたびに引く | 10 名以内の社内でも、記録は版として消せないため。`schema-columns.test.ts` の禁止語にも当たらない。自由記述には「書かないでください」の注意書きを出す（N5） |
| 8 | 現場の簡易記録は、**選択肢だけ**（区分・けがの有無・時刻・計画の ID）を端末に保存して送る。自由記述は端末に残さない。簡易記録は `detail_pending = true` で保存し、残りの事実の項目は「わからない」にする（目安は可能性ありに倒れ、あとから詳細を補う次にやることが出る） | 圏外・混乱の中で入力を減らしつつ、端末に個人データや座標を残さない（12c の端末保存の規則を守る）。「わからない」を既定にするのは、「なし」と誤って記録しないため |
| 9 | 簡易記録は 12c の `ops-outbox` を**そのまま拡張せず**、同じ規則（localStorage＋メモリのフォールバック、順序、4xx を黙って捨てない、`clientRequestId` による冪等性、利用者ごとのキー、ログアウトの警告）の**別の小さなモジュール**にする。共通にできる純粋な補助関数は import して再利用してよいが、12c の export の型・挙動・テストは変えない | `OutboxKind` は 12c の閉じた型で、変えると 12c の契約・テストに波及する。キーは `soraban:ops-draft:incident-<計画の ID>:<利用者の ID>`（`soraban:ops-draft:` の配下にして `clearOtherUsersDrafts` で消える形） |
| 10 | 書き込みの権限：**作成と報告の記録は運航管理者と操縦者**（操縦者は誰の飛行でも事実を記録できる）、**訂正・報告の記録は運航管理者と「自分の分」（記録を作った本人か、記録の操縦者が自分）**、**取消（誤登録）は運航管理者のみ**、閲覧者は読むだけ。閲覧は全役割 | 事実の記録を「自分の飛行でないから」と妨げない（12c が離陸の記録を止めない方針と同じ）。取消は記録が消えたように見えるため運航管理者に限る |
| 11 | 日誌の「安全に影響のあった事項」から**記録の入力へ移るリンク**は付けるが、事故・ヒヤリハットの記録を**自動で作らない**。`flight_records` に列を足さない。結び付きは事故・ヒヤリハット側（`flight_record_id`）に持つ | 既存の日誌の列・保存の挙動を変えない。自動で記録すると誤記録になる |
| 12 | 事故・ヒヤリハットの記録は**飛行計画がなくても作れる**（計画の ID は任意）。計画があれば、機体・操縦者・場所を引き継ぎ、そのときの現在のスナップショットの ID を記録する | 点検中・計画外の飛行・地上での取り扱い中のヒヤリハットも残すため |
| 13 | 通知（メール・プッシュ）、社内の緊急連絡先の表示、保険会社への連絡、機体の自動休止は**範囲外**。次にやること（「今日」）への表示だけ行う | 範囲を抑える。連絡先は社内で決める事項（U19）。機体の休止は Sprint 13 の点検整備と合わせる |

### C. 純粋関数（`apps/web/src/server/ops/incident-logic.ts`（案）と、画面も使える `apps/web/src/lib/ops-incident.ts`（案）。DB・時計・ネットワークに触れない）

**事実の項目（版つきのデータ。`INCIDENT_GUIDANCE_REVISION = 1`、状態 `unconfirmed`）**

| キー | 画面の名称（案） | 目安に効くか |
|---|---|---|
| `people_injury` | 人のけが（亡くなった場合を含む） | あり／わからない → 可能性あり（※U17 で確認） |
| `property_damage` | 他人の物の損壊（建物・車・設備など） | 同上 |
| `aircraft_damage` | 自社の機体の損傷 | 同上 |
| `loss_of_control` | 制御不能・墜落・不時着・行方不明 | 同上 |
| `aircraft_contact` | 他の航空機との衝突・接触・接近 | 同上 |
| `fire_smoke` | 発煙・発火（バッテリーを含む） | 同上 |

- 項目の追加・効き方の変更（U17 の結果）は、このデータの更新だけで済み、型・画面は変えない。

**`incidentGuidance(facts, kind)`**：
- `kind` が `accident` または `undetermined`、または事実の項目のどれかが `yes`／`unknown` なら `possible`。それ以外（区分が `near_miss` で、6 項目すべて `no`）だけ `none_selected`。
- 出力は `{level, revision, reasons}`（`reasons` は当たった項目のキー）。**「報告不要」「対象外」に当たる値・文字列を返さない。**
- 3 段の組合せ（6 項目 × 3 値 × 区分 3 種）を単体テストで全数確かめる。

**`validateIncident(input, mode)`**（`mode`＝`full`／`quick`）：
- `full`：区分・起きた日時・`summary`（1〜200 文字）・事実の項目 6 つ（すべて選択が必須。既定の値を置かない）。`quick`：区分・起きた日時・`fact_people_injury` だけが必須で、残りの事実の項目はサーバーが `unknown` にし、`detail_pending = true`、`source = field_quick`。
- 長さ・値域（人数 0〜999、座標の対、`contacts_made` の値と重複、`follow_up_status`／`follow_up_on` の整合）を項目ごとの理由コードで返す。禁止語（設計 A）の不在を確かめる。

**`incidentReportState(records, currentFingerprint)`**：`reported`（有効な報告の記録あり）／`consulted`（報告の記録はないが、要否を確かめた記録あり）／`none`。さらに `changedSinceReport`（有効な報告・確認の記録の指紋が現在の指紋と違う）。

**`incidentNextActions(...)`**：記録の有無から毎回導出する（保存しない）。文言は `NEXT_ACTION_LABEL` に足す。

| 次にやること（動詞で始まる） | 条件（導出） | 押すと |
|---|---|---|
| 事故・ヒヤリハットの報告の要否を確認する | 目安が `possible` で、報告の記録も要否を確かめた記録も無い。または `changedSinceReport` | 記録の詳細（報告の記録のフォーム） |
| 事故・ヒヤリハットの詳細を記入する | `detail_pending`（取消されていないもの）。起きた日から 14 日以内（社内の目安） | 記録の訂正 |

- tier は 12b の表（通報の漏れ・目安の超過・未了）に合わせて generator が決め、完了報告に書く（要否の確認は通報の漏れと同じ重さ、詳細の記入は日誌と同じ重さを推奨）。期限の日付は作らない。`canAct` が偽（閲覧者など）のものは、リンクにせず「運航管理者に依頼」と示す（12b・12c と同じ）。
- 既存の `planNextActions` の期待（12b）と「今日」の並び（12c）は変えない。計画に結び付かない記録の次にやることも出せる形にする。

### F. 現場の簡易記録と端末の保存

**入口**：現場モード（`/ops/plans/[id]/field`）の上部に、**常に見える小さめの帯（高さ 56px 以上・全幅）**「事故・ヒヤリハットを記録する」を 1 つ置く。離陸・着陸の大きなボタンの**隣・直上・直下に置かない**（誤タップを避ける。離着陸ボタンとの距離は 24px 以上）。押すと簡易記録の画面へ**移動する**（その場で記録されない。確認ダイアログは出さない）。12c の「押す大きなボタンは常に 1 つ」は変えない（この帯は大きなボタンではない）。

**簡易記録の画面**：①G1（最上部）→ ②N1 → ③区分（3 つ）→ ④けがの有無（3 つ）→ ⑤「そのほかの事実はあとで入力できます」（折りたたみ。開くと残りの事実の項目）→ ⑥「記録する」（全幅）。時刻は「いま」を既定にする。保存の直後に「記録しました。詳細はあとで記入できます」と、「詳細を記入する」「現場モードへ戻る」を出す。記録は残る（取消は運航管理者）。N2 を完了後に出す。

**端末の保存（送信待ち）**：12c の設計 F の規則を、簡易記録に適用する。

- 押した時点で、端末の `localStorage`（保存できなければメモリ）に 1 行保存し、`clientRequestId` と `occurredAt` を付けて自分のサーバーの API だけへ送る。成功（201・200）で消す。通信できない・5xx・時間切れは残して再試行する（接続が戻ったとき、画面を開いたとき、開いている間の 15 秒ごと）。順序を守る。
- 4xx（`clock_skew`・`too_old` など）の行は**黙って捨てない**。理由を出し、「あとから入力」（詳細な入力画面）へ案内し、破棄は利用者が選ぶ。
- 画面に「未送信 N 件」を常に出す（0 件は「送信済み」）。押した結果は送信の前に画面へ反映する。
- 端末に残す内容は、計画の ID・区分・けがの有無・時刻・識別子だけ。**氏名・技能証明書番号・座標・自由記述は入れない。** キーは `soraban:ops-draft:incident-<計画の ID>:<利用者の ID>`。ログアウトは未送信があるとき警告し、黙って消さない（12c と同じ）。他の利用者の保存は `clearOtherUsersDrafts` が消す。
- 12c のモジュールは export の追加を除き変更しない（判断 9）。

### G. テスト環境と E2E の作法

- サーバーの時計は `OPS_TEST_NOW`（JST 2027-01-05 12:00）。ブラウザの時計は `page.clock` で合わせる（12c・12d と同じ）。圏外は `context.setOffline(true)`。
- **過去の教訓：E2E で `waitForResponse` を `goto` の後に登録しない。** 応答が先に届くと待ち続ける（CI で起きた。`e2e/ops-db/sprint12a-db.spec.ts` の注記）。応答を待つときは、操作の**前**に `Promise.all([page.waitForResponse(...), 操作])` で登録するか、画面に結果（文言・要素）が出るまで待つ。generator・evaluator はこの書き方を守る。
- 色の比は 12c の補助関数（`e2e/field-checks.ts`）を再利用し、簡易記録の画面を明暗両方で検査する。
- 通常の E2E：`e2e/sprint12e.spec.ts`。DB あり：`e2e/ops-db/sprint12e-db.spec.ts`。

## デザイン 4 基準の観点（designer 向けの注意点）

| 観点 | 注意点 |
|---|---|
| 現場で使う画面の大きさ | 現場の簡易記録は、片手・屋外・手袋を前提にする。押す部品は高さ 56px 以上、隣との間は 12px 以上、本文 18px 以上、状態の語は 20px 以上で太く。選択肢（区分・けがの有無）は縦に並べ、1 つ 1 行・全幅にする。「記録する」は画面の下寄りの親指が届く位置に全幅で置く。現場モードの帯は大きなボタンにしない（離着陸の「1 つの大きなボタン」を保つ） |
| コントラスト | 本文・主要ボタンの文字は背景との比 7:1 以上、そのほかも 4.5:1 以上。**明るい配色と暗い配色の両方**で満たす。日差しの下を既定に考え、淡い灰の文字・細い線に頼らない。G1（最初の案内）は、入力欄より目立つが、警告の赤一色にしない（落ち着いて読める濃さと余白。形・記号も添える） |
| 誤操作防止 | 現場の入口の帯は、離陸・着陸のボタンから離す。記録は 1 画面の選択で完結し、確認ダイアログは使わない（保存後に「詳細を記入する」を示す）。取消（運航管理者のみ）・訂正・取り下げは理由の入力が要る画面にし、主な操作の隣に置かない。報告の記録の確認チェックを入れるまで「記録する」を押せなくする。事実の項目に初期値を置かない（選び忘れを防ぐ）。「ある」「ない」「わからない」を色だけで区別しない |
| 日本語の文言の穏当さ | 責める・驚かせる語（違反、過失、不注意、落ち度、処分、罰則）を使わない。「事故を起こしました」ではなく「起きたこと」と書く。固定の文言（設計 A）は変えない。入力欄の見出しは「考えられる要因（推測でかまいません）」「とった対応」のように、事実を書きやすい言葉にする。目安は断定せず、「可能性があります」「確認してください」の語調を保つ。報告の記録は「利用者の申告」と常に添える |
| 全般 | 色だけで状態を区別しない（目安・報告の状態・簡易記録・取消は文字と記号）。375px で横スクロールなし。既存の紙面調（明るい紙面と暗い紺地）に合わせる。ロジック・経路・`data-testid`・文言の定数は変えない |

## 分量の判断と削る順

機能は 5 件（記録と版の履歴、報告の記録、目安、現場の簡易記録と端末の保存、他の画面との連携）、契約 18 項目は §13.6 の目安（10〜20）の上限付近。1 項目あたりの検証は重い（契約 1・2・7・12）ため、1.5 週間の上限と見る。遅れたときに削る順：

1. 「今日」の次にやること 2 項目と、日誌の `safety_issue` からのリンク（契約 13 のその部分。計画・日誌の節と `/ops/more` は残す）。
2. 報告のあとで事実が変わったときの「内容が変わった」の導出（`facts_fingerprint`。契約 7・10 のその部分。報告の記録そのものは残す）。
3. 一覧の絞り込み（`reportState`・`followUp`・`planId`。区分の絞り込みと一覧は残す）。
4. 連絡した先（`contacts_made`）の記録。

**削らないもの**：最初の安全の案内（G1）と固定の注意書き（N1〜N6）、追記専用の記録と報告の記録（版・取消・取り下げ・ハッシュ）、事実の項目に初期値を置かないこと、目安を 2 段のままにし「報告不要」「報告対象外」「報告が必要です」を出さないこと、報告の記録を利用者の申告と示すこと、個人情報を記録しないこと、現場の簡易記録とその端末保存（順序・二重防止・黙って捨てない）、判定エンジン・`ENGINE_VERSION`・証跡 ID を変えないことと回帰の確認、禁止語の不在。

## 未決事項

**推奨で決めたもの**（覆す場合は着手前に知らせる）：目安を 2 段にして「報告対象外」を出さない（判断 3）、区分は利用者が選ぶ（判断 4）、事実の項目は広く拾う（判断 5）、個人情報を持たない（判断 7）、現場の簡易記録は別モジュールの端末保存（判断 8・9）、書き込みの権限（判断 10）。

1. **sprint-12.md の当初案「事故／重大インシデント／報告対象外／要確認」の 4 段を改め、2 段にしてよいか。** 推奨：2 段にする。理由は判断 3 のとおり（「報告対象外」は義務がないという断定に当たり、一次資料が未照合の間は誤りになりうる）。U17 で区分が確認できたら、「事故」「重大インシデント」の目安を足す別の契約をつくる。
2. **操縦者が、自分が作った簡易記録を取り消せるようにするか。** 推奨：12e では運航管理者のみ（誤記録の影響が小さく、取消が消去に見えるのを避ける）。現場試用で押し間違いが多ければ、「作った本人は作成から一定時間内に取り消せる」を別の枠で検討する。

**ユーザーに伺うこと**：なし（上の 1・2 は推奨で決めた。覆す場合のみ知らせてほしい）。
