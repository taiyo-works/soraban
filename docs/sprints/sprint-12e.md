## 目的と位置付け

飛行の事後（sprint-12.md §2.2 の段階 8）のうち、**事故とヒヤリハットを、事実として確実に残す**スプリント。現場で何かが起きたとき、まず人の安全を確保してもらい、そのあと（または現場では最小の操作で）起きたことを記録し、飛行計画・日誌・機体・操縦者と結びつけ、国への報告の要否を確かめる手がかりと、報告した結果の記録を残す。

12e が終わると、利用者は次のことができる。

1. 事故・ヒヤリハットの入力画面を開くと、**最初に「飛行を中止し（速やかに着陸させ）、けがをした人の救護と危険の防止を最優先にしてください」という案内**が出る。入力はそのあとでよい。
2. 現場モードから、**2 回のタップほどで簡易に記録**できる（区分・けがの有無・時刻。詳細はあとで補う）。通信が切れても端末に残り、戻ったら二重にならずに送られる。
3. 事務所で、起きたこと（事象の類型、けがの有無、経過、とった対応、考えられる要因、再発防止）を詳しく記録し、あとから訂正できる（訂正は版として残る）。
4. 入力した事実から、**「報告の対象になる可能性があるか」の目安**が出る。目安は確認の手がかりであり、報告の要否を決めない。
5. 国への報告を DIPS 2.0 等で行ったら、その結果（日時・番号）を**利用者の申告として記録**できる。要否を国土交通省などに確かめたことも記録できる。
6. 飛行計画・日誌の画面から、その飛行に関する事故・ヒヤリハットへ移れ、日誌の「安全に影響のあった事項」から記録を始められる。

### 安全の原則（不可侵）

- **記録は事実の記録であり、法的な報告の完了も、責任の判断も意味しない。** この旨を、事故・ヒヤリハットのすべての画面に固定の注意書きとして出す（設計 A の N1）。
- **報告の義務の有無を、アプリは断定しない。** 「報告不要」「報告対象外」「報告の必要はありません」と出さない。同時に「報告が必要です」「報告義務があります」とも出さない（報告の要否は、起きた事実が類型に当たるかの判断であり、その判断は利用者が報告要領に照らして行う）。目安は「報告の対象になる可能性があります／入力の範囲では選ばれた事象がありません」の 2 段だけで、分からないときは可能性の側（厳しい側）に倒す。**事故と重大インシデントはどちらも報告の対象（一次資料で確認済み）なので、利用者の次の行動（DIPS 2.0 で報告する・要否を確かめる）に法令上の区分の判定は要らない。** 重傷と軽傷の境目は要領に定義がなく、アプリが判定すると誤りの危険があるため、区分も重さも判定しない。
- **数値の期限・罰則・連絡先を、アプリは出さない。** 「○日以内」「○時間以内」「○営業日」の数値の期限（要領にも記載が確認できない）、罰則の額、報告先の電話番号・メールアドレス、URL、条番号を、画面・API・データに作らない（文書にだけ置く）。報告の方法の案内は、一次資料で確認できた次の内容だけを、目安のデータの版から出す（設計 A）：DIPS 2.0 の「事故等の報告」から操縦者が速やかに行うこと、DIPS 2.0 で報告できないやむを得ない場合は報告要領に定める方法（様式による電話・電子メール）で報告できること。様式（Excel）の中身は未確認のため、様式の項目は出さない。
- **そらばんは国へ報告を送信しない。** 報告は DIPS 2.0 などの公式の手続きで行う。記録は利用者の申告で、そらばんが報告の完了を確認したものではない（12b の通報の記録と同じ作法）。
- **救護・安全の確保が先。** 入力を求める前に案内を出し、入力が済まなくても人命に関わる行動を妨げない。
- **個人を特定する情報を記録しない。** けがをした人・第三者の氏名、連絡先、病状の詳細、写真は扱わない（設計 B）。
- 「通報不要」の語は、どの画面・文言にも出さない。条番号・URL は `packages/regulations/src/model-aircraft.ts` にだけ置く方針のまま、**12e は条番号も URL も新しく書かない**（設計 A）。判定エンジン・`ENGINE_VERSION`・証跡 ID は変えない。

## 12e の設計の判断（planner の判断。generator は sprint-12.md の記述でなく本書に従う）

| # | 判断 | 理由 |

| 3 | **sprint-12.md の目安の出し方を改める。** 当初案の「事故／重大インシデント／報告対象外／要確認」の 4 段をやめ、**「報告の対象になる可能性がある」「入力の範囲では選ばれた事象がない」の 2 段**にする。「報告対象外」は出さない。事故・重大インシデントの法令上の区分も、アプリは出さない | 「報告対象外」と出すのは報告の義務がないと断定することで、入力が事実の一部しか表さない以上、誤りになりうる（12a が「通報不要」を禁止語にしたのと同じ理由。North Star §0.1.9「分からないときは厳しい側」）。**一次資料（2026-10-22 確認）で、事故も重大インシデントも報告の対象であることが確かめられた。** 利用者の次の行動（DIPS 2.0 で報告する・要否を確かめる）は区分によらず同じなので、法令上の区分の判定は要らない。重傷・軽傷の境目は要領に定義がなく、アプリが判定すると誤りの危険がある。区分は利用者が自分の言葉で選ぶ（判断 4）。ユーザー承認済み（2026-10-22） |
| 4 | **「事故／ヒヤリハット／まだ分からない」は、利用者が選ぶ区分**であって、法令上の事故・重大インシデントの判定ではない。画面に「法令上の区分ではありません」と書く | アプリが法令上の区分を決めると、判断の誤りが利用者の報告漏れになる。区分は一覧の整理のためだけに使う |
| 5 | 起きた事象は、**版つきのデータの「事象の類型」から選ぶ**（複数可。`INCIDENT_GUIDANCE_REVISION = 1`・状態 `confirmed`・出典「国土交通省航空局『無人航空機の事故及び重大インシデントの報告要領』（令和4年11月4日制定）。2026-10-22 原本照合」）。**目安に効く 7 類型**（人の死傷（重傷以上）／人の負傷（軽傷）／第三者の物件の損壊（軽微なものも含む）／航空機との衝突・接触（機体に損傷）／航空機との衝突・接触のおそれ（回避の措置をとったもの）／機体の不具合による制御不能（これによる紛失を含む）／飛行中の発火（推進装置が動いている間））のどれかを選べば「可能性がある」。**単独では目安に効かない事実の類型 1 つ**（操縦ミスなどによる操縦不能・機体の紛失（機体の不具合によらないもの）。`guidance = fact_only`）を置く。ほかに排他の「どれにも当たらない」「まだ分からない」（後者は可能性がある側）。各類型に要領に基づく説明文を持ち、選択肢の下に出す。**目安は類型だけで決め、利用者の区分（判断 4）は使わない** | 類型を要領の定める事故・重大インシデントの範囲（一次資料）に合わせ、利用者が事実を選びやすくする。操縦ミスによる操縦不能は要領で制御不能の対象外とされるが、事実としては残す価値があるため、単独では目安に効かない類型として置き、説明文で「不具合か分からないときは制御不能か『まだ分からない』を」「けが・損壊・発火があればその類型も」と案内する。旧案の「機体の紛失（要確認）」「その他」は廃止（紛失は制御不能に含まれるか、操縦ミスの類型に入る。その他は判断の手がかりにならない） |
| 6 | 目安は**記録の保存のたびにサーバーが事実から計算して版の中に残す**（画面の値は読まない）。後で類型のデータの版が変わっても、過去の版には当時の目安と類型のデータの版・出典が残る | 「当時は何を根拠に何を表示したか」を辿れるようにする（根拠の鎖の考え方） |
| 7 | **個人を特定する情報は列にも自由記述の想定にも置かない。** けがをした人の人数（0〜999）と有無だけを持ち、氏名・連絡先・病状の詳細は持たない。写真・画像は扱わない。操縦者は `pilot_id` だけを持ち、氏名は表示のたびに引く | 10 名以内の社内でも、記録は版として消せないため。`schema-columns.test.ts` の禁止語にも当たらない。自由記述には「書かないでください」の注意書きを出す（N5） |
| 8 | 現場の簡易記録は、**選択肢だけ**（区分・けがの有無・時刻・計画の ID）を端末に保存して送る。自由記述は端末に残さない。簡易記録は `detail_pending = true` で保存し、事象の類型は「まだ分からない」、機体の損傷は「わからない」にする（目安は可能性がある側に倒れ、あとから詳細を補う次にやることが出る） | 圏外・混乱の中で入力を減らしつつ、端末に個人データや座標を残さない（12c の端末保存の規則を守る）。「分からない」を既定にするのは、「当たらない」と誤って記録しないため |
| 9 | 簡易記録は 12c の `ops-outbox` を**そのまま拡張せず**、同じ規則（localStorage＋メモリのフォールバック、順序、4xx を黙って捨てない、`clientRequestId` による冪等性、利用者ごとのキー、ログアウトの警告）の**別の小さなモジュール**にする。共通にできる純粋な補助関数は import して再利用してよいが、12c の export の型・挙動・テストは変えない | `OutboxKind` は 12c の閉じた型で、変えると 12c の契約・テストに波及する。キーは `soraban:ops-draft:incident-<計画の ID>:<利用者の ID>`（`soraban:ops-draft:` の配下にして `clearOtherUsersDrafts` で消える形） |
| 10 | 書き込みの権限：**作成と報告の記録は運航管理者と操縦者**（操縦者は誰の飛行でも事実を記録できる）、**訂正・報告の記録は運航管理者と「自分の分」（記録を作った本人か、記録の操縦者が自分）**、**取消（誤登録）は運航管理者のみ**、閲覧者は読むだけ。閲覧は全役割 | 事実の記録を「自分の飛行でないから」と妨げない（12c が離陸の記録を止めない方針と同じ）。取消は記録が消えたように見えるため運航管理者に限る |

- 旧案の「機体の紛失（※要確認）」「その他」は廃止した（紛失は、不具合によるものは制御不能に含まれ、操縦ミスによるものは `loss_by_operation` に入る。「その他」は判断の手がかりにならないため。事実の詳細は経過の欄に書く）。
- 類型の追加・名称・説明文・状態の変更は、このデータの版を上げるだけで済み、型・画面・DB の CHECK は変えない。過去の記録は、保存した版の `guidance_revision` で当時の類型の名称・説明文を引ける（データは版ごとに残す。古い版を消さない）。
- データの各版に、出典・状態（`unconfirmed`／`confirmed`）・確認日・確認者を持たせる（12b の項目の対応表と同じ流儀）。画面の「※要確認」は、状態が `unconfirmed` の版にだけ出す（版 1 は `confirmed`）。データ・説明文に URL・条番号・電話番号・メールアドレス・罰則を書かない（「要領 3(1)a」などの参考の区分の列は文書だけに置き、データに入れるかは generator が決めてよいが画面に出さない）。

**`incidentGuidance(eventTypes, revision)`**（**区分 `kind` は使わない**）：
- `eventTypes` に `guidance = possible` の類型が 1 つでもあるか、`unknown` なら `possible`。`none` だけ、または `fact_only` の類型だけのときは `none_selected`。
- 出力は `{level, revision, reasons, source, status}`（`reasons` は当たった類型のキー）。案内の文（設計 A）はデータの版から出す。**「報告不要」「対象外」に当たる値・文字列と、「事故」「重大インシデント」の区分を返さない。**
- 8 類型の部分集合（2^8 通り。空集合は検査で拒む）と、排他の `none`・`unknown` を単体テストで全数確かめる。

**`validateIncident(input, mode)`**（`mode`＝`full`／`quick`）：
- `full`：区分・起きた日時・`summary`（1〜200 文字）・事象の類型（1 件以上の選択が必須。**既定の選択を置かない**）・けがの有無・機体の損傷（どちらも選択が必須）。`none`・`unknown` は他の値と一緒に選べない（400 `event_types_exclusive`）。けがの有無が「いる」なのに類型に `death_or_serious_injury`・`minor_injury`・`unknown` のどれも無いときは 400 `injury_type_missing`（けがの重さは利用者が選ぶ。分からなければ `unknown`）。値はその時点のデータの版にあるものだけ（400 `unknown_event_type`）。
- `quick`：区分・起きた日時・けがの有無だけが必須で、サーバーが `event_types = ["unknown"]`、`aircraft_damage = unknown`、`detail_pending = true`、`source = field_quick` にする。
- 長さ・値域（人数 0〜999、座標の対、`contacts_made` の値と重複、`follow_up_status`／`follow_up_on` の整合）を項目ごとの理由コードで返す。禁止語（設計 A）の不在を確かめる。

**`incidentReportState(records, currentFingerprint)`**：`reported`（有効な報告の記録あり）／`consulted`（報告の記録はないが、要否を確かめた記録あり）／`none`。さらに `changedSinceReport`（有効な報告・確認の記録の指紋が現在の指紋と違う）。

**`incidentNextActions(...)`**：記録の有無から毎回導出する（保存しない）。文言は `NEXT_ACTION_LABEL` に足す。

| 次にやること（動詞で始まる） | 条件（導出） | 押すと |
|---|---|---|
| 事故・ヒヤリハットの報告の要否を確認する | 目安が `possible` で、報告の記録も要否を確かめた記録も無い。または `changedSinceReport`。**報告の確認が済むまで出し続ける（日数・時間で消さない）。** 消えるのは、報告の記録か要否を確かめた記録が付いたとき、訂正で目安が `none_selected` になったとき、記録が取消されたときだけ | 記録の詳細（報告の記録のフォーム） |
| 事故・ヒヤリハットの詳細を記入する | `detail_pending`（取消されていないもの）。起きた日から 14 日以内（社内の目安） | 記録の訂正 |

- tier は 12b の表（通報の漏れ・目安の超過・未了）に合わせて generator が決め、完了報告に書く（要否の確認は通報の漏れと同じ重さ、詳細の記入は日誌と同じ重さを推奨）。期限の日付は作らない。`canAct` が偽（閲覧者など）のものは、リンクにせず「運航管理者に依頼」と示す（12b・12c と同じ）。
- 既存の `planNextActions` の期待（12b）と「今日」の並び（12c）は変えない。計画に結び付かない記録の次にやることも出せる形にする。

### D. 認可・API（すべて `opsHandler`。`OPS_ENABLED` 無効なら 404）

`authz.ts` に行を足す（`OPS_ACTIONS` に入れる。全役割 × `isSelf` の組合せを単体テストで網羅）：

| 操作 | 運航管理者 | 操縦者 | 閲覧者 |
|---|---|---|---|
| `incident.read` | 可 | 可 | 可 |
| `incident.create` | 可 | 可（誰の飛行でも） | 不可 |
| `incident.update`（訂正・対応状況） | 可 | 自分の分のみ（`isSelf`：記録を作った本人、または記録の操縦者が自分） | 不可 |
| `incident.report`（報告の記録・取り下げ） | 可 | 自分の分のみ | 不可 |
| `incident.void`（誤登録の取消） | 可 | 不可 | 不可 |

| メソッド・経路 | 内容 |
|---|---|
| `GET /api/ops/incidents` | 一覧（`?kind=`・`?followUp=`・`?planId=`・`?reportState=` で絞り込み。取消は既定で出さない）。要約に目安・報告の状態・簡易記録の印を含む。一括で引く（件数に比例してクエリが増えない） |

| `GET /api/ops/incidents/[id]` | 詳細（事実、目安と類型のデータの版・出典、報告の記録の一覧、報告の状態、結び付いた計画・日誌・機体・操縦者） |

### F. 現場の簡易記録と端末の保存

**入口**：現場モード（`/ops/plans/[id]/field`）の上部に、**常に見える小さめの帯（高さ 56px 以上・全幅）**「事故・ヒヤリハットを記録する」を 1 つ置く。離陸・着陸の大きなボタンの**隣・直上・直下に置かない**（誤タップを避ける。離着陸ボタンとの距離は 24px 以上）。押すと簡易記録の画面へ**移動する**（その場で記録されない。確認ダイアログは出さない）。12c の「押す大きなボタンは常に 1 つ」は変えない（この帯は大きなボタンではない）。

**簡易記録の画面**：①G1（最上部）→ ②N1 → ③区分（3 つ）→ ④けがの有無（3 つ）→ ⑤「事象の類型などは、あとで入力できます」の案内（簡易記録では類型を「まだ分からない」で保存する）→ ⑥「記録する」（全幅）。時刻は「いま」を既定にする。保存の直後に「記録しました。詳細はあとで記入できます」と、「詳細を記入する」「現場モードへ戻る」を出す。記録は残る（取消は運航管理者）。N2 を完了後に出す。

**端末の保存（送信待ち）**：12c の設計 F の規則を、簡易記録に適用する。

- 押した時点で、端末の `localStorage`（保存できなければメモリ）に 1 行保存し、`clientRequestId` と `occurredAt` を付けて自分のサーバーの API だけへ送る。成功（201・200）で消す。通信できない・5xx・時間切れは残して再試行する（接続が戻ったとき、画面を開いたとき、開いている間の 15 秒ごと）。順序を守る。
- 4xx（`clock_skew`・`too_old` など）の行は**黙って捨てない**。理由を出し、「あとから入力」（詳細な入力画面）へ案内し、破棄は利用者が選ぶ。
- 画面に「未送信 N 件」を常に出す（0 件は「送信済み」）。押した結果は送信の前に画面へ反映する。
- 端末に残す内容は、計画の ID・区分・けがの有無・時刻・識別子だけ。**氏名・技能証明書番号・座標・自由記述は入れない。** キーは `soraban:ops-draft:incident-<計画の ID>:<利用者の ID>`。ログアウトは未送信があるとき警告し、黙って消さない（12c と同じ）。他の利用者の保存は `clearOtherUsersDrafts` が消す。
- 12c のモジュールは export の追加を除き変更しない（判断 9）。

### G. テスト環境と E2E の作法

- サーバーの時計は `OPS_TEST_NOW`（JST 2027-01-05 12:00）。ブラウザの時計は `page.clock` で合わせる（12c・12d と同じ）。圏外は `context.setOffline(true)`。
- **過去の教訓：E2E で `waitForResponse` を `goto` の後に登録しない。** 応答が先に届くと待ち続ける（CI で起きた。`e2e/ops-db/sprint12a-db.spec.ts` の注記）。応答を待つときは、操作の**前**に `Promise.all([page.waitForResponse(...), 操作])` で登録するか、画面に結果（文言・要素）が出るまで待つ。generator・evaluator はこの書き方を守る。
- 色の比は 12c の補助関数（`e2e/field-checks.ts`）を再利用し、簡易記録の画面を明暗両方で検査する。
- 通常の E2E：`e2e/sprint12e.spec.ts`。DB あり：`e2e/ops-db/sprint12e-db.spec.ts`。

## 範囲外

- DIPS 2.0・国土交通省への報告の送信（DIPS 2.0 の API に事故の報告の API はない）、数値の期限の表示（要領にも記載が確認できない）、**報告先（官署）の連絡先の一覧（電話番号・メールアドレス）の表示**、様式（Excel）の提供。電子メール・電話での報告の方法は、`possible` の案内の文で「報告要領に定める方法（様式による電話・電子メール）で報告できる」と案内するだけにする。
- **報告の下書き**（報告要領の報告事項に沿って、そらばんの記録・計画・機体・操縦者・許可の登録から事実を整理し、項目ごとにコピーできる機能）。報告事項の項目と順は一次資料で確認できた（`accident-report-primary-sources.md` H）が、**Excel 様式の中身・更新の確認（U17 の残り ④）を前提条件として**、**別の契約（12e-2 の候補）**で行う。氏名・技能証明書番号を集める画面になるため、個人情報の扱いもその契約で決める。
- 事故・重大インシデントの法令上の区分の自動判定、罰則・責任の判断・原因の断定の表示。
- 写真・動画・図面の添付、けがをした人・第三者の氏名や連絡先の記録、保険会社への連絡の記録・案内、社内の緊急連絡先の表示（U19）。
- 通知（メール・プッシュ）、機体の自動休止・点検整備との連動（Sprint 13）、証跡の出力（Sprint 15）、事故・ヒヤリハットの集計や傾向の分析、他社との共有。
- 日誌（`flight_records`）への列の追加、日誌の自動作成。Service Worker による完全な圏外動作（12c の判断のまま）。
- 実機（iPhone・Android）の屋外での確認（ユーザー作業。U14 に簡易記録を含める）。

- [ ] 4. （単体）`incidentGuidance` が、8 類型の部分集合（2^8 通り。空集合は検査で拒む）と排他の `none`・`unknown` の全数で、設計 C のとおり返す（`possible` は `guidance = possible` の 7 類型のどれかか `unknown` を含むとき。`none` だけ・`fact_only` の類型だけは `none_selected`）。**区分（事故・ヒヤリハット・まだ分からない）を変えても結果が変わらない。** 出力に「報告不要」「対象外」に当たる値・文字列も、「事故」「重大インシデント」の区分も含まれない。データの版（`INCIDENT_GUIDANCE_REVISION = 1`）・状態 `confirmed`・出典（報告要領（令和4年11月4日制定）。2026-10-22 原本照合）が出力に含まれ、案内の文が設計 A と一致し、「※要確認」が付かない。テスト用の `unconfirmed` の版 2 を与えると、型・DB を変えずに類型の名称・説明文が変わり「※要確認」が付き、版 1 で保存した記録は版 1 の名称・説明文で読める。旧案の `aircraft_lost`・`other` が版 1 に無い。データ・コードに URL・条番号・電話番号・メールアドレス・罰則の額がない。

### C. API・認可

- [ ] 6. （DB・API）作成・訂正・取消・版の履歴：`full` で作成（201）、`quick` で作成（201。`detail_pending`）。同じ `clientRequestId` の再送（逐次と並行の 2 リクエスト）は新しい行を作らず 200 で既存を返し、内容が違えば 409 `request_conflict`。訂正は `reason` と `expectedVersion` が必須（違えば 409 `version_conflict`）で、訂正前の値が `/versions` に残り、事象の類型の変更で目安とデータの版が再計算される（区分を変えても目安は変わらない）（リクエストの値は読まれない）。取消は `reason` が必須で、取消した記録の訂正は拒否される。物理削除はない。計画を結ぶと現在のスナップショットの ID が入り、機体・操縦者が計画から引き継がれる。他の組織の記録・計画は 404。時刻の検査（未来 5 分超は 400 `future_time`、`quick` のその場の送信で ±5 分超は 400 `clock_skew`、送信待ちは 72 時間まで・超えると 400 `too_old`、`full` に過去の上限なし）。

| 誤操作防止 | 現場の入口の帯は、離陸・着陸のボタンから離す。記録は 1 画面の選択で完結し、確認ダイアログは使わない（保存後に「詳細を記入する」を示す）。取消（運航管理者のみ）・訂正・取り下げは理由の入力が要る画面にし、主な操作の隣に置かない。報告の記録の確認チェックを入れるまで「記録する」を押せなくする。事象の類型・けがの有無・機体の損傷に初期値を置かない（選び忘れを防ぐ）。類型は 1 つ 1 行・全幅のチェックにし、説明文を選択肢のすぐ下に読みやすい大きさで出す（長い説明は折りたたまず、行間を取る）。目安に効く 7 類型と、`fact_only` の「操縦ミスなどによる操縦不能・機体の紛失」は間を空けて分け、後者が「当たらない」の意味に見えないようにする。「どれにも当たらない」「まだ分からない」は他と離して置く（同時に選べない）。「ある」「ない」「わからない」を色だけで区別しない |
| 日本語の文言の穏当さ | 責める・驚かせる語（違反、過失、不注意、落ち度、処分、罰則）を使わない。「事故を起こしました」ではなく「起きたこと」と書く。固定の文言（設計 A）は変えない。入力欄の見出しは「考えられる要因（推測でかまいません）」「とった対応」のように、事実を書きやすい言葉にする。目安は断定せず、「可能性があります」「確認してください」の語調を保つ。報告の記録は「利用者の申告」と常に添える |
| 全般 | 色だけで状態を区別しない（目安・報告の状態・簡易記録・取消は文字と記号）。375px で横スクロールなし。既存の紙面調（明るい紙面と暗い紺地）に合わせる。ロジック・経路・`data-testid`・文言の定数は変えない |

## 分量の判断と削る順

機能は 5 件（記録と版の履歴、報告の記録、目安、現場の簡易記録と端末の保存、他の画面との連携）、契約 18 項目は §13.6 の目安（10〜20）の上限付近。1 項目あたりの検証は重い（契約 1・2・7・12）ため、1.5 週間の上限と見る。遅れたときに削る順：

1. 「今日」の次にやること 2 項目と、日誌の `safety_issue` からのリンク（契約 13 のその部分。計画・日誌の節と `/ops/more` は残す）。
2. 報告のあとで事実が変わったときの「内容が変わった」の導出（`facts_fingerprint`。契約 7・10 のその部分。報告の記録そのものは残す）。
3. 一覧の絞り込み（`reportState`・`followUp`・`planId`。区分の絞り込みと一覧は残す）。
4. 連絡した先（`contacts_made`）の記録。

**削らないもの**：最初の安全の案内（G1）と固定の注意書き（N1〜N7）、追記専用の記録と報告の記録（版・取消・取り下げ・ハッシュ）、事象の類型に初期値を置かないこと、類型を版つきのデータに置き出典・状態と説明文を出すこと、報告の確認が済むまで次にやることに出し続けること、目安を 2 段のままにし「報告不要」「報告対象外」「報告が必要です」を出さないこと、報告の記録を利用者の申告と示すこと、個人情報を記録しないこと、現場の簡易記録とその端末保存（順序・二重防止・黙って捨てない）、判定エンジン・`ENGINE_VERSION`・証跡 ID を変えないことと回帰の確認、禁止語の不在。

## 未決事項（2026-10-22 にすべて決定済み）

ユーザーが「制度を調べた上で、オーケストレーターの推奨で」で承認した（2026-10-22）。以下は決定の記録である。

1. **sprint-12.md の当初案「事故／重大インシデント／報告対象外／要確認」の 4 段を改め、2 段にする。**（承認済み）理由は判断 3 のとおり。「報告対象外」は義務がないという断定に当たり、報告要領の原本が未照合の間は誤りになりうる。加えて、事故も重大インシデントも報告の対象（一次資料で確認済み）なので、利用者の次の行動に法令上の区分の判定は要らない。事象の類型は報告要領の範囲に合わせた版つきのデータで持つ（判断 5）。
2. **簡易記録の取消は運航管理者のみ。**（承認済み）誤記録の影響は小さく、取消が消去に見えるのを避ける。現場試用で押し間違いが多ければ、「作った本人は作成から一定時間内に取り消せる」を別の枠で検討する。
3. **報告の下書き（報告事項に沿った事実の整理とコピー）は 12e の範囲外。**（オーケストレーターの推奨。承認済み）Excel 様式の中身の確認（U17 の残り ④）を前提条件に、別の契約（12e-2 の候補）で行う（判断 14）。
4. **一次資料に基づく改訂（2026-10-22、オーケストレーターの決定）。** 類型を要領の範囲に合わせた 7 類型＋`fact_only` 1 類型＋排他 2 つにし（旧案の「機体の紛失」「その他」は廃止）、目安は類型だけで決める（区分の条件を外す）。データの版 1 を原本照合済み（`confirmed`）にし、「※要確認」は付かない。`possible` の案内に DIPS 2.0 の「事故等の報告」・「速やかに」・やむを得ない場合の電話・電子メールを入れ、「速やかに」を禁止語から外した。G1 を「飛行を中止し（速やかに着陸させ）」に改めた。罰則・電話番号・メールアドレス・URL・条番号は画面・データに出さない。

**本書で planner が決めたこと**（推奨で決めた）：区分は利用者が選ぶ（判断 4）、個人情報を持たない（判断 7）、現場の簡易記録は別モジュールの端末保存（判断 8・9）、書き込みの権限（判断 10）。
