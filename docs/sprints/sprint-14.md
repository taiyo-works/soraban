## 目的と位置付け

企画書の現場の流れは「飛行前点検 → 飛行（離着陸記録）→ 飛行後点検、次の飛行で繰り返し」である。いまの現場モードは、計画ごとに「飛行前の確認（日常点検・緊急用務空域・通報済みの再確認・携行品）→ 離陸・着陸 → 日誌」で、書類・手続きは人が「確認した」を押すだけ、現場状況と飛行後点検は手順に無い。

14 が終わると、操縦者は現場で次のことができる。

1. 現場画面の飛行前に、**書類・手続きの項目が、登録内容から自動で「確認済み」「要確認」「満たさない」に分かれて**出る。足りない（要確認の）ものだけを 1 タップで確認できる。根拠（どの登録の、どの番号・期間か）がたどれる。
2. 空域（緊急用務空域・飛行自粛要請）を、公表ページへのリンクつきで確認し、確認の事実を残せる。
3. 現場状況（第三者・他機・風・気温・雨・視程）を、飛行ごとに自分で確認して残せる。
4. 着陸のあと、**飛行後点検**へ進み、記録できる。次の飛行を始めると、前後の確認が飛行ごとにそろう。
5. 離陸の時点の未了事項（`gaps`）に、書類・手続きと現場状況の未了が出る。離陸は止めない。

## 設計の判断（planner の判断。generator は本書に従う）

1. **飛行ラウンド**: 「1 回の離陸〜着陸と、その前後の確認・点検」を 1 ラウンドとする。ラウンドは行から**導出**し、保存しない（12c の「状態は行から毎回導出」と同じ）。着陸の後に新しい飛行を始めると次のラウンド。取り消し（undo）でラウンドは戻る。
2. **何がラウンドごとで、何が計画ごとか**（企画書の「現場状況は毎回人が確認」「書類・手続きは登録から自動判定」に合わせる）。

   | 項目 | 単位 |
   |---|---|
   | 日常点検（飛行前）・飛行後点検 | ラウンドごと |
   | 空域（緊急用務空域・飛行自粛要請）の確認 | ラウンドごと（当日に指定が変わり得るため） |
   | 現場状況（第三者・他機・風・気温・雨・視程） | ラウンドごと（毎回人が確認） |
   | 書類・手続きの自動判定 | 画面を開くたびに**導出**（登録が変われば変わる）。離陸の時点の結果を `gaps` に写す |
   | 書類・手続きの「人が確認した」 | 計画ごと（同じ計画の次のラウンドに持ち越す。取り消しで戻せる） |
   | 通報済みの再確認・携行品 | 計画ごと（現状のまま） |

   **点検をいつ・何回するかの運用上の短縮ルールは、この契約で決めない**（※要再確認。取扱要領・マニュアルの定め）。企画書どおり、各ラウンドに前後の点検の手順を出す。連続飛行で前回の結果を土台に「すべて正常」を押しやすくする UI は許すが、項目別の保存は必須（既存）。
3. **書類・手続きの判定は 3 値**: 確認済み（自動）／要確認（人が確認する）／満たさない（登録に反する）。**判定できないときは要確認**に倒す。「不要」「該当なし」と出さない（北極星 §0.1.9。通報は既存の「通報不要とは出さない」規則を守る）。各項目は**根拠**（登録の種類、番号、有効期間、版または確認日）を表示でき、登録の画面へ移れる。
4. **項目ごとの判定の考え方**（P-1 で確定する一覧に、同じ形式で足す）:

   | 項目 | 確認済み（自動） | 満たさない | 要確認 |
   |---|---|---|---|
   | 通報（受付番号） | 計画の通報が必要または要確認で、離陸前に有効な通報の行があり受付番号がある（`effectiveReport`・`COMPLETED_STATES` を再利用） | — | 通報の行が無い・受付番号が無い・要否が判定不能。**通報の要否の語は 12b の既存の語を再利用し、「通報不要」を出さない** |
   | 許可・承認（期間と対象） | `permit-match` で、飛行日が有効期間内、計画の特定飛行の形態が範囲に含まれ、失効していない | 期間外・失効・範囲外 | 登録が無い・照合できない |
   | 技能証明 | 操縦者の有効期限が飛行日以降 | 期限切れ | 期限が未入力。限定など登録に持たない条件がある場合は、自動で確認済みにしない |
   | 登録記号 | 計画の機体の登録記号が機体台帳にあり、機体が取消・休止でない | 機体が取消・休止 | 登録の**有効期限**は記録場所が無いため、確認済みの表示に「有効期限は人が確認」を残す（Sprint 24 で自動化） |
   | リモートID | 機体登録に対応する列があり、有効 | 無効と登録されている | 対応する列が無い・未入力（常にここ） |
   | 飛行マニュアルの組み合わせ制限 | 組み合わせの登録があり、計画が収まる（現状は登録が無い見込み） | 組み合わせに反する | 登録が無い（常にここ） |

5. **記録の形（12c の作法）**: 現場の事実は**追記専用の行**（更新・削除・TRUNCATE を拒む）。1 タップ 1 行、`client_event_id` で冪等、DB が `snapshot_id`・`plan_version`・`recorded_by_*`・`recorded_at`・`content_hash` を決める（アプリが送った値は使わない）。誤りは「取り消す」（undo）で戻す。推奨する形: `flight_field_events` の `item` に「書類・手続きの確認（項目キーつき）」「飛行自粛要請の確認」「飛行後点検」を足し、現場状況は構造化された列を持つ**新しい追記専用の表**に置く。最終の列と制約は generator が PR に示す。満たすべき性質は下の契約で固定する。
6. **現場状況の記録**: 事実の記録であり、**合否の閾値をこの契約で決めない**（法令の数値を創作しない。※要再確認）。入力は、第三者（いない／いる）、他機（いない／いる）、雨（なし／あり）、視程（良好／制限あり）の選択と、風速（m/s）・気温（℃）の数値（任意。測れない現場がある）。「いる／あり／制限あり」を選ぶと備考を必須にし、離陸の未了事項に「現場状況に注意あり」を出す。**離陸は止めない**（12c の「飛んだ事実の記録を止めない」を守る）。
7. **飛行後点検**: 着陸の後、現場画面に「飛行後点検」の手順が出る。既存の日常点検の入力（`timing=post_flight`）へ移って戻る（`inspectionNewHref` と同じ作り）。飛行後点検を後回しにできる（未了事項として残る。日誌・今日の「次にやること」に出る）。異常があれば、不具合として記録する導線を出す（整備への紐付けは Sprint 16）。
8. **オフラインへの備え（Sprint 15 の前提）**: 新しい現場の事実は、すべて **12c のイベントの形で、端末の送信待ちに乗せられる**ようにする（クライアントが識別子と時刻を付ける）。S14 では送信待ちの許可リスト（端末に残す項目）を広げるだけで、IndexedDB・Service Worker は S15。端末に残すのは、項目キー・結果・数値・時刻・識別子。**氏名・技能証明書番号・座標・備考の自由記述は端末の送信待ちに入れない**ことは変えない（備考が必須の場合の扱いは契約 C-9）。
9. **画面の方針**: 12h の v2 部品と現場モードの寸法（押す部品 56px、重要な画面 64px）を使い、Sprint 13 §7 の方針（結論がスクロールなしで見える、情報は 3 段、色は操作の橙と判定色だけ）に従う。**Sprint 13 §7 の「点検の見直し」はこのスプリントに統合する**（要承認）。
10. **文言**: 「代行」「代理」を使わない。通報不要・手続き不要と読める語を、判定不能・要確認の状態に使わない。登録内容の表示は、許可書や技能証明の**原本・写しを意味する表現にしない**（Sprint 18 で扱う）。

### B. 書類・手続きの判定（単体・DB）

| # | 内容 |
|---|---|
| B-1 | 判定の純粋関数が、P-1 の各項目について、確認済み／要確認／満たさないを返す。**全項目に、登録が無い・判定できない入力の場合の「要確認」の単体テスト**がある（「確認済み」「該当なし」にならない） |
| B-2 | 許可・承認: 期間内・範囲内で確認済み、期間外・失効・範囲外で満たさない、登録なしで要確認（`permit-match` の既存の結果と一致する） |
| B-3 | 技能証明: 有効期限が飛行日以降で確認済み、期限切れで満たさない、期限未入力で要確認。飛行日が日付またぎ（JST 0 時付近）でずれない |
| B-4 | 通報: 要または要確認の計画で、離陸前に完了した通報の行（受付番号つき）があれば確認済み。離陸**後**に記録された通報は確認済みにしない。要否が判定不能なら要確認。画面・単体テストのどこにも「通報不要」の文言を新しく作らない |
| B-5 | 登録記号: 機体が取消・休止なら満たさない。確認済みの表示に「有効期限は人が確認」が付く |
| B-6 | 各判定が根拠（登録の種類、番号または記号、期間、確認の版）を返す。技能証明書の番号は根拠の文字列に**含めない**（名前と期限まで） |
| B-7 | 判定は他の組織のデータを読まない（組織をまたぐ登録を取り違えない）。DB テストで固定する |

### C. 記録（DB・E2E-DB）

| # | 内容 |
|---|---|
| C-1 | 新しい記録は追記専用。更新・削除・TRUNCATE が、テーブルの所有者のロールでも拒否される（SQLSTATE `SB409`、12c と同じ作法） |
| C-2 | 同じ `client_event_id` の再送は、内容が同じなら既存の行を返し、行は増えない。内容が違えば 409 で拒否される |
| C-3 | 記録を取り消す（undo）と、導出される状態が戻る。同じ行を 2 回は取り消せない。日誌済みの飛行に紐づく記録は取り消せない（12c の規則を維持） |
| C-4 | DB が `recorded_at`・記録者の表示名と役割の写し・`content_hash`・計画の現在のスナップショットと版を決める。アプリが送った値は使わない |
| C-5 | 認可: `viewer` は記録できない（403）。`pilot` と `manager` は記録できる。他の組織の計画には記録できない（404）。取り消された計画（`plan_cancelled`）には記録できない |

## 再評価後のユーザー決定（2026-10-30）

条件付き合格（`docs/evaluations/sprint-14-eval.md`「再評価（9613f05）」）を受けて、ユーザーが次を決めた。Sprint 14 の追加修正として扱い、再評価で確かめる。

1. **飛行後点検は「今日」の次にやることに常に出す**（D-7 は文言どおり）。上位 8 件の枠に押し出されないようにする。
2. **通報の前後は記録の時刻で判定する**。サーバーが決める記録の時刻（`created_at`）が離陸より後の通報は、利用者が入力した通報日時が前でも「要確認」にする。
3. **日誌済みの飛行のラウンドに属する空域・現場状況などの確認は取り消せない**（409）。C-3 をラウンドの確認にも広げる。
4. 飛行後点検を計画内に絞る対応（評価の R-1）は **Sprint 15 に含める**（`sprint-15.md`）。
